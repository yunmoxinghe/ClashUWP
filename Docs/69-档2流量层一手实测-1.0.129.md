# 档 2 流量层一手实测（2026-10-27 21:52–21:59，本机已有真 IPv6）

环境：1.0.129 装机实物；`settings.txt` 末条 `ipv6=2`；路由器 IPv6 已开（WAN GUA + PD，见 Docs/68 §十二.4）；
WLAN ifi=22 三个全局 v6 地址（RA /128、RA /64、DHCP `::1000/128`）；隧道 ClashUWP ifi=47 `fd66:6:6600::2/128`；
`2000::/3` 与 `fdfe:dcba:9876::/64` 都在 ifi=47；`nrpt 规则数=1`。

## 一、v6 流量真的走完了隧道（档 2 · 经普通 v4 节点）

| 请求 | 结果 |
| --- | --- |
| `curl -6 https://api.ipify.org` | **200**，`fdfe:dcba:9876::33` → `Established ... from fd66:6:6600::2 port 60173`，出口 `209.141.58.4` |
| `curl -6 https://www.gstatic.com/generate_204` | **204**，源 `fd66:6:6600::2` |
| `curl -6 https://www.google.com/generate_204` | **204**，0.475 s |
| `curl -6 https://www.cloudflare.com/cdn-cgi/trace` | **200**，`ip=209.141.58.4 tls=TLSv1.3 colo=SLC` |
| `curl -6 https://one.one.one.one/cdn-cgi/trace` | **200**，同上 |
| `curl -4` 同一批对照 | 全部同码同出口 |

⇒ 本地 v6 应用（fake-ip `fdfe:` 池、源 `fd66:6:6600::2`）→ 内核 TUN → 代理节点 → v4 出口，
整条链路通；v4-in 与 v6-in 在同一个节点上给出**同一个出口 IP**，说明差异只在本地那一侧，而那一侧已经打通。

## 二、v6 字面量节点被桥内核真拨通（档 2 独有收益）

`select 星链机场 ipv6-高速-德州`（server `2602:f9f3:0:2::470`，type=tuic）后：

| 请求 | 结果 |
| --- | --- |
| `curl -4/-6 https://api6.ipify.org` | **200**，返回 `2602:f9f3:0:2::470` —— 站点看到的正是该节点自己的 v6 地址 |
| `curl -4 https://api.ipify.org` | 200，返回 `209.135.168.241`（同一节点的 v4 出口） |
| `curl -6 https://www.cloudflare.com/cdn-cgi/trace` | 200，`colo=DFW`（德州） |
| `groups` 里四个 v6 节点的测速 | 德州 589 ms / 洛杉矶 1535 ms / 纽约大学 1474 ms / 纽约大学Tiktok 2133 ms —— 全非 0 |
| `Find-NetRoute 2602:f9f3:0:2::470` | `InterfaceAlias=WLAN`（ifi=22），不是隧道 —— 节点服务器的 v6 拨号没有回环 |

⇒ 桥内核经物理 WLAN 用真 IPv6 拨到了字面量 v6 节点服务器，且端到端跑出 200。
这正是档 1（`ipv6: false`）被判死刑的那 4 个节点，`Docs/68 §十二.3` 的推断第一次拿到实物。
测完已 `select 星链机场 自动选择` 复位。

## 三、订正：先前「v6-in/v4-out 经代理节点断掉」是错的

21:52 那轮我看到 `curl -6 https://api6.ipify.org` rc=35，而同节点组 `curl -4 https://api.ipify.org` 200，
据此写成「断点在 v6-in/v4-out」。补测同一域名两族各一次：

```
api6 v6-in  rc=35 :: schannel: failed to receive handshake, SSL/TLS connection failed  CODE=000 TIME=0.244
api6 v4-in  rc=35 :: 同上                                                              CODE=000 TIME=0.249
```

两族**同错同耗时** ⇒ 与本地地址族无关，是「US高速拉斯维加斯(209.141.58.4) → api6.ipify.org」这一对
不通（该节点访问同站点的其它域名两族都 200）。换到 `ipv6-高速-德州` 后 api6 直接 200。
教训：一次 A/B 必须锁死「同域名同节点、只换族」，否则换的是站点不是族。

## 五、【1.0.130 同日续】这份实物换来了两件事

① **默认档从 0 抬到 2 并装机复验**：`settings.txt` 里一条 `ipv6=` 都不写，插件仍读回 `ipv6=2`，
形状、`SKIP_SYSTEM_IPV6_CHECK=1`、`clash_bridge_start rc=0 用时=197ms`、
以及**默认路径上的流量层**（`curl -6` api 200 / gstatic 204 / google204 204、
`ipv6-高速-德州` delay 200 `{"delay":301}`）全部同刻拿到实物 —— 读数与判据见 **Docs/70 §一**。

② **档 0 与档 1 也在同一台机器上跑到流量级**，本文件 §一/§二 不再是唯一一档的实物：
档 0 的旁路被 `Find-NetRoute`（三个全局 v6 目的地位全选 `WLAN ifi=22`）+ `ping -6` 3/3 +
内核连接列表里没有它们 四项同向钉死；档 1 则给出 `AAAA` 空应答、`curl -6` 全 rc=6、
`delay` v6 节点 **HTTP 503**（Docs/70 §三/§四）。
★ 其中一条限定值得单独抄回来：**档 0 会话里 AAAA 全空应答不是这一档的功劳**，
是 NRPT 根规则把 DNS 整条拽进隧道 + 订阅自带 `dns.ipv6: false` 的产物
（同窗口里 `nslookup` 绕开 Windows 解析器就能拿到真记录）。
所以 §一 那句"v4-in 与 v6-in 在同一个节点上给出同一个出口 IP"的对照组，
在档 0 下根本不是"v6 走代理失败"，而是"v6 压根没被解析出来"——读表的人要分得清这两件事。
