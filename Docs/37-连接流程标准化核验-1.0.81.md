## 一 · 与"盾标"直接相关的一处内部矛盾（必须先订正）

记忆里挂着"盾标唯一成立根因是 `ServerUri=127.0.0.1`"，但本仓库自己的取证数据不支持"唯一"这个词：

- `Docs/27` §根因2 的证据块（引先遣 docs/48-D1）原文是：
  - 臂 A（loopback ServerUri）：NCSI 新增 **0 条**事件；`IPv4Connectivity = NoTraffic`
  - 臂 B（真实黑洞 ServerUri）：NCSI 新增 1 条：**`Capability=Local`**，reason=`PassivePacketHops`
- 也就是说**换成黑洞之后，NCSI 报的仍然是 `Local`，不是 `Internet`**。
- 但同一篇 `Docs/27` 第 89 行却写成"不回 ICMP，NCSI 的被动探测能正确判断为**可达 Internet**" —— 这句话与它上面 12 行前贴的数据直接冲突。

⇒ 结论：`ServerUri=192.0.2.1` 这一步**方向对、但从未证明过它能把 Capability 推到 Internet**。1.0.73/1.0.75/1.0.77 三轮都没量过装机的 NCSI 事件，盾标至今没有一次"改动前后对比"的正证。

另外，官方口径到今天为止也只有一句 **"connected to a *recognized* VPN"**（[Microsoft Support](https://support.microsoft.com/en-us/windows/connect-to-a-vpn-in-windows-3d29aeb1-f497-f6b7-7633-115722c1009c)），"recognized" 从未有公开定义；该功能随 2023-05 配置更新 KB5027423 引入，判据在 shell 侧闭源。所以我们无法从文档侧证明"改了 ServerUri 就一定出盾标"。

## 二 · 确认有害的偏离：Encapsulate 不走官方出参

**位置**：`ClashVpnPlugin.cs:1133-1135`（出参 `encapulatedPackets` 收下即弃）+ `:1459-1512` `TryReturnSendBuffer` 档 2。

**机制**：官方给 `AppendVpnSendPacketBuffer` 的形参名就是 `encapsulatedPacketBuffer`，`FlushVpnSendPacketBuffers` 的条文是 "Flushes any appended send packet buffers"。⇒ 档 2 的每包 Flush 语义上等于**把裸 L3 包当"封装结果"交平台经外层 transport 发出去**：每一份出站流量在本机被重复 UDP 发一次（明文负载上局域网 + 等量上行占用）。

**为什么当初这么写**：数据面在进程内（mihomo），我们没有"封装结果"可交，出参路是空的。这个理由成立，但选档 2 而不是档 4 是因为档 4 未实测（`Docs/09 §3.1` 在册质量债）。

**对盾标的可能影响（推断，未量）**：UDP 反复打黑洞地址会招 ICMP 端口不可达，先遣 docs/93 记过"外层 socket 一旦被 ICMP 拒绝，OS 直接拆通道重拨"。若平台按"外层 transport 不可达"降低对该隧道的可信度，就会同时影响 828 重拨环与 NCSI 的 Passive 判定 —— 这条链只有推理，没做过单变量。

**解法已在仓**：档 4（`:1434-1441`，`RemoveAtBegin` → 就地处理 → `packets.Append()` 塞回原列表让平台 cleanup，一次 Append/Flush 都不调）。**仍未实测。**

**【1.0.87 订正】**默认已从档 2 抬到档 5（`LocalSettings.EncapReturn = 5`），实测结论见 §5.3：抬档**没有**消掉上面这条"重复 UDP 发往外层黑洞"的质量债 —— 包照样经 `AppendVpnSendPacketBuffer` 交出去，只是提交次数从每包一次变成每批一次。真正能消掉它的是档 4，而档 4 的风险形态（赌平台自己回收，赌错就是 7188 后黑洞）没有变。

## 三 · 未验证即上线的偏离

**1. namespaceScope 传空对象（`:758`）**
`VpnPacketBufferList`/trafficFilter 那一路实测过"空对象 ≠ null"（空对象=默认 deny），而这里 dnsInTunnel=0 时传的是**空 `VpnDomainNameAssignment`**。若空对象在 namespace 这一路同样是"下发一条根 Namespace 的策略"，就正对上 `Docs/08 §10.10` 那次孤儿 NRPT（`Namespace="."`）造成整机断网的形状。**这一项本仓库明确标注"属未验证"，是本次核验里风险最高的一条。**

**2. Connect 内同步阻塞（`:620` 的 `GetResult()`、`:846` 桥启动数秒）**
官方 sample 同样 `.Wait()`，形状不算越规；但平台对 Connect 有超时，桥阻塞数秒这段时间里会话状态停在 Connecting。1.0.41 已加内部诊断日志（`StartMihomoBridge silent failure`），仍未量过超时余量。

**3. keep-alive 空转（`:1633-1720`）**
`GetKeepAlivePayload` 交出去的包被平台发往黑洞 ⇒ 平台的保活判定对我们无意义。真正的存活判定被我们自建的两条看门狗接管（`:854`、`:865`）。设计上自洽，但要写清"平台侧 keepalive 不参与健康判定"，否则以后有人按官方语义读它就会读反。

## 五 · 追问与本轮处置（1.0.87 实装）

用户追问两点：①"内核为什么自己发出去，不该内核交给我们再交给系统吗"；②"这么卡，快接入正确的 API"。

### 5.1 架构问题的口径（补进 Docs/09 §3.1 的语义）

"内核交给我们、我们再交给系统"确实是官方形态，但在现有路线 A 上**做不到**，原因是机制而非写法：

- 桥里是 **gvisor 用户态栈**（`clash_bridge_put_packet` 收的是裸 L3 包），它在 mihomo 内部把内层 TCP **终结**了 —— 应用那条连接在隧道里就到头了。
- 之后 mihomo 用自己的 Go dialer **另开一条真 socket** 连节点（所以有 `clash_bridge_bound_iface` 这个观测点）。那条线上的字节是 VMess/VLESS/TLS 密文流，Go 直接 write 进 socket，**插件侧从来见不到这些字节**，因此没有"封装结果"可以填进 `encapulatedPackets`。
- 就算见了也装不进平台的口子：`encapulatedPackets` 只会经 `AssociateTransport` 关联的**那一个** transport、**那一个**已连接对端发出 —— 一份订阅几十个不同 IP/端口/协议的节点在这条路上表达不了。
- `LocalSettings.cs:219-222` 早就写着同一句：档 2 是过渡形态，"真正的协议封装要在 `encapulatedPackets` 里放真正的隧道报文（WireGuard 等）时才成立"。

⇒ 现有架构下"正确用法"只剩**怎么归还 buffer**这一个变量，即档 4/5。

### 5.3.1 ★ 本轮最重要的一条否定结论：Flush 次数不是"卡"的主因

`flush == calls` 逐字成立 ⇒ 平台**基本一批只交 1~2 个包**就回调一次 `Encapsulate`（`encap/calls` 全程 ≈ 1.75~2.2）。所以档 5 相对档 2 的收益上限就是"每包一次 Flush → 每批一次 Flush"，本轮实测省掉 **43%**（21985 包 → 12606 次提交），而不是量级上的下降。

推论：靠攒批治卡顿没有实现空间。要把每批包数抬上去，管的是平台侧的批处理策略与回程侧的 `receiveBatch`（本轮 `receiveBatch=0` 未启），不在这个开关的管辖范围内。**下一轮要治"卡"，得先定位它到底在哪一段**（内核转发 / 回程泵 / 节点本身 RTT），而不是继续调 buffer 归还方式。

（口径提醒：别把本轮 103 包/s 与 run 35 档 2 的 37 包/s 当成对照 —— 两轮后台负载不同，`Encapsulated` 的绝对值不可比；本轮唯一可比的是同一会话内的 `ret/encap/left/flush` 关系。）
