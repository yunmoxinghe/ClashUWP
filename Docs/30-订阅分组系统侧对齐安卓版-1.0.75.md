## 一、六项缺陷与修法

### 1.1 select：组名带空格被拆错（P0）

- **症状**：面板点一个成员名带空格的组（`美国 01 直连`）里的节点，切不过去，报"找不到组 美国"。
- **根因**：调试命令与界面共用一条字符串通道 —— 界面把组名和节点名拼成 `"{group} {member}"`
  交给 `RunSelectAsync`，而它按**第一个空格**拆。订阅里组名、节点名普遍带空格，这个口径从原理上就不成立。
- **安卓口径**：CMFA 的 `SwitchProxyItemAction` 传的是 `(group, node)` **两个值**，从来不拼文本。
- **修法**：
  - 新增 `MihomoController.SelectAsync(string group, string node)` —— UI 走两个独立实参，不再拼字符串
    （`MainComponent.SelectAsync` 的调用点同步改掉）；
  - `RunSelectAsync` 保留"一行文本"入口（调试命令用），拆法改为 `SplitSelectArg`：
    **在已知组表里做最长前缀匹配**（`arg` 以 `组名 + 空格` 开头，取最长的那个），
    匹配不到才退回旧的空格口径 —— 目的是让"找不到组 X"的报错还能列出可抄的候选；
  - 组名互为前缀时取最长（`自动优选` 与 `自动优选 备用` 不能撞）；只给一段时当节点名，组名由调用方补。

### 1.2 代理组被当成节点（P0）

- **症状**：组选择页里，一个组的名字出现在"节点"列表里，看起来像"组成了节点"。
- **根因**：分类做在**前端呈现层**，而后端只给了一串成员名。`GET /proxies` 的每条条目带
  `all`（组才有）与 `history`（测速历史），旧代码在读表时按 `IsSelectableGroupType` 直接
  `continue` 掉了内置策略与非 Selector 组，**这些条目就没进名称表** —— 于是"成员里有个也叫 X 的组"
  在 UI 眼里与普通节点无异。
- **安卓口径**：CMFA 在**后端** `convertProxies` 里算 `isGroup = hasAll && !builtin`，
  嵌套组照样列出、副标题写 `Selector(<now>)`，且**只有 `type == "Selector"` 的组接点行动作**
  （url-test / fallback / load-balance 是只读的，由内核自己选）。延迟胶囊只在
  `delay in 0..Short.MAX_VALUE` 时出现，**从不显示"未测"**。
- **修法**：
  - `MihomoController.ReadProxiesTable` 返回值扩成 `(Groups, LastDelay, ByName)`，
    新增 `record ProxyInfo(Name, Type, IsGroup, Now, IsBuiltin)`，
    分类在 `builtin` / 组类型过滤**之前**对**每一条**记录（结构性判据：`有 all 且不是内置策略`）；
  - `KernelView.Group/Member` 带上 `Type/IsGroup/IsBuiltin/Now`，
    新增 `IsUserSelectable`（只有 `Selector`）与 `RealNodeCount`（非组、非内置策略的成员数）；
  - `MainComponent`：`GroupPicker` 计数在组≠节点时写成 `（节点 2/成员 5）`；
    `MemberList` 对非 Selector 组渲染**纯文本行**并加一句"该组类型是 {Type}：由内核测速/故障转移自己选，
    和安卓版一样不可手选"；`MemberSubtitle` 对嵌套组给 `{Type}({Now})`（没选过给 `(未选)`），
    对内置策略给类型或"内置策略"，延迟只在 `DelayMs >= 0` 时才拼上去；
  - `RunGroupsAsync`（`debug-cmd groups`）同步：打印 `成员=N（其中节点=M）`，
    逐成员带 `[组:{Type}({Now})]` / `[策略]` 标记，避免调试通道读出口径又不一致。
- **刻意保留**：`GLOBAL` 不进可切换组表（它是 mode 的载体，不是订阅里的组），已在注释里写明这是取舍不是漏项。

### 1.3 YAML 行式判据两处纠偏（P1，会连带误判产品行为）

订阅正文是**行式**解析的（不能用 YAML 库重写，会丢注释/顺序，见 `KernelConfig` 的"宁可漏改也不能改坏"纪律），
所以缩进判据错一处就体现在产品数字或内核配置上：

- **条目计数**（`SubscriptionView`）：节点数/规则数/组名以前按"行首是 `- `"就数一条"，
  于是节点的**嵌套子列表**（`client-ips`、组的 `proxies:` 成员表）被数成节点，面板数字虚高。
  改为先取块的**条目列** `FirstItemColumn`，只有落在该列的破折号才算条目，更深的一律算子列表；
  向后找块尾的判据也补上"同级或更浅的破折行不算新的顶层键"。
- **`FindNextTopLevel`**：以前把**零缩进**的 `- name: …` 当成"下一个顶层键" ⇒
  零缩进列表（不少订阅生成器就这么吐）整段被当成空块，**节点数读成 0**。
  现与 `KernelConfig.EndOfBlock` 同口径（破折行不算键）。
- **`LockUrlTestTolerance`**（url-test 组锁 `tolerance: 999999`，防止内核测速把用户手选的节点抢回去）：
  块写法以前整组跳过。现在向上扫到本组破折行列定边界、**先向上**找已有 `tolerance` 再向下补写
  （顺序反了就可能出现两个同名键 —— `yaml.v3` 直接报 duplicate key，内核解析失败而隧道照装，
  就是 run 25 那次黑洞的形状），向下扫描时更深缩进的 `- ` 是成员列表要跳过，
  确定不了边界就**整组不动**（漏锁可以，改坏不行）。

### 1.4 系统侧订阅显示不正常（P1）

- **症状**：Windows 快速设置的 VPN 列表里，订阅条显示不对（旧名字 / 旧地址），
  删掉的订阅还留一条幽灵条目。
- **根因**：启动对账 `SyncSystemProfilesAsync` 只遍历**订阅**（每条 `subId` 一个 profile），
  **基础 profile（`ClashUWP`，不带 `subId`）从来不在这轮里** ——
  所以 1.0.72 修好的"已存在的 profile 必须走 `UpdateProfileFromObjectAsync`、不能走 `Add`"
  这条路径对基础 profile 从没跑过，`ServerUri` 还停在 127.0.0.1 时代下发的旧值上不自愈；
  订阅删除后残留的 profile 也没有任何一轮负责清掉。
- **修法**（都在 `ClashUWP/Vpn/VpnProfileSetup.cs`，接进对账的 ①②③ 三步）：
  - `EnsureBaseProfileResultAsync()`：缺就 `Add`；有就按**解析后的内容**比
    （显示名 + `RequireVpnClientAppUI` + `SubId` 为空 + `ServerUris` 一致），
    一致则 `Unchanged` 不动，不一致且 `ConnectionStatus == Disconnected` 才 `Update`，
    正在连接/断开一律 `Skipped` —— 与订阅 profile 同一条纪律：**绝不改活动会话的 profile**；
  - `PruneOrphanProfilesAsync(keepSubIds)`：只碰**同包家族**、`subId` 非空且不在当前订阅清单里的 profile；
    清单为空时**整轮跳过**（"拿不到订阅"绝不能变成"把面板清光"）；
    删除照旧过 `GracefulTeardown.EnsureTornDownAsync` 那道闸 —— 会话没收干净就拒绝删，
    否则就是 memory「Orphan NRPT machine blackout」那台整机断网；
  - 对账汇总行带上基础 profile 与 prune 结果，日志频道 `profile-base` / `profile-prune`，
    失败理由原话进日志（静默不算修完）。

### 1.5 空回环连接：空壳不拨号（P0）

- **症状**：能连上、图标是盾、状态 Connected，但哪儿都打不开；断掉重连有时就好了。
- **根因**：`LoadMihomoConfig` 在读不到订阅正文时**回落内置兜底配置** —— 那份兜底是
  `{"mode":"rule", …, "tun":{"enable":false}}`，**一个节点都没有**。
  旧代码带着它把隧道装起来：路由 0.0.0.0/0 进隧道，内核里却没有任何出站能承接，
  于是"连接成功"就是一次整机黑洞，只能等健康哨兵 30 s × 10 轮（5 min）兜住。
- **安卓口径**：CMFA `ClashService.kt` 是硬失败 ——
  `try { Clash.start() } catch (e) { reason = e.message } finally { stopSelf() }`：
  配置不可用就带着原因把服务停掉，**绝不"先接着，回头再说"**。
- **修法**：
  - 新增 `KernelConfig.ReasonIfNoOutbound(config)`：能出网就返回空串，否则返回一句可直接给用户看的理由。
    判据只看**有没有可用出站**：`proxies:` 段有至少一条同列破折条目（有条目就放行 ——
    这里问的不是"能不能数出节点名"，裸 `-` 把 `name:` 写在下一行的合法写法不能当空）；
    或者 `proxy-providers:` 段非空（节点由内核运行时自己拉，行数上看不见）；
    内置兜底那份 JSON 没有 `"proxies"` ⇒ 不可用。
    另外两条专门防**误杀**：行内写法（flow 列表 / YAML 锚点 / `!include`）写在键行冒号后面，
    数不清也一律放行；首行 BOM 先摘掉再匹配（匹配不到 `proxies` 在这里等于拒绝连接）。
    **判据自身抛异常 ⇒ 返回空串放行**：假阴性还有 `failFast` 那条内核启动失败兜着，
    假阳性直接变成"用户连不上网"。
  - 调用点在 `ClashVpnPlugin.Connect` 步 4.1 之后、**`KernelConfig.WriteEffectiveFile` 之前**
    （空配置一旦落盘，常驻热重载会把用户那份能用的正文覆盖掉），由 `LocalSettings.FailFast` 门控
    （`failFast=0` 保留"先建隧道再看诊断"的实验臂）；
    失败走 `AbortConnectionAttempt` = `SetErrorMessage(reason)` + `TerminateConnection(reason)`，
    系统 VPN 面板因此显示具体原因而不是光一条"连接失败"，同时落 `evt=connect-abort stage=no-outbound` 会话行
    与 `RollingLog.Warn("config", "空壳不拨号：…")`。
  - **热重载同口径**（`SubscriptionReload.RegenerateEffectiveFile`）：隧道正在跑的时候 PUT 一份零出站的配置
    等于把能用的旧配置换成黑洞，这里返回 `null` = **维持现状**（旧 `config.kernel.yaml` 不动、内核继续用已在跑的那份），
    并把 `config.yaml` 不存在与空壳两种成因一起写进前台提示，理由原话进 app.log 的 `config` 频道。

### 1.6 顺带修掉的既有 bug：连接列表显示 UUID

`KernelView.ReadChainLabel` 把 `/connections` 里的 `metadata` 当**字符串**读（它其实是**对象**），
所以 `GetStr(c,"metadata")` 恒为空 ⇒ 界面一直显示连接 id（UUID）而不是 `host:port`。
现按 `metadata.host` → `sniffHost` → `destinationIP` + `destinationPort`（字符串或数字都吃）取，
取不到才回落 id。

## 二、两则发布事故（本批最重要的发现）

### 2.1 组件 1.0.41 / 1.0.42 **从未打包**，装机的 1.0.72 里跑的是 1.0.40 的插件

证据（都是本次现读的，不是推断）：

- `artifacts/packages/` 里 `ClashUWP.Vpn.*.nupkg` 最高只有 **1.0.40**；
- 全局缓存 `~/.nuget/packages/clashuwp.vpn/` 同样最高 **1.0.40**；
- 主工程 `ClashUWP/obj/project.assets.json` 里留着还原失败原文：
  `找不到版本为 (>= 1.0.42) 的包 ClashUWP.Vpn / 在 clashuwp-local 中找到 40 个版本[最接近版本: 1.0.40]`。

⇒ 提交 319eab1（1.0.73：`NotifyStatus` + `ServerUri` 盾标修复）与 29d0609（1.0.74：`SetErrorMessage` +
`SystemHealth`）**只动了版本号，产物从来没变过**：1.0.72 那次成功构建吃的仍是 1.0.40 的组件。
这两次"修复"在上机的版本里一条都不存在，Docs/27 的结论也据此建立在未部署的代码上。

根因不是版本号写错，是**流程缺口**：bump `<Version>` + `<PackageReference>` 之后没有跑
`dotnet pack` 就直接当"已发布"。这正是 memory「Same-version reinstall 0x80073CFB」那族问题
（"改了源码但装的是旧二进制"）的另一个方向 —— 那次是版本没跳，这次是包根本没生成。
**已写进 §6 的收工判据**：bump 组件必须同时留下 `artifacts/packages/ClashUWP.Vpn.<新版本>.nupkg` 与
主工程 `deps.json` 里同版本的取证行，缺一律算没发布。

### 2.2 `VpnChannel.NotifyStatus` 是**不存在的 API**，已撤销并更正 Docs/27

- 1.0.73 写的 `channel.NotifyStatus(VpnManagementErrorStatus.Ok)` 之所以没暴露问题，
  正因为 §2.1 —— 它一次都没被编译过。本次打包时 `dotnet pack` 立刻报
  `CS1061: "VpnChannel"未包含"NotifyStatus"的定义`。
- 按官方元数据重验（不是查二手文章）：对 26100 的投影程序集
  `Microsoft.Windows.SDK.NET.Ref 10.0.26100.57 / Microsoft.Windows.SDK.NET.dll`
  用 `ilspycmd -t Windows.Networking.Vpn.VpnChannel` **全量导出**（460 行）：
  成员里没有任何 `Notify*`，接口只到 `IVpnChannel/2/4/5/6`；
  与 `VpnSystemHealth` 对照导出确认 `SystemHealth` / `StatementOfHealth`（`Windows.Storage.Streams.Buffer`）
  **确实存在**，所以 1.0.74 那两处调用保留。
- 结论：插件侧**没有**"向系统上报隧道状态"的原语 —— 这件事是平台在 `Start(...)` 成功、
  首个包被取走后自己推进的。Docs/27 的"根因 1：缺少 `NotifyStatus` 调用（已修复 ✅）"是错的，已更正；
  盾标那条线索只剩 **`ServerUri` 不再指向 127.0.0.1**（现默认 192.0.2.1，1.0.73 的另一半，本次也首次真正打进包里）。

★ 取证手法（写下来免得下次重踩）：本包 Native AOT，字面量是 **UTF-16**，
`grep -a "no-outbound"` 直接搜是 **0 命中**（Docs/21 那句"ASCII 命中标记"在短 ASCII 串上并不总成立）。
先把 NUL 去掉再搜：`tr -d '\000' < ClashUWP.dll > flat.txt && grep -a -o "no-outbound" flat.txt | wc -l`。
CJK 判据串别按字节拼 UTF-16 去搜，会错位；一律用 ASCII 标记判定。

## 八、装机过程新暴露的缺陷（六条，均未修）

> 取证口径：本节所有原文都抄自本机

### 8-A 连接失败时哨兵照样删 profile ⇒ 快速设置里的条目自己消失（P0，本批最严重）

- **实况**：03:19:37 第二次拨号（故意把 `config.yaml` 改名做"空壳不拨号"）→
  插件按设计 abort，平台侧只回一次，一切正常；**30 秒后**哨兵把承载面板条目的基础 profile 删了：
  ```
  03:19:38 profile-connect [ClashUWP] 发起前状态=Disconnected, 连接请求=ServerConnection, 实际状态=Disconnected
  03:20:08 health        隧道未建立（状态=Disconnected），跳过黑洞判定
  03:20:08 health-trigger 隧道未建立（状态=Disconnected）→ 探针只会量到直连网络，不做黑洞判定
  03:20:08 profile-disconnect 断开=NoConnection
  03:20:12 health-trigger 收尾动作：断开=NoConnection，why=前台请求（VpnProfileSetup.DropProfileAsync）
                         无需断开（状态=Disconnected） 删除=ok 复核=已消失 …
  03:20:39 health-trigger 收尾动作：找不到我们的 profile，why=前台请求（…） profile 不存在，无需收尾
  ```
  最后一行是第三次拨号：profile 已经没了，`状态=Profile缺失` —— **用户视角就是"VPN 条目自己消失了"**。
- **根因**（`ClashUWP/Backend/HealthMonitor.cs`，非本批引入）：`RunAsync` 的前置确认（L123–137）
  等 30 s 拿不到 `Connected` 时，只是把 `reason` 设成"隧道未建立…不做黑洞判定"，
  **然后照样往下走 L190–199 的收尾**（`DisconnectAsync` + `DropProfileAsync`）。
  而"断开后必须删 profile"这条设计的前提写在方法注释里：*哨兵收尾的会话都是「已经判死」的会话*
  —— 根本没建成的连接不属于"已判死的会话"，它没有 RasMan 重拨燃料要拆
  （本轮实测：abort 后平台一次都没重拨，§6 第 5 项）。
- **修法方向**：`!tunnelUp` 分支记完日志直接 `return`（不进收尾），收尾只留给"曾经 Connected"的会话。
  同一口径要检查硬上限那条（L183–184 `reason` 为空时补的"到达硬上限"），它也必须只在
  `tunnelUp` 为真时才可能触发。
- **附带**：`GracefulTeardown` 的残留自检在这一次报了 `teardown-selfcheck IP=OK 域名=超时 →
  疑似 DNS 残留（孤儿 NRPT）`，并给出 `Get-DnsClientNrptRule | Remove-DnsClientNrptRule -Force`
  —— 那是**全机器**的 NRPT（见 8-C），照抄会把别人产品的规则一起删掉，
  而收工实测 `Get-DnsClientNrptRule` 计数 0，说明这句提示在本机是假阳性。
  修法方向：自检只查**我们自己**的规则/路由（按 profile 名与家族哈希取），命令也只给可精确圈定的那条。

### 8-B 物理兜底哨兵的探针不绑物理接口：有第三方 VPN 时是 5 分钟定时炸弹（P0）

- **实况**：03:11:50 武装哨兵后，兜底探针**每 30 秒连续失败**，而那段时间整机网络其实是好的：
  ```
  03:11:50 physical-watchdog 启动：每 30s 探 114.114.114.114，10 次失败即拆隧道
  03:12:23 physical-watchdog 114.114.114.114 不可达 (超时)，累计失败 1/10
  …
  03:16:15 physical-watchdog 114.114.114.114 不可达 (超时)，累计失败 8/10
  03:16:29 session 用户发起断开（已解除健康哨兵）
  ```
  按 30 s 一拍，第 10 次落在 **03:17:21** —— 只差 52 秒就走到
  `连续 10 次物理网络不可达 → 整机网络已坏，自动拆隧道`，而那条分支的动作是
  `Cancel()` + `DisconnectAsync()` + **`DropProfileAsync()`**（L257–274）。
  也就是说：只要这台机器上有常驻第三方 VPN，这个哨兵**必然**在每次连接 5 分钟后
  把隧道拆掉并把 profile 删了，与 8-A 同一个破坏结果，且完全没人碰它。
- **根因**：`PhysicalNetworkWatchdogAsync` 的方法注释声称"探的是物理直连而非隧道，所以结果可信"
  —— **这句被实测证伪**。`TcpProbeAsync` 是一个普通 TCP 连接，不绑接口、不绑路由表，
  它走的是**操作系统默认路由**。本机默认路由 0.0.0.0/0 在 Clash Verge 的 `Meta` wintun 上
  （海外出口），而 `114.114.114.114:443` 只有走直连才应答（memory「Local network baseline」），
  于是失败是**必然**的，与"整机网络坏了"没有半点关系。
  我们自己下发的 `Ipv4ExclusionRoutes` 只让**节点 IP** 绕开隧道，管不了第三方 VPN 抢走的默认路由。
- **修法方向**（下一批定，本文只给结论性判断）：
  ① 这条"最后防线"的判据不能是"能不能连上某个公网 IP"，只能是**我们能确属自己的信号**
  （我们的隧道接口状态、我们写的排除路由是否还在），否则任何第三方 VPN 都把它变成定时炸弹；
  ② 无论判据怎么改，**删 profile 这个动作不能出现在"探针不可信"的分支里** ——
  拆隧道是可逆的，删 profile 会让入口消失，代价不对等；
  ③ 在那之前，本机测试纪律：**开工先看 `Meta`/`v Ethernet`/任何第三方 wintun 是否常驻**，
  常驻就不要武装长时间哨兵。

### 8-C 本机常驻 Clash Verge 抢默认路由 ⇒ 本轮所有"可达性"判据被污染

- 现象：`verge-mihomo` 进程 + `Meta` wintun（`0.0.0.0/0` + 9 条路由）全程在场。
  我们断开之后 `Get-NetAdapter` 里仍看得见 `Meta` —— **那不是我们的接口**（§6 第 8 项的 ⚠️）。
- 影响面（三条判据因此不能算我们头上）：
  1. 主页状态标签那句 `PUT /proxies/… -> 204` 证明的是"切换成功且内核应答"，
     **不能**拿来证明"我们的隧道在服务探测"（204 走的是 Verge 的出口）；
  2. 8-B 的兜底探针必失败；
  3. 8-A 附带的残留自检假阳性。
- 另记一条与第三方无关但同样影响实测的：包内内核 REST（`127.0.0.1:9090`）**未打包进程读不到**
  （`Invoke-RestMethod` 直接超时，这是包应用 loopback 隔离，不是 bug）。
  ⇒ 任何"从外面看一眼内核"的取证都得走界面或 `debug-cmd`，别浪费时间写 curl。
- 修法方向：无代码可修。作为验收纪律写进本文与 §6：**判据先问"这个数是谁给的"**；
  需要干净测量时，必须先让用户确认可以暂时停掉 Verge（停第三方 VPN 是**动用户环境**，不自己按）。

### 8-D 「拉取并启用」不写 `config.yaml` ⇒ 紧接着的自动热重载必然空手而归（P1）

- **根因**（`ClashUWP/Backend/SubscriptionManager.cs`）：`FetchAsync(url, activate: true)`
  做了 `WriteAllTextAsync(PathFor(id), text)`（写 `subscriptions/<id>.yaml`）、`SetUrlAsync`、
  `SetNameAsync`、注册系统 profile、`SetActiveAsync(id)`、`ReloadActiveConfigAsync()`，
  **唯独没把正文复制到内核实际读的 `config.yaml`** —— 那一步只在 `ActivateAsync` 里
  （`await WriteAllTextAsync(ActiveName, text)`）。而 `ReloadActiveConfigAsync` →
  `SubscriptionReload.RegenerateEffectiveFile()` 第一句就是"读 `config.yaml`，不存在返回 null"。
  于是"拉取并启用"这一路自己把热重载喂了个空，结果串末尾带的是那句
  `没有可重载的生效配置：config.yaml 不存在…`，用户看到的是"拉下来了但要再点一次才生效"。
- **实测印证**（文件时间戳，与代码互相咬合）：
  ```
  03:07:58.904  subscriptions\iz9ld…Z1Ef.yaml   （fetch 落盘）
  03:07:59.308  app.log  profile-sub 订阅profile[ClashUWP · iKuuu_V2] … 新建=Ok
  （此后 89 s 内 LocalState 根目录没有 config.yaml，日志里也没有任何 config 频道行）
  03:09:27.256  config.yaml                     （点「切到/启用」才写出来）
  03:09:27.345  app.log  config 热重载配置已重生成 应用分流=无名单，rules 未动；DNS 覆盖=无覆盖 …
  ```
  即：只有走了 `ActivateAsync` 的那条路，`config.yaml` 才存在、热重载才有东西可重载。
- **修法方向**：`FetchAsync` 的 `activate` 分支在 `SetActiveAsync(id)` 之前补一次
  `WriteAllTextAsync(ActiveName, text)`（与 `ActivateAsync` 同一份文本、同一口径），
  或直接把 `activate:true` 的实现改成"落盘后调用 `ActivateAsync(id)`"，避免两份复制逻辑分叉。
  属于一行级修复，但必须与 §1.4/§1.6 的"订阅正文是单一来源"注释一起改，别只补写文件不写理由。

### 8-E 常驻 ↑↓ 状态通知从未常驻：系统按 `TimedOut` 撤下，被我们当成"用户划掉"（P1）

Docs/18 §7 挂着的那条"整机零验证"项，本轮有答案了 —— **答案是不成立**：
```
03:11:56 toast 启动：每 1000ms 原位刷新 tag=clash-status setting=Enabled 补发上限=3 引导通知=每天一次
03:11:58 toast 状态通知已消失（第 1 次，dismissed:TimedOut）
03:11:58 toast 已发引导通知（普通横幅 +「打开通知设置」按钮）
03:11:59 toast 状态通知已消失（第 2 次，dismissed:TimedOut）
03:12:00 toast 状态通知已消失（第 3 次，dismissed:TimedOut）
03:12:01 toast 状态通知已消失（第 4 次，dismissed:TimedOut）
03:12:01 toast 本会话不再刷状态通知（原因见上一行 toast 日志）
03:16:29 toast 撤下失败（平台回调 Disconnect）err=COMException: 通知无法隐藏，除非它已经显示。
```
- **读法**：从"启动"到"放弃"总共 **5 秒**，用户一次都没碰它。`ToastDismissedReason.TimedOut`
  是 toast 的**正常寿命**（横幅显示完自动收起），不是"用户划掉"；
  而 `StatusToast` 把它计进 `MaxReRaise=3` 的补发额度，于是每个会话都在 5 秒内把额度烧光、
  还顺手发一条**会出横幅的引导通知**（本来设计给"用户反复划掉"时用，现在人人都收到）。
  收尾那句 `通知无法隐藏，除非它已经显示` 是同一条错误的下游：循环早已放弃，`Stop()` 去 `Hide` 一条不存在的通知。
- **修法方向**：`TimedOut` 不计补发额度（只有 `UserCanceled` 才算划掉；`ApplicationHidden` 另计），
  引导通知只在真的 `UserCanceled` 之后发；同时核对三处 `new ToastNotification(doc)`
  全都没设 `ExpirationTime`（走系统默认寿命）—— **想常驻就得显式设它**，
  但设成多久、上限是多少要先读官方文档再定，不许凭记忆拍（memory「Verify official first」）。

### 8-F 换签名证书＝换包家族哈希 ⇒ 按 `FamilyName` 匹配的六处逻辑集体失效（P1，运维性）

- §5 的重签路子让安装包从旧家族变成 `8B8CC4F4.ClashUWP_4tjvwvefxrz66`。
  包家族后缀是**由签名证书算出来的**，所以"同 CN 换一张证书"在清单身份上合法、
  在数据面上是**另一个产品**：`LocalState`（订阅正文、`settings.txt`、日志）全是新的，
  旧家族目录留在原地但新包读不到。
- 更要紧的是代码里按 `PackageFamilyName` 找我们的 VPN profile，共六处
  （`ClashUWP/Vpn/VpnProfileSetup.cs` L64、L531、L586、L642、L693，写入侧 L130、L363、L769）：
  一旦家族变化，**老 profile 的 `VpnPluginPackageFamilyName` 不再等于当前包家族** ⇒
  启动对账看不见它们（本轮日志 `启动对账：订阅 0 份 + 基础 profile 1 条，新增 1` 里
  `profile 数=0` 就是这个形状），prune 也清不掉它们 ⇒ 面板里挂着上一代产品的幽灵条目、
  当前代又新建一份同名的，用户看到两条都以为能连。
- **修法方向**（两件事，都做）：
  ① 运维上**固定签名证书**：本轮用的 `FB3309A6…` 要进构建脚本/文档成为唯一签名身份，
     换证书要当成"发布新家族"来对待（连带数据迁移），不许顺手换；
  ② 代码上把"是不是我们的 profile"的判据从单一 `FamilyName` 改成
     **`FamilyName` 或名字前缀（`ClashUWP · ` / 基础 `[ClashUWP]`）任一命中**，
     并把命中的旧家族条目纳入 prune（迁移式清理），这样换证书不至于在面板里留下永久疤。
