# 11 · 滚动日志 —— 发布版也有的统一取证通道

对应版本：app `1.0.36.0` / 组件 `ClashUWP.Vpn 1.0.24`。
本轮只做一件事：把"日志"从**只有 Debug 版才有**改成**任何版本都有**，并且给两个进程各一条不会互相踩的通道。

---

## 1. 为什么原来的三条通道都不算"发布版也有"

| 原通道 | 为什么不能用 |
| --- | --- |
| `Debug.WriteLine` | 带 `[Conditional("DEBUG")]` ⇒ Release/AOT 里**根本不会被编译进二进制**。本轮之前的真实状态就是"发布版零日志"。 |
| `VpnChannel.LogDiagnosticMessage` | 【官方】"Writes a diagnostic message to the system log" —— 要 RAS tracer / ETL 才看得见，实测还常被平台日志清空/丢失（09 号文档记过）。而且它只在插件侧存在。 |
| `LocalState\*.txt` 诊断文件 | 全是**覆盖式快照**，只有"最后一次"。答不了"第 3 分钟发生了什么"。`dataface-sessions.txt` 是追加式，但①不封顶，②旧实现每行新开一个 `Task.Run` ⇒ 并发追加、连行序都不保证。 |

结论：要自己写一个。约束来自这个项目已经付过学费的地方 —— 日志**绝不能**成为数据面的新风险源。

---

## 2. 设计口径（`ClashUWP.Vpn\RollingLog.cs`，~350 行，单文件）

### 2.1 为什么放在组件工程而不是 app

日志要同时覆盖前台 app 进程与 `vpnClient` 后台任务进程，而**依赖方向只有一条**：app → 组件（组件不引用 app，见 Docs/10 §1 的同款理由）。把类放组件里、靠 `AssemblyInfo.cs` 的 `InternalsVisibleTo("ClashUWP")` 给前台用，是两个进程共用同一份实现的唯一低成本做法。代价也写明：`internal` 意味着外部工具不能直接调它，取证只能走 `logtail` 或读文件。

### 2.2 四条硬规则

1. **调用方永不阻塞、永不抛。** 只做一次 `BlockingCollection.TryAdd(..., 0)`；队列满就丢并 `Interlocked.Increment` 计数，工作线程随后补一行 `[dropped=N]` —— 让"少了几行"本身可见，而不是安静地骗人。
2. **数据面热路径一律不调。** `Encapsulate` / 回程注入泵 / keep-alive / `GetKeepAlivePayload` 那些地方要的是**计数器**（已经在 `dataface-plugin.txt` 快照里），日志只记生命周期与异常。这条是 7188 包停摆那轮（项目记忆「Send buffer pool 7188」）的直接教训：任何往平台回调里塞磁盘 I/O 的想法都先假定它会杀死会话。
3. **单工作线程落盘**，`ThreadPriority.BelowNormal`，每批最多 64 行、最长 200 ms 强制刷一次；写用 `FileStream` + `fs.Flush(true)`（到磁盘，不是只到 OS 缓存）⇒ 进程被平台直接杀掉时的损失窗口 ≤ 200 ms，而已写下的行保得住。
4. **按大小滚动**：`512 KB × 3`（当前 + `.1` + `.2`），到点 `X → X.1 → X.2`，最老覆盖。每个汇占用恒定 ≈ 1.5 MB。滚动/写盘失败只吞掉这一批，绝不反压调用方。

### 2.3 两个汇（sink），分流靠显式标记不靠猜

| 汇 | 文件 | 行格式 | 谁读 |
| --- | --- | --- | --- |
| 自由文本 | `LocalState\logs\app.log`<br>`LocalState\logs\plugin.log` | `yyyy-MM-dd HH:mm:ss.fff pid=N role I\|W\|E tag message` | 人 |
| 会话事件 | `LocalState\dataface-sessions.txt` | `yyyy-MM-dd HH:mm:ss pid=N connectCalls=N evt=…` | **机器** |

★ `dataface-sessions.txt` 的行格式是**硬契约**：插件 `SessionWatchdog` 与前台 `HealthMonitor` 都用 `DateTime.TryParseExact(line.Substring(0, 19), "yyyy-MM-dd HH:mm:ss")` + `Contains("evt=connect-begin")` 数重拨次数，那是"平台自动重拨就立刻拆掉"的保险丝。加毫秒 ⇒ 前 19 个字符变了 ⇒ 解析失败 ⇒ 保险丝**静默失灵**。所以这个汇单独一条写入口 `Sessions(uint connectCalls, string evt)`，无毫秒、逐字符照旧（旧实现见 `ClashVpnPlugin.LogSession` 的注释），并且入队时用 `Item.ToSessions` 显式标记 —— 不做任何"看行长像什么"的猜测。

### 2.4 落盘方式与它的代价

用 `System.IO` 直接写 `ApplicationData.Current.LocalFolder.Path`：打包应用读写**自己的**应用数据不需要额外能力，AOT 下也不依赖反射（对比 WinRT `FileIO` 每行一次异步往返）。代价说明白：路径在包目录内 ⇒ **卸载 / `Remove-AppxPackage` 会连带删掉日志**，与 LocalState 里那些诊断文件同命运。要留证据就先复制出来。非打包上下文（工具/单测）拿不到 `LocalFolder` 时退回 `Path.GetTempPath()`，不抛。

## 3. 调用点位清单（谁在什么时候写一行）

原则：**生命周期 + 异常 + 安全闸生效**。正常包量、逐轮探针这些仍然只进计数器和原有流水账文件，日志不重复记账。

### 3.1 前台 app 进程 → `logs/app.log`

| tag | 位置 | 内容 |
| --- | --- | --- |
| `app` | `App.Main` | 进程启动 + 包版本 + pid（**所有其它工作之前**） |
| `diag` | `Diagnostics.StartOnce` | 取证通道装配完成（同时是"界面首渲染成功"的证据） |
| `probe` | `StartupProbe` | 启动探针完成 / 失败 |
| `dump` | `ProfileDump` | profile 清点结果条数 / 失败 |
| `appsettings` | `AppSettings.LoadAsync` | ★ 1.0.37 起：门控读到的 `settings.txt` 生效值（`src=… autoProbe=0/1`）。"这次为什么没自动拨 VPN"第一眼就看它 |
| `probe-selftest` `probe-dataface` | `StartupProbes` | 两个探测主体抛异常时 |
| `probe-teardown` | `StartupProbes` | ★ 收尾闸**没过** ⇒ 拒绝删 probe（Warn）。这是"可能留孤儿 NRPT"的现场 |
| `session` | `VpnSession` | 用户发起连接 / 断开（连=已武装哨兵，断=已解除） |
| `health-arm` `health` `health-trigger` | `HealthMonitor` | 武装、隧道建没建起来（决定后面探针读的是隧道还是直连）、判死动手的原因与收尾动作 |
| `health-sessions-read` | `HealthMonitor` | ★ 保险丝的眼睛瞎了（读 sessions 失败）也要留痕 |
| `profile` `profile-recreate` `profile-connect` `profile-disconnect` | `VpnProfileSetup` | 一次动作一整句结果原文 |
| `profile-delete-refused` | `VpnProfileSetup` | ★ 拒绝删除（防整机断网的闸生效） |
| `cmd` `cmd-unknown` `cmd-loop` | `DebugCommandLoop` | 命令原文（谁在什么时候下发了什么）/ 未知命令 / 回路异常 |
| `mihomo-*` | `MihomoController` | 六条控制器命令各自的失败 |
| `localstate-write` | `LocalState` | 诊断文件写不进去 |
| `teardown-selfcheck` | `GracefulTeardown` | 残留自检结论（见下） |

### 3.2 插件进程 → `logs/plugin.log`

| tag | 位置 | 内容 |
| --- | --- | --- |
| `bgtask` | `VpnBackgroundTask.Run` | 插件进程启动（版本 + pid）、Run 返回 |
| `connect` | `ClashVpnPlugin.Connect` | 平台第 N 次发起连接、是否复用常驻内核 |
| `connect-abort` | 同上 | `AssociateTransport` 失败 ⇒ 本次连接已终止 |
| `session` | 同上 | L3 隧道接口建立（includeMode / include / outer / mtu）；会话结束（存活秒数 + encap/inj/keepAlives） |
| `start-failed` | 同上 | ★ 阶段分开报：`StartWithTrafficFilter` 本身失败 vs 桥 FailFast / 看门狗（Docs/09 C4） |
| `disconnect-inner` | 同上 | ★ 收尾主体抛异常 ⇒ 通道可能没收干净 |
| `keepalive` `self-split-filter` | 同上 | 原先仅有的两处 `Debug.WriteLine` 的替身 |
| `snapshot` | `WriteDatafaceSnapshot` | 快照写失败 ⇒ 前台读到的可能是**旧**快照 |
| `watchdog` `watchdog-trip` `watchdog-teardown` | `SessionWatchdog` | 按设置关闭 / 判黑洞动手的原因 / 收尾结果 |
| `settings` | `LocalSettings.Load` | 每次装载后把**生效开关**整行打出来，末尾附 `Diag()` |
| `kernel-home` | `KernelHome.Ensure` | ★ 1.0.37（G10）：内核 home 落在哪 —— `home=LocalState（已复制 Country.mmdb） size=…` 或 `home=包目录 退回原因=…`。选节点持久化/provider/热重载这三样的成败全由这一行决定，所以必须能当场查到 |
| `hot-reload` | `ClashVpnPlugin.TryHotReload` | ★ 1.0.37：`PUT /configs?force=true` 的状态码；非 2xx **连响应原文一起记**（400 的原文就写着 path 不是绝对路径 / 不在 safePaths / 解析失败） |
| `teardown-selfcheck` | `GracefulTeardown` | IP/域名交叉自检：`直连完好` = Info，其余一律 **Error** |

★ `GracefulTeardown` 的自检"跑在哪个进程就写哪个文件"，因为收尾本来就是两边都会发起的动作 —— 这正是共用一个日志类的收益。

### 3.3 顺带补进快照的两处

- `dataface-plugin.txt` 新增一行 `Log=<Diag()>`：丢行数、当前队列、日志文件与容量。没有它，"plugin.log 里查不到某件事"分不清是**没发生**还是**被丢了**。

## 4. 怎么读

方式一（推荐，只读、不碰隧道）：写 `LocalState\debug-cmd.txt` 一行

```
logtail                 # app.log 尾部 40 行
logtail plugin 120      # plugin.log 尾部 120 行
logtail sessions 200    # 会话事件流尾部
```

结果进 `debug-out.txt`，末尾附 `Diag()`。`logtail` 读之前会先 `Flush(150)` 把**本进程**队列排空一点（攒批落盘嘛），但它叫不动插件进程的队列 —— 读 plugin 汇时那 200 ms 批窗口只能等。

方式二：直接看文件。路径 `%LOCALAPPDATA%\Packages\<包名>\LocalState\logs\`，注意包名是 GUID（见 Docs/07 §包名）。滚动出来的历史是 `app.log.1` / `app.log.2`。

## 5. 版本与构建链路

| 项 | 值 |
| --- | --- |
| 组件 | `ClashUWP.Vpn 1.0.23 → 1.0.24`（`dotnet pack` 进 `artifacts\packages`） |
| 前台引用 | `PackageReference` 同步 `1.0.24` |
| 包清单 | `Package.appxmanifest Version="1.0.35.0" → "1.0.36.0"` |

★ `1.0.23` 是打包过程中的中间态：它被 pack 出来之后组件又改了三处（`Error(tag, message)` 重载、`PackageVersion()`、后台任务版本行）。按 csproj 里那条"同版本号会命中 NuGet 全局缓存的旧 nupkg"的规则，`1.0.23.nupkg` 与 `%USERPROFILE%\.nuget\packages\clashuwp.vpn\1.0.23` **已删除**，不留可被误引用的版本。

构建实测：组件 `dotnet build -c Release` **0 警告 0 错误**；前台 **Release 与 Debug 各一次，同 0 警告 0 错误**；`msbuild -t:Publish`（AOT 原生代码生成）通过 ⇒ 证明 `RollingLog` 用到的 `BlockingCollection` / `FileStream` / `StringBuilder` 在 PublishAot 下无裁剪问题。

★ **"发布版真的有日志"这条到底怎么验的** —— 不靠推理，直接查 AOT 产物本身。
`ClashUWP/bin/Release/.../win-x64/publish/ClashUWP.dll`（17 MB 原生主模块，组件代码静态并进来，
publish 目录里**没有**单独的 `ClashUWP.Vpn.dll`）里按 UTF-16 检索得到：

| 常量 | 来源 | 命中 |
| --- | --- | --- |
| `profile-recreate` | 前台 `VpnProfileSetup` | 1 |
| `watchdog-trip` | 插件 `SessionWatchdog` | 2 |
| `app.log` | `RollingLog.LogPathFor` | 1 |
| `log-dropped` | `RollingLog.WorkerLoop` 丢行补记 | 2 |
| `evt=run-enter` | 插件 `VpnBackgroundTask` 的 sessions 行 | 1 |

> 注：字面量在 .NET 原生产物里是 **UTF-16**，`grep -a "profile-recreate"` 直接搜是搜不到的
> （我第一次就搜了个"未命中"，差点得出反结论）。要搜得用 `grep -a -P 'p\x00r\x00o\x00f\x00...'`。
> 另外 bash 的命令替换会吞掉 `\x00`，所以转义串必须**手写进命令行**，不能用 `sed` 生成。

**装包与实测留给 Visual Studio**（AGENTS.md 第 2 条），本轮没有部署、没有碰隧道。

## 6. 明确没做的事

1. **没做级别过滤**（比如只写 Warn 以上）。日志量本来就是"生命周期 + 异常"，过滤只会让"少了几行"更难解释；真要降噪应该删调用点，不是加开关。
2. **没接 `LogDiagnosticMessage`**。它仍是插件面向平台的出口，保留原样；滚动日志是**并行**的第二条通道，不是替代。
3. **没做跨进程行序保证**。两个进程各写各的文件，时间戳是墙上时间，合并读靠时间戳排序 —— 够用，且避免了跨进程同步带来的阻塞风险。
4. **真机输出还没看过**。本轮把"发布版**二进制里有没有**日志代码"证到了（§5 那张 UTF-16 命中表），
   但"跑起来**写不写得出文件**"是另一件事 —— 部署后至少要确认四项：
   `logs\app.log` 有 `app 启动 version=...` 行、点一次「建/重建 profile」后出现 `profile-recreate`、
   连一次之后 `plugin.log` 出现 `connect` / `session`、`dataface-plugin.txt` 的 `Log=` 行 `dropped=0`
   且 `dataface-sessions.txt` 仍能被告警保险丝正常解析（`logtail sessions` 一眼能核对格式）。
5. **热路径没加任何日志**，这是刻意的，别以后当遗漏补上。
