## 一、G1 —— 健康会话不再被 30 分钟计时器拆掉

### 1.1 这条是什么

`HealthMonitor` 的会话保险丝原来有一条 **无条件兜底**：`hardCapOwnedSeconds = 1800`，
"先武装再连接"那条路到点必断，且判据写死为 `while (tunnelUp && DateTime.Now < deadline)`。
用户视角的症状就是**每半小时自己掉线一次**，隧道当时是不是健康与这条无关。

### 1.2 改了什么

| 位置 | 旧 | 新 |
| --- | --- | --- |
| `HealthMonitor.RunCoreAsync` 循环条件 | `tunnelUp && DateTime.Now < deadline` | `tunnelUp` |
| 到点收尾 | `reason = "到达硬上限 …s（无条件兜底）→ 断开"` | `if (reason.Length == 0) return;`（正常退出，不动手） |
| `AdoptArm` 注释①「认领模式无硬上限」 | 用"有无上限"区分两条路 | 删掉该条（两条路都没有上限了），只留基线计数 `connects - 0` 这一条真差别 |
| 三处滚动日志文案 | 「上限 1800s」 | 「无固定时长上限」 |

判据本身没有消失，只是**不再由计时器代答**。动手条件收敛进新文件
[`SessionWatchdogPolicy.cs`](../ClashUWP/Vpn/SessionWatchdogPolicy.cs)（前台与插件共用一份）：

1. `unmanagedRedials > 1` —— 非本次发起的 connect 超过一次 ⇒ 平台在自动重拨（828 那条死循环）；
2. `tunnelProbeFailures >= 2` —— 连续两轮隧道内探针不可达 ⇒ 黑洞；
3. `fakeIpProbeFailures >= 2 && aliveSeconds > 30` —— 系统解析连续两轮不再返回 fake-ip ⇒ DNS 侧已断。

★ 第 3 条里的 `aliveSeconds` 是**下限**（刚连上 30 秒内不据此判死），不是上限。
这是本批唯一还留在判据里的时间量，方向和旧的那条正好相反。

### 1.3 移除上限后补上的出口

固定上限原先兼职了"会话早就没了但哨兵还在探"这件事的收口。上限一走，那个洞就露出来：
会话被快速设置断开后，哨兵会在**直连网络**上继续探针并计失败，攒够两轮就把
承载快速面板条目的基础 profile 删掉（Docs/30 §8-A 记过的同款代价）。
出口是 `goneRounds` —— **连续两轮**读到会话消失才退出，且只退出、不收尾、不删 profile
（给 RasMan 正常重拨的中间态让路，也避开 Docs/45 的读数中毒）。

## 二、G2 —— 节点选择台账改成"按漂移回放"

### 2.1 旧实现的两个缺陷（都在装机读回来的那一层）

`selection.txt` 的回放原先由一只 **bool 闩**触发，判的是"内核可达边沿"：

- ① **闩在读台账之前就置位**。于是「内核起来（此时台账还是空的）→ 用户在这次会话里点选」
  这个顺序中，后写入的每一条**再也没有回放周期** —— 台账记了，内核没吃到，界面上选中的是预设值。
- ② **复位只挂在轮询的 `catch` 上**。而内核不可达时 `KernelView.LoadAsync` 是
  **返回 `Ok=false` 而不抛**（1.0.118 起还额外带回退的配置视图），`catch` 那条路压根不走
  ⇒ 闩一旦置上就永远不会再回放。

两条合起来的形状就是"这次选好了，下次开又回到默认节点"。

### 2.2 新判据

[`SelectionReplayPolicy.cs`](../ClashUWP/Backend/SelectionReplayPolicy.cs) —— 纯函数，输入台账记录 +
内核当前组表，输出这条记录的处置：`Put` / `AlreadySelected` / `SkipGroupMissing` /
`SkipNotManual` / `SkipNodeMissing`。

触发不再依赖"有没有观察到掉线边沿"，而是**内核现值与台账有漂移**：
内核重启后手动组的 `now` 自己会退回配置默认值（home 只读，内核 `cache.db` 跨重启不保留），
漂移一出现就把该放的放回去。这个形状同时覆盖了①和② —— 它不需要知道"刚才断过"。

口径同源：**手动组 = `Selector` / `select` / `Relay` / `relay`** 用的仍是
`KernelView.IsUserSelectableType` 那一份（1.0.84 抽出来的那个函数），实时切换那一路
（`MihomoController.SelectCoreAsync`）也是同一份。三处不再各写各的。

## 三、G6·P3 —— 换网后桥真的重绑

Docs/32 §四 P3（Docs/33 §六.4 明记着"本轮仍未修"）那条缺口：
`residentBridge=1` 的复用路径不重跑 `clash_bridge_start`，Go 侧 `rebindInterface()`
（`Tools/mihomo-bridge/bridge/core.go:66-104`）沿用上一次探测的结果；桥回话
`bound_iface=Meta` —— 那是别的程序留下的 wintun 设备，此刻已经 `Disconnected`，真正的出口是 WLAN。
而 `net-follow` 报「指纹=未变」，连"可疑"都没说出来。

**为什么旧指纹看不见这件事**：它比的是 WinRT 的 `GetConnectionProfiles()` 枚举 ——
那是 **profile**，不是链路状态。26100 的 winmd 里 `NetworkAdapter` 只有
`IanaInterfaceType` / `NetworkAdapterId` / `NetworkItem` / 收发速率五个成员，
**没有名字也没有连接状态**（ilspycmd 反编译实录，Docs/21 §四 同一条）。

**现在拿什么判**：改用 `System.Net.NetworkInformation.NetworkInterface` 那张系统适配器表。
采集在 `NetworkFollow`，判据单独成 [`AdapterHealth.cs`](../ClashUWP/Vpn/AdapterHealth.cs)（纯函数）。
`Name` 与 Go 侧 `ifc.Name` 同源（都取 Windows 的接口友好名，`Meta` / `WLAN` 两边写法一致），
`OperationalStatus` 与 `NetworkInterfaceType` 给"这张卡还在不在、还是不是物理卡"。

★ 判据刻意分成两半 —— **只在有正证据时动手**：

| 观测 | 结论 | 动手 |
| --- | --- | --- |
| 名字找得到，但状态不是 Up / 没有 IPv4 / 桥根本没绑 | 坏 | 重跑一次探测（严格优于留着死绑定） |
| 名字在表里**找不到** | 不确定（可能只是命名口径不一致） | **只报不猜** |
| 绑到隧道/第三方 VPN 设备（`Tunnelish`） | 已知是别人家的设备 | **只报不动手** —— 重跑探测会挑出同一个名字（Go 的 `isVirtualNIC` 名单里没有 wintun/tap，`core.go:49-61` 逐字读过） |

把"我们的观测缺口"当成"网络变了"去驱动一次 `clash_bridge_start`，是本项目有前科的病态路径
（Docs/05 §2④），不能拿数据面赌。

现场出口：`dataface-plugin.txt` 的 `NetFollow=` 那一行现在带 `sys=` 段
（`AdapterHealth.Format`），绑定生效过没有、绑在哪、那张卡现在什么状态，当场可读。

## 四、G7 —— IPv6 不绕过 VPN

细则与判据都在 **Docs/22 §9**（本节只登记结论与去向，避免两处各说各话）：

- 路由表四桶的分配判据从 `BuildRoutes` 抽进 [`RouteInclusion.cs`](../ClashUWP/Vpn/RouteInclusion.cs)（纯函数）；
- **档 1/2 的 v6 节点服务器宿主路由从前 `/32` 纠正为 `/128`** —— 旧形状下拨向 v6 节点的
  外层包会落进自家 `2000::/3`，是一个自环黑洞陷阱；
- profile 里的 v6 段不再被塞进 v4 桶（按族分桶 + 每一笔剔除都点名）；
- `::/0` 这条禁令从"文档里写着"变成**代码里拒绝 + 离线断言钉住**
  （先遣 docs/96 §6.2.1：四条臂里 `::/0` 4/4 把 VPN 变成 IPv4 默认路由，`2000::/3` 0/2）；
- 档 0（默认档）的泄漏面**如实报三种读数**：本机有全局 v6 / 本机没有 / 读不到 ——
  第三条不许被读成第二条（"读不到 ≠ 安全"）。
  现场证据是 `dataface-plugin.txt` 新增的 `Ipv6=` 与 `Routes=` 两行。

★ **默认档没有上调，仍是 `ipv6=0`。** 理由写在 Docs/22 §9.6：档 1/2 动的是隧道本体，
而这台机器**没有全局 IPv6**，装机测不出增益也测不出回归。
要不要上调是用户的决定，本批只把"不上调正在漏什么"变成看得见的三句话。

## 五、G4 / G5 —— 活动连接能强断、内核日志有界面入口

这一项名义上是"加两个功能"，实际是把两条**已经存在但够不着**的通道打通到界面。

### 5.1 G4 · 强断单条连接（UI 侧此前无入口）

**根因不是缺按钮，是缺数据**：`KernelView.Conn` 这个记录里**没有 `Id`** ——
内核 `GET /connections` 的原文里有 `id`，旧解析在折成 UI 模型时把它丢了。
所以"活动连接"这一块以前只能看，`DELETE /connections/{id}` 只挂在 debug-cmd 上。

改了三处，一处加一处：

1. `Conn` 增加 `Id` 与 `Network`（`tcp`/`udp`）。协议要显示出来，因为**断一条 UDP
   会被应用立刻重发**，不显示协议就没法解释"断开了又冒出来一条"。
2. `ReadChainLabel` 的兜底从 `GetStr(c,"id")` 改成明写 `(目标未知)`。
   1.0.75 修的是"metadata 被当字符串读 ⇒ 整列显示 UUID"，但 metadata **真缺**的那几条
   仍然被 UUID 顶上去。`id` 现在有自己那一列，不该再冒充目标。
3. `ReadNum` 除了 Number 也认**字符串数字**（老 Clash 的 `downloadTraffic` 那一族，
   也是 `MihomoController.ReadNumber` 早就在防的形态）。旧实现只认 Number ⇒
   界面永远显示 `↑0 ↓0`，而"读不出来"和"读出来是 0"在界面上**长得一模一样**。
   上下行同时从裸字节改成 `FormatBytes`（`1048576` 要人算才知道"这条还在长"，
   而"还在长"正是"该不该断它"的判据）。
4. 界面（主页 · 活动连接）每行一个「断开」，顶部「全部断开」+「刷新」+ 条数；
   只显示前 30 条，但**条数不说谎**（`…（另有 N 条未列出）`，不是省略号糊过去）。

★ **`204` 只证明请求被接住，不证明那条真没了。**
官方 `DELETE /connections/{id}` 对不存在的 id **也是 204**（不区分）。
所以 `CloseConnectionAsync` 受理后立刻再读一次列表，把"现剩 N 条"一起回出去；
读不回来就写「复核剩余条数失败=…（不影响上面的受理结果）」，不拿 204 冒充"断开成功"。

★ **URL 必须转义**：`id` 现在有三个来源（内核回话 / 命令文件原文 / 界面缓存的旧列表），
旧写法 `$".../connections/{id}"` 直接把字符串拼进路径 —— 带 `/`、`?`、`#` 的值会把
DELETE 打到**别的路径**上。新增 `ConnectionDeleteUri` 走 `Uri.EscapeDataString`。
debug-cmd 的 `connections kill` / `kill-all` 改成**委托同一对方法**，界面与命令行不再两套实现。

### 5.2 G5 · 内核实时日志进界面（且不改掉用户的等级）

`GET /logs` 以前只有 debug-cmd 一个入口。拨号失败的原文（`dial … error` / `bind4: …`）
是本项目反复出静默失效的那一层（Docs/08 的 run 14、Docs/12 §6），而看它要先会开命令行、
还要知道去读 `LocalState`。

设置页新增「内核实时日志」：点一次挂 12 秒流，原文直接画出来，
上面一行标出**当前内核日志等级**和"若不是 debug 会临时抬、结束后恢复这一档"。

★ 等级这条是真缺陷，不是打磨：旧实现**无条件** PATCH 到 debug，再**无条件**恢复成硬编码的
`info` —— 用户把内核设成 `warning`，看一次日志就永久变成 `info`，界面上没有任何痕迹。
现在判据抽成 `LogStreamLevelPlan(currentLevel)`（纯函数）：

| 内核当前等级 | 抬到 debug | 恢复成 |
| --- | --- | --- |
| `debug` | 不抬 | `debug`（等于不动） |
| `silent` / `error` / `warning` / `info` | 抬 | **回它自己** |
| 认识之外 / 空 / 脏值 | 抬 | `info`，★ 绝不把原样字符串拼进 JSON 体 |

第三行是白名单存在的理由：这个值会被插进 `PATCH /configs` 的 JSON 体，
一个 `"` 就能改掉别的字段。`IsKnownLogLevel` 只收内核 `config/config.go` 那五个值。

★ **调用方不传等级时不再默认"不知道"**：`RunLogStreamAsync` 自己先 `GET /configs` 读一次
（`GetLogLevelAsync`，读不到给空串而不是猜 `info`）。
debug-cmd 那条路本来就没有快照可传，这条改动让它也享受等级保持 ——
否则这次修复只治了界面新按钮，而**新按钮出现之前唯一在跑的入口**恰恰是 debug-cmd。

★ 内核不可达时按钮**当场拒绝并说明**，不发起 VPN 连接：
「内核未运行：抓不了实时日志（这条路只读内核 REST，不会为此发起 VPN 连接）」。
口径同 1.0.118 的测速按钮 —— 隧道不是 `/logs` 的前提，把两者绑起来是假的依赖。

## 六、G6 —— 实时流量 / 代理页排序 / 订阅自动更新

这一节是 §九 原先写"整项未开工"的那一项，本轮做完。**三条各自都有"默认必须是那一档"的纪律**，
所以逐条写清判据住在哪、夹具钉了什么、以及装机上会以什么形状骗人。

### 6.1 实时流量（`Backend/TrafficRate.cs`，纯函数）

§九 已经把"绕不开 WebSocket"那句撤回了：`GET /connections` 的响应体里
`downloadTotal` / `uploadTotal` / `memory` 是**累计值**，两次轮询之差除以间隔就是平均速率，
零新增传输通道。本轮就按这个做：

- `KernelView.LoadAsync` 顺手把这三个数读进 `Snapshot.Totals`（以前整条丢掉，尤其 `memory`
  是 Docs/60 那条内存实测的直接来源）；`ParseTraffic` 与 `ParseConnections` 共用同一套
  "根不是对象就返回全 0，不抛"的守卫。
- `TrafficRate.Between(prevTotals, prevAt, curTotals, curAt)` 返回 `(Known, Up, Down, WhyUnknown)`。
  **四条判据**（各有一条断言）：
  1. 首个样本（`prevAt == MinValue`）判**未知**，不画 `0 B/s` —— "刚连上"和"真没流量"
     在界面上同形就是骗人；
  2. 计数器**变小**判未知，★ 绝不取绝对值 —— 一次内核重启会被读成一次突发大流量；
  3. 上行跌而下行没跌也整组判未知 —— 半真半假比全假更难查；
  4. 间隔非正判未知且不做除法（时钟回拨 / 同轮重复采）。
- ★ "三条全零 = 没读到"与"有内存、流量为零 = 真空载"是**两种不同**状态，分开画
  （`DescribeTotals`）。这一条值得单独记：老写法只看 `up==0 && down==0` 就报 0，
  于是内核刚重启、计数器还没涨的那一拍，会被画成"隧道空载"。
- 差分用的上一条累计值放**字段**（`_prevUp/_prevDown/_prevTrafficAt`）不放 `UseState`：
  它是轮询循环自己的私有账本，不参与渲染；画出去的是那一行文本。
  口径同 `_subUrl` 那条"渲染之外的代码只读字段"的纪律。
- ★★ **内核不可达那一拍（`Ok=false`，配置视图）显式改成「读不到」，并把差分账本清成
  "还没有上一条"**。
  ★ 这里第一版写的是"不动这条、保留上一行"，理由挂着"断开时也想知道刚才多少" ——
  **那个理由是错的**：形状正是 1.0.79/1.0.80 栽过的那一次，<b>状态文本悄悄停在最后一次
  成功的读数上</b>，界面看着还在跑、实际早就读不出来了（memory「Sentinel silent death」）。
  流量这一行没有理由例外：`↑512B/s` 挂在一条已经断掉的隧道上，比挂一个「读不到」危险得多。

  ⇒ 重连后第一拍是「首次采样」，这是**对的**行为，不是缺陷（装机取证时别当 bug 记）。

### 6.2 代理页排序（`Backend/NodeSort.cs`，纯函数）

三档视角：**原序（默认）/ 延迟 / 名称**。判据里两条是本轮最容易犯的错，各钉了断言：

- ★★ **按延迟排序时，"从没测过"的 `DelayMs == -1` 绝不能排到最前**。
  拿 `DelayMs` 直接升序排的结果是一屏"看起来 0ms 的神秘节点"，而它们只是没被测过。
  所以排序键是**分档**的：真延迟（`>0`，越小越前）→ 本轮不通（`==0`，官方测速失败往
  history 写的就是 0）→ 未测（`-1`）。不通排在未测**前面**：至少它是个被测过的条目。
- ★ **组行与内置策略不参与"按延迟"那档的序列**（`DelayBucket` 回 `-1`）。
  把 🔰 选择节点混进真节点的延迟序列，会出现"它排在某真节点前因为它 history 末位是 0"——
  正是 1.0.84 修过的那一类"一列混排读反"。它们按**原索引留在原槽位**上。
- ★ 夹具在这一条上抓到一处真缺陷：第一版写 `outList[r.Index] = r.M`，
  那是"每个节点回自己家"，排序**完全没生效**（`B-慢 300ms` 仍在 `a-中 120ms` 前面）。
  正确写法是把真节点占的**槽位集合**先抄下来，排完序按槽位顺序回填。
  这个形状装机后的表现是"点了延迟排序，顺序看着也挺合理"，**没有夹具就查不出来**。
- ★ 同档用原索引做决胜（`List.Sort` 不稳定）：否则两条未测的节点每次刷新换个先后，
  比不排序更难受。
- ★ `ParseMode` 认不出的字符串一律回**原序**，不回延迟 —— 默认必须是"不改任何东西"那一档。
- 名称档用 `OrdinalIgnoreCase`（中英混排 / emoji 是订阅常态，文化敏感排序会随区域设置换位）。
  ★ 这里**不**沿用 `KernelView.Find` 的 `Ordinal`：那边是"按名字选中这一条"，
  差一个大小写就该选不中，绝不能近似；同一项目里两种口径各自成立。
- 排序是**视图**，不改 `Members` 本体 —— 选择、测速、台账回放读的还是内核那份。
- 界面在页头下面画三枚按钮 + 一句 `DelaySummary`（`有延迟 N　不通 M　未测 K`）。
  ★ 那句摘要才是这一档的实际价值：30/32 条未测时，"按延迟"的前两名其实是那 2 条测过的，
  不写这句就会被读成"这两个节点最快"。
