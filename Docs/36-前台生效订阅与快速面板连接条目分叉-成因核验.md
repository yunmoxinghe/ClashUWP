# 36 · 前台显示「星链机场」但快速面板亮「iKuuu」—— 成因核验

> §1–§3 是核验记录（**只读现证，不含推测**）；上一轮基于猜测改的三处（`SystemProfileName` → `p.Name`）
> 已全部撤销。§4 是方案对比，§6 是**按 §4 的「A + B」组合在 1.0.86 落地的实现记录**。
> 代码已 `dotnet build` 0 警告 0 错误；**装机实测尚未做**，未验项集中在 §5。

## 0. 一句话结论

**不是显示 bug，是数据面真的在跑 iKuuu。**

「快速面板亮 iKuuu」是**真值**；「前台生效订阅 = 星链机场」是**假账**。
根因：**App 内切订阅只热重载内核配置，不切 VPN profile 会话**；而插件每次（重）拨号都按
profile 里钉死的 `subId` 把 `config.kernel.yaml` 覆写回旧订阅，把那次热重载的成果吃掉。

## 2. 因果链

```
02:33  生效=hkom1，用户点「连接 VPN」→ ConnectProfile(iKuuu_V2) → 会话建立
        插件 _config.SubId = hkom1（钉死在这条 profile 的 CustomConfiguration 里，会话期不可变）
之后   用户拉取并启用「星链机场」
        ActivateAsync：写 config.yaml → SetActive(starlink) → ReloadActiveConfig（热重载）
        ★ 全程不 Disconnect / 不 ConnectProfile → 会话仍属 iKuuu_V2
随后   每次（重）拨号（含 RasMan 自动重拨、装机重启）
        插件 Connect 按 _config.SubId=hkom1 重新生成 config.kernel.yaml = iKuuu
        ★ 把上一次热重载推进去星链机场的成果整个覆写掉
结果   账本（config.yaml/subActive/前台「生效中」）= 星链机场
        隧道与内核（profile 会话 + config.kernel.yaml + 出口节点）= iKuuu
```

## 3. 为什么现有两道保险都没拦住

### 3.1 `ActivateAsync` 不切会话（`SubscriptionManager.cs:245`）

函数体只有四步：`WriteAllTextAsync(ActiveName)` → `SetActiveAsync` →
`ReloadActiveConfigAsync` → `EnsureSubscriptionProfileAsync`（只保证 profile **注册/改名**，
不碰连接）。注释「点一下即原地热重载（连接中）」写的就是现状 —— 这个 UX 是照 Clash Verge 抄的，
但 Verge 侧内核与 profile 不是这种「会话期 subId 不可变」的绑定关系，**照抄了交互、没照抄前提**。

### 3.2 轮询回填是**边沿触发**，且首轮不判定（`MainComponent.cs:258-295`）

下列代码是 **1.0.85 及以前**的形状（1.0.86 已按 §6 的 B 案改掉，此处保留以证成因）：

```csharp
if (firstPoll) { lastConnectedSub = connectedSub; /* 只记日志，不回填 */ }
else if (connectedSub != lastConnectedSub) { AdoptAsync(connectedSub); }
```

本例里 `connectedSub` 从始至终 = `hkom1`，一次都没变 ⇒ 边沿永不触发 ⇒ 分叉对这段逻辑
**完全隐形**（E10：全 log 零条 adopt）。首轮不回填是 1.0.72 为了避免「把上一次会话的残留
当成用户意图」而刻意设计的，设计本身没错，但它与 §3.1 合起来造成：**唯一能发现分叉的观察者
被设计成看不见这个分叉**。

### 3.3 反向回填也会输

即便 adopt 触发（用户在**面板**切订阅），`AdoptAsync` 改的是 `config.yaml`；而插件下次拨号
仍按 profile 的 `subId` 覆写 `config.kernel.yaml`。两边都在写「生效」，
但**profile 是真相、config.yaml 是账本**，覆写方向决定了账本永远赢不了。

## 4. 可行方案

| 方案 | 做法 | 覆盖面 | 风险 |
|---|---|---|---|
| **A 切订阅即切会话**（推荐主修） | `ActivateAsync` 时若已有会话且 `connectedSubId != 新 id`：走 `VpnProfileSetup.DisconnectAsync` → 等新会话离开 Connected（复用 `GracefulTeardown` 的等待口径，**只等不断profile**）→ `ConnectProfile(新 subId 的 profile)` | 根治：面板/账本/隧道三者一致 | 碰隧道。自动重拨会把旧 profile 再拨回来（memory「Redial 828 loop」），必须在断开后确认没有对旧 profile 的续拨；误拆会话＝整机断网事故重演 |
| **B 让账本跟隧道走** | App 启动/轮询把边沿触发改为**电平触发**：`生效 != connectedSub` 且会话是 Connected ⇒ 以隧道为准回填，并在界面显式标出「生效 X / 隧道 Y」分歧 | 消灭「假绿灯」，用户至少不被骗 | 不解决「切了没换」，只是把错位如实显示；且可能与用户刚点的启用互相顶 |
| **C 插件侧不再覆写** | 插件生成 `config.kernel.yaml` 时，若存在比会话更新的一次「启用」，改读生效订阅正文 | 让热重载不被吃掉 | 让 profile 的 `subId` 语义失效，「面板点哪条连哪条」这条已验收的产品契约会被破坏 —— **不建议单独用** |
| **D 无生效 profile 时禁连** | 已有：`连接 VPN` 按钮在无生效订阅时禁用 | 只挡空态 | 与本症状无关 |

**建议组合：A（主修）+ B（兜底可见）**。A 负责让三者一致，B 负责任何残留不一致都必须被用户看见
—— 按本项目纪律「静默或指错的失败一律算没修」，只做 A 而无 B 的话，A 失败时又是一次静默错位。

平台约束（进 A 的实现前必读）：官方 `VpnChannel.Start` 有 "There can only be one VPN profile per
process"，`VpnProfileSetup.ParallelConnectedReportAsync` 对并发的口径是**只观测不处置**。
⇒ A 必须是「先断干净、再连新的」串行流程，不能并行两个 profile。

**落地状态**：A + B 已按上述组合写进 **1.0.86**，实现细节与两处口径修正见 §6；C 未做（会破坏
「面板点哪条连哪条」这条已验收契约）；D 维持现状。

## 5. 未验证 / 待补（1.0.86 装机前这些都是**开放项**）

1. **断开→重连新 profile 的实测形状**：本仓没有做过「会话期切订阅」的装机实测
   （E4 显示星链机场 profile 建成但从未被连过）。A 方案已实现，但它是不是真能落到
   `Connected` **仍然未知** —— 这条就是 §6.5 验收清单的第 1 项，`profile-switch` 那行日志
   （成功 Info / 失败 Warn 都必写）是专门为补齐它准备的第一手证据。
2. **RasMan 自动重拨与 A 的竞争**：需要一条实测判据确认切会话后旧 profile 不被系统再拨回来
   （memory「Redial 828 loop」）。当前实现只在**发起时**串行，**没有任何机制阻止系统在收尾后
   把旧条目再拨起来**；若真被拨回，B 的电平回填会把账本改回旧订阅 —— 用户会看见分歧行反复横跳，
   这是可观测的，不会再变成静默错位。
3. **切换窗口与健康哨兵的竞争**（新增，源于 A 的实现）：切会话走的是 profile 级断开
   （`EnsureTornDownAsync` 内部的 `ProfileStore.DisconnectProfileAsync`），绕开了
   `VpnSession.DisconnectAsync`，因此**哨兵全程保持武装、也不会被解除**
   （设计如此：旧会话断开期间整机不能失去兜底）。但物理网络看门狗（`HealthMonitor`）的判据是
   「连续 N 轮物理出口不可达 + 动手前复核」，切换那几秒正是默认路由短暂缺失的时刻。
   理论上要连续 N 轮才动手、且必须复核一致，命中概率低，**但没有实测背书**。
   最坏形状已现读核对过，**不是**「拆掉我们正在拨的那条」：看门狗动手时走
   `DisconnectThenDeleteAsync(why)`，它找的是 `FindProfileAsync()`（默认名 `ProfileName`
   = 基础条目 `ClashUWP`，见 `GracefulTeardown.cs:141`），所以它删的是**基础 profile**，
   与订阅 profile 的切换不直接撞车。但后果仍然难看：`OurStatusAsync` 在没有任何 Connected
   条目时会兜底回基础 profile，基础条目被删 ⇒ 前台「当前状态」变 `Profile缺失`。
   装机实测必须盯 `physical-watchdog` 这个通道有没有在切换窗口里出声。
4. `RequireVpnClientAppUI` 翻转（基础条目隐藏）在 1.0.85 装机后是否已把老 `ClashUWP` 条目
   改成隐藏 —— E3/E4 显示基础条目 UI=False，这条**成立**，与本症状无关。
5. 本机 `GetProfilesAsync` 读到的 `星链机场` 条目是何时建的：app.log 尾部未见其
   `订阅profile[星链机场] 新建` 行（日志滚动或写入被跳过），不影响本报告结论，但建档时该标为未决。
6. **分歧行的可见性只到「代码层」**：`DivergenceLine` 已去掉前景色刷（见 §6.4 的理由），
   但「粗体 + ⚠ 在真机上确实显眼」没有装机截图背书。

### 6.2 A 案：`SwitchToSubscriptionAsync` 的流程与安全闸

```
GetProfilesAsync → 按 CustomConfiguration.SubId 选目标 profile
  找不到 → Ok=false「先拉取并启用该订阅」
FindConnectedProfileAsync() 选「当前连着的那条」（同一份判据，见订正④）
  显式再要一次 Connected；否则视为无会话
  没有 → Ok=true「当前无活动会话，无需切换」    ← 无事可做不算失败，且绝不擅自拨号
  已经是目标 → Ok=true「会话已经在 [x] 上，无需切换」
GracefulTeardown.EnsureTornDownAsync(旧)            ← 只等不删；断开由它自己发起（见订正③）
  收不干净 → 记 Warn、Ok=false，拒绝发起新连接（绝不带着未收尾会话去连第二条）
ConnectProfileAsync(新) → 20 秒轮询实际状态
  落到 Connected → Ok=true / Info
  否则        → Ok=false / Warn「未落到 Connected，不能对用户说『已切到』」
```

四处**对 §4 计划的修正**，都是实现（或实现后复核）时发现的口径问题：

- ① 计划里写「走 `VpnProfileSetup.DisconnectAsync`」——那是**基础 profile** 的断开入口
  （它内部 `FindConnectedProfileAsync()` 找不到已连接条目时会退回基础条目），切订阅时
  要断的是旧会话自己那条 ⇒ 断开动作只对 `current` 这条 profile 发
  （`ProfileStore.DisconnectProfileAsync(profile)`，由 `EnsureTornDownAsync` 代劳，见 ③）。
- ② **不删 profile**：只断会话、留条目，快速面板上那条订阅仍然可点（删除会连带 `LocalState`，
  见 memory「Loose layout vs packaged MSIX」）。
- ③ **断开必须由 `EnsureTornDownAsync` 自己发起**（首版写成「我们先 `DisconnectProfileAsync`，
  再叫它保证收尾」，复核时判定为错并改掉）：该方法开头先读一次状态，
  不是 `Connected` 就直接返回「无需断开」并**跳过等待**。我们先断一次，它几乎必然读到
  `Disconnected` ⇒ 「连续两轮、最多 `WaitSeconds`(=20) 秒等真收尾」这道闸形同虚设，
  旧会话还在平台手里半起半落时就去连第二条 —— 正是这个串行流程要避免的并发。
  现在 `st0` 读到的必是 `Connected`，断开与等待都由它一次做完。
- ④ **「当前连着哪条」不再自己写判据**（首版在 switch 里另写了一遍 Probe/Dataface 排除 +
  `Connected` 筛选，复核时改成复用 `FindConnectedProfileAsync`）：同一份筛选写两处早晚分叉，
  口径同 1.0.84 对 `KernelView.Find` 的订正。但不能直接拿它的返回值当「有会话」——
  它没连着时会**兜底回基础 profile**，若照单全收就变成「用户根本没连接时，切订阅擅自拨了一条
  隧道出来」，违反已验收的「空壳不拨号」。所以复用判据、再显式要一次 `Connected`。

`Ok` 的语义写死在底层方法里（无事可做 = true；找不到 / 安全闸拒绝 / 没落到 Connected = false），
上层不再靠猜字符串拼成功文案 —— 这正是 Docs/36 §0 那个「假账」的成因所在。

### 6.3 B 案：电平触发 + 切换让路

回填条件（每 3 秒评一次，不再是「读数变了才评」）：

```csharp
connectedSub 非空 && !VpnSession.SwitchInProgress && connectedSub != _subActive.Id
  → AdoptAsync(connectedSub) → 成功后 RefreshSubscriptionsAsync() 刷新 _subActive
```

- **判据为什么是「隧道为准」**：§3.3 已经证明覆写方向是 profile → `config.kernel.yaml`，
  账本永远赢不了，所以只能让账本跟隧道走。
- **为什么首轮不再豁免**：1.0.72 的「首轮只取基线不判定」是为了不「把上一次会话的残留当成用户意图」，
  而它换来的代价是 E10 那种**启动即分叉、永远不跟账**的形状。现在启动基线只写一行日志、
  判定照常进行。
- **1.0.72 那条「回填撤销用户切换」的坑怎么防**：`VpnSession` 用 `int` + `Interlocked`
  计数暴露 `SwitchInProgress`，切换期间轮询**一律不动账本**，由切换自己给出结论；
  切换完成后账本与隧道本就一致，条件自然不成立。
- **不会反复回填**：`AdoptAsync` 成功 → `RefreshSubscriptionsAsync` → `_setSubActive` 重渲染 →
  `_subActive` 镜像刷新（`MainComponent.cs:211`），电平条件自消。失败走 Warn 不重试刷屏。
- 两条 profile 同时 Connected 的**并发观测仍按边沿**（每轮都查会成热路径刷屏，且平台无背书）。

### 6.4 界面：`DivergenceLine`

主页「当前状态」下面多一行，一致或未连接时是 `Empty()`（不制造常态噪音）：

```
⚠ 隧道实际连的是「iKuuu_V2」，生效记为「星链机场」—— 正在按隧道跟账，见下方提示
```

三个刻意的设计：

- **名字复用 `SubscriptionManager.DisplayName`**（`SubLabel`），不在界面上另写一套取名规则；
  清单还没读出来时原样回 id，**绝不回空串**把分歧伪装成「没连着」。
- **不设前景色刷**：Docs/19 §4 记过资源键缺失时 Reactor 发的是透明画刷 —— 不抛异常、直接看不见。

### 6.5 日志通道与装机验收清单

新增 `profile-switch` 通道（成功 Info / 失败与拒绝 Warn），加上既有 `profile-sub-adopt`、`session`。
验收按顺序做，任一项不过就停下报现象，不要继续往下测：

1. 连接状态下切订阅 → app.log 有 `profile-switch` 且结尾 `实际状态=Connected`；
   `probe.txt` 里 Connected 的那条变成新订阅；前台 hint 开头是「已切到」。
2. `plugin.log` 下一次会话的「配置源」= **新订阅** 的 `subscriptions/{subId}.yaml`；
   `config.kernel.yaml` 行数/name 数与新订阅正文一致（本例应 569/36，而不是 9920/18）。
3. 快速面板与前台显示同一条订阅，界面上**不出现** `⚠` 分歧行。
4. 人为制造分叉（面板点旧订阅）→ 分歧行出现，3 秒内账本跟隧道走、行消失；
   整段过程 `nrpt=0` 与死接口路由 `=0`（收工判据，memory「Orphan NRPT machine blackout」）。
5. 断开后不再有任何自动重拨把旧 profile 拨回来（§5 第 2 项）：观察 `profile-switch` 之后
   是否出现指向旧 subId 的新会话日志。
6. 切换中途拔网线/让旧会话收不干净 → `profile-switch` 出现「拒绝切换」Warn，
   前台说「切到…未完成」而**不是**「已切到」。
   （`profile-switch` 那行的形状是 `[旧]→[新] 收尾=…（状态=Connected → 发起平台断开 …）, 新连接请求=…, 实际状态=…`
   —— 「断开」不再单列，因为断开由 `EnsureTornDownAsync` 内部发起，见订正③。）
7. **未连接时切订阅绝不能自己拨号**：断开状态下点「启用」→ `profile-switch` 不出现拨号行，
   前台 `当前状态` 仍是 `Disconnected`（走的是「当前无活动会话，无需切换」这条 Ok 分支）。
   这条是订正④的回归判据，也是「空壳不拨号」没被 A 案打掉的证明。
8. CLI 侧 `subuse` 已被本地闸门拦下（不带 `--force` 退出码 7、命令不发出去）—— **本条已实测通过**，
   见 §6.1。
