## 二、闸的形状（`VpnProfileSetup.ProveStoreWriteSafeAsync`）

★ **【1.0.109 订正】** 本节原判据是三条，**第 3 条已删**，理由与细则见
[Docs/55 §三.⑤](55-切订阅改走先断开后修改再重连三段式-反向修订1.0.93的切换不收尾-1.0.109.md)：三段式之后"后修改"这一步正跑在 `SwitchInProgress` 窗口**之内**，留着它等于让切换自己需要的 Add/Update 再欠一次账。

两条判据，任一命中就不写：

1. 任一本包条目 `Connected` / `Connecting` —— 走 `StatusOf`，**按条目降级**（1.0.96 那套），一条坏不拖死整轮；
2. 默认路由落在本包某条条目上 —— 这条走网络栈，不碰管理面那个坏句柄，正好补上判据 ① 的盲区
   （中毒那条自己读不出，看着像"没会话"）。

（原第 3 条 `VpnSession.SwitchInProgress`：1.0.101 立它时是"旧会话未必收尾"的近似；1.0.109 起
切换的第一段用官方那把尺子把这件事**证实或证伪**了，近似让位给真值。`SwitchInProgress` 本身仍留给轮询让路。）

### 二.① 和删除那道闸（`ProveNoLiveSessionAsync`）的分工，写在代码里也写在这儿

删除要的是"证明干净"，所以**读不到默认路由归属也算脏**（2026-10-16 那次整机断网的教训）。
写入不需要这个严格性：整机本来就没网时 `GetInternetConnectionProfile()` 返回 null，
照删的标准判，就会变成"没网的机器上连 profile 都建不出来"。
⇒ `ProveNoLiveSessionAsync(bool ownerUnknownIsDirty)` 开一个参数，**删除传 true（默认，逐字不变）、写入传 false**。
判据 ①（清单里任一条 Connected/Connecting）两边一样硬，没有松。

### 二.② 一条已经中毒的旁观条目**不挡**写入

`[星链机场]` 在本机现在就抛，`StatusOf` 回 `状态读不出` —— 那不是会话态。
如果把它当"可能有会话"，此后所有对账永久锁死，等于用一个已知坏的条目把整个功能判死刑。
（代价：判据 ① 对中毒条目失明时，只剩判据 ② 兜 —— 这也是为什么 ② 不能省。）

## 三、被拦下来之后：欠对账台账（`Backend/ReconcileOwed.cs`）

闸一拦，面板就少条目。"少一条目且没人记得它欠着"是本项目最忌的静默失败，所以：

| 位置 | 行为 |
| --- | --- |
| `Ensure*ProfileResultAsync` 的 Add / Update 分支被闸拦下 | 回 `Skipped`，文本带上**当时那句判据**，并 `MarkAsync(key, 判据)` 记一行账 |
| 同一 key 补齐（新增成功 / 更新成功 / 已就位） | `ClearAsync(key)` 销账；台账空了把提示位归零 |
| 订阅删除 | `RemoveSubscriptionProfileAsync` 成功后销账（否则台账里永远躺着一个清单里已不存在的 key） |
| 对账汇总行 | `profile-sub-sync` 末尾追加 `；仍欠：{key}⇥{首次}⇥{末次}⇥{判据}…` |
| 界面 | 挂载那轮如果台账非空 ⇒ 状态行下面提示"有 N 条 VPN 条目还欠着…断开后会自动补上"（★ 人话在前、`内部判据：`在后，1.0.100 的教训） |

**落盘**：`LocalState\profile-reconcile-owed.txt`，一行一条 `key⇥首次时间⇥最后一次判据`。
为什么不是内存静态位：写入方分属"拉取 / 切换 / 挂载对账"三条调用路径，其中挂载那轮可能在
另一个进程里跑（关窗后无头宿主，Docs/31 §4.3），进程内静态位随宿主一起消失。
`ReconcileOwed.Dirty` 只是**给前台轮询用的提示位**，不是数据源；每轮对账都用文件真值刷新它。

### 三.① 为什么"会话边沿补一轮"（1.0.95 那套）从这里起不够用了

边沿那一轮跑在 `connectedSub` 刚变空的那一刻，而平台会话此刻常常还在 `Disconnecting`
（Docs/38 实测 `DisconnectProfileAsync` 返回 Ok ≠ 收干净）⇒ 这一轮又被闸欠回去，
而之后 `connectedSub` 一直是空，**再也没有边沿**，那条 profile 就漂到下次挂载。
⇒ 轮询里加一条补扫：`ReconcileOwed.Dirty` 且不在切换窗口 ⇒ 每 5 轮（≈15 s）补一轮
`SyncSystemProfilesAsync("补账", allowPrune: false)`，台账空了自己就停。
粗筛（`connectedSub`）错了只会白扫一轮，真正的闸在 `Ensure` 里面。

### 三.② 1.0.104：这本账自己也得会"停止追讨"和"过期销账"

三.① 那套补扫写完，本机过一遍就露出三个洞 —— 都是"台账非空 ⇒ 永远有人在追"这一类的：

| 洞 | 形状 | 出口 |
| --- | --- | --- |
| 欠账的订阅被删掉 | 对账轮只为**清单里还在的**订阅跑 `Ensure`，而 `Ensure` 是唯一销账的地方；尤其"profile 还没建出来就被删"这条：`RemoveSubscriptionProfileAsync` 找不到条目就提前返回，连那一次销账都走不到 ⇒ key 永远躺在账上 ⇒ `Dirty` 恒真 ⇒ 前台 15 秒白扫，无休止 | `ReconcileOwed.PruneStaleAsync(keepKeys)`：对账轮末尾把 key 不在"清单 id + `基础profile`"里的欠账销掉并记 `profile-owed`。**清单为空时整个方法不动盘**（空清单更可能是"还没拉/读失败"，此时清空台账属于二次事故：丢了证物还顺手把欠账抹了） |
| 每轮都盖新时间戳 | `MarkAsync` 旧写法每次都重写那一行 ⇒ 台账内容**永远在变** ⇒ 谁都判不出"这一轮到底有没有进展"，也等于每 15 秒无谓写盘（与 `ClearAsync` 那条"台账空了别碰盘"的纪律自相矛盾） | 行格式改四段 `key⇥首次⇥末次⇥判据`；**判据逐字相同 ⇒ 直接返回**，不写盘不记日志。只有判据真的变了才更新末次并记一行 `欠账判据变化` |
| 拦着的不是会话，是条目自身中毒 | Docs/45 那条读数中毒（`状态读不出`）会让 `status != "Disconnected"` 这一支**永远**不满足 —— 没有任何时刻会来补它，补扫就成了每 15 秒撞一次 `VpnManagementAgent` 的 RPC + 每轮两条日志 | 补扫轮比较"本轮结束时的快照"与"上一轮结束时的快照"：非空且**逐字相同** ⇒ `SetDirty(false)` 并记一行 `补账连续两轮判据逐字相同，暂停补扫`。只放下提示位、文件原样留着当证物；判据一变会重新置脏，会话边沿 / 切换 / 挂载那几轮不看提示位照扫 ⇒ 不会漏补 |

第二行是第三行的**前提**：没有"判据没变就不写盘"，快照每轮都不同，那个"逐字相同"的判据根本不存在。
`Dirty` 仍然是进程内提示位（三.① 的口径不变），这三条出口都不改数据源。

## 四、代价：Docs/50 那句"换了订阅，条目立刻跟着动"改成什么了

| 场景 | 1.0.95~1.0.100 | 1.0.101 起 |
| --- | --- | --- |
| 断开状态下切订阅 | 立刻推整份清单 | **逐字不变**（没有会话 ⇒ 闸放行） |
| 连接中切到**已有条目**的订阅 | 其它条目改名/补齐立刻生效 | 立刻**不写**（欠着）；会话一交接完 + 补扫一轮 ⇒ 排在断开之后几秒内闭合 |
| 连接中**拉取**一条新订阅 | 立刻 `新建=Ok` ← 就是 Docs/45 那一行 | 跳过并记账，断开后补 |
| 连接中点「建/重建 profile」 | 只盯基础条目自己的状态，隧道挂在**别的**条目上时照删照建 | 整轮拒绝：`重建=跳过（{判据} ⇒ 会话期间不往 profile 存储里写条目）：请先断开当前连接，再点「建/重建 profile」` |

**「启用一条从没注册过的订阅」不能被打断** —— 这是本批唯一一处"必须写存储"的正经需求，
处理方式不是开后门，而是**自己创造干净时刻**（`VpnProfileSetup.PrepareStoreWriteForSwitchAsync`）：

- 目标条目已在 ⇒ 什么都不做（**绝大多数切换走这条**：fetch 时建过、或之前某轮对账补过）⇒ 会话零影响，照旧平台原子交接；
- 目标缺失且本来没会话 ⇒ 交给对账轮；
- 目标缺失且会话挂着 ⇒ **先对当前这条发平台断开、等它读数回到可信**（复用 1.0.99 的 `DisconnectAndWaitReadableAsync`），
  再建条目。此时"切换"已无对象可切（`SwitchToSubscriptionAsync` 找不到活动会话只会回"无需切换"、隧道躺在地上），
  ⇒ 改成直接拨目标 profile（`VpnSession.ConnectAsync(id)`，哨兵照常武装）。这一次切换会看到一次真实的断开再重连。
- 收尾等不到干净 ⇒ 如实拒绝，**绝不退回去"照样 Add"**。

### 五.② 装机才现形的反向 bug（1.0.104 → 1.0.105）

`PruneStaleAsync` 第一版写成了 `lines.RemoveAll(l => set.Contains(KeyOf(l)))` —— 判据**整个反了**：
删的是"清单里还在的那些"，留的是 ghost。本机塞了一条 `ghost-sub-for-prune` 进台账再跑一轮：

```
07:23:44.099 profile-owed 销掉清单里已不存在的欠账 1 条：ghost-sub-for-prune …   ← 日志说销了
台账文件里：ghost-sub-for-prune  07:00:00  07:00:00  新建：手工塞进来验 PruneStale   ← 文件说没销
```

两件事同时成立 ⇒ 证死，1.0.105 改成 `!set.Contains(...)`。
**教训写在这儿而不是只写进代码注释**：这一条如果只看 `profile-sub-sync` 汇总行就会误判成通过 ——
"日志说了什么"永远不能当"文件里是什么"的替代，凡是声称改了盘的动作，判据必须是回读盘。
