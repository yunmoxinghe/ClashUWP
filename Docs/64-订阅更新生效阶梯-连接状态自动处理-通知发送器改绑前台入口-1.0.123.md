## 一、这一批补的是执行侧的洞，不是判据侧

1.0.122 把「连着 VPN 也照样更新」接通之后，`ReloadActiveConfigAsync` 只有两支出口：

| 内核 REST | 旧行为 | 那句话在什么情形下是真 / 是谎 |
| --- | --- | --- |
| 可达 | `PUT /configs?force=true` | 真（原地生效，不拆隧道） |
| 不可达 | 回「新订阅已落盘（内核未连接，下次连接自动加载）」 | **没有会话**时是真话；**会话还记着**时是谎 —— 那一刻平台认为隧道在跑，而数据面已经不认这份配置了，"下次连接"永远不会自己来 |

⇒ 「支持连接状态自动处理更新」缺的就是这一步：按连接状态**自己选一条能生效的路**，
而不是把"没生效"包装成"以后会生效"。

## 二、Verge 实物口径（现读 `dev` 分支源码，逐条带行号）

`src-tauri/src/core/manager/config.rs`：

- `:359` `apply_config(path)` → 非服务模式走 `:397` `reload_or_restart(path)`
- `:443-464` 就是这一支的骨架：**先** `reload_config(path)`（`:466` = `mihomo().reload_config(true, path)`，
  即原地 `PUT /configs?force=true`），`let Err(err) = … else { return Ok(()) }`
  ⇒ 原地成功就到此为止、**不断流**；
- 原地失败打 `"Failed to apply configuration by mihomo api, restart core to apply it"`，
  然后 `restart_core_during_config_update()`（`lifecycle.rs:785-802`：受控 stop → `start_core_inner`
  → 复核 readiness generation → 重新套系统代理），重启成功就把这次更新判成**成功**（`:457 Ok(())`）
- 更新失败而正文已存时，回话固定是 `feat/profile.rs:234`「订阅已保存，但未能确认已应用到内核: …」
  ⇒ 本仓 `Unreadable` 那两支照抄这个口径，不许写成成功。

## 三、本仓的阶梯（`ClashUWP/Backend/ConfigApplyPolicy.cs`，纯函数 + 离线夹具）

```
① 正文落盘（SubscriptionReload.RegenerateEffectiveFile）
   └ 落不出 ⇒ 失败，明说两种成因（config.yaml 不存在 / 不含可用出站）
② 内核可达 ⇒ PUT /configs?force=true ⇒ 回读核心是否仍在线
   stage ∈ { Accepted, Refused, SilentAfterAccept }；内核本来不可达 ⇒ stage = Landed
③ 只在 Landed / SilentAfterAccept 这两支才读会话状态（ReadSessionPresenceAsync，纯读）
④ 结论：None 或 ReconnectOnce（自动拆会话重拨一次）
```

四态 × 四态 × 切订阅中 的判据表（`ConfigApplyPolicy.Decide`，`:104-149`）：

| stage | presence | 切订阅中 | 动作 | `Ok` | 回话口径 |
| --- | --- | --- | --- | --- | --- |
| `Accepted` | 不读（`NotAsked`） | 任意 | `None` | true | 已热重载内核并确认核心在线 ⇒ 原地生效，隧道未断 |
| `Refused` | 不读 | 任意 | `None` | false | 旧隧道原样保留，**不自动重拨**（拿被拒收的配置重拨，只会把还能用的隧道换成起不来的那一条） |
| `Landed`/`SilentAfterAccept` | `LiveSession` | 否 | ★ `ReconnectOnce` | 由重拨结果说 | 隧道还记着、数据面不认这份配置 ⇒ 自动断开重拨一次（对齐 `reload_or_restart`） |
| 同上 | `NoSession` | 否 | `None` | true | 台上没有会话 ⇒ 新订阅已就位，下次连接自然加载（**不凭空拨号**） |
| 同上 | `Unreadable` | 否 | `None` | false | 会话状态读不出 ⇒ 不自动重拨。**订阅已保存，但未能确认已应用到内核**（自己断开再连一次即可生效） |
| 同上 | 任意 | ★ 是 | `None` | true | 切订阅正在进行 ⇒ 不另开一次重拨，交给那一次的「先断开→后修改→再重连」（它拨的就是这份新配置，Docs/55） |

★ 全表**只有 2 格**允许动隧道（`Landed/LiveSession/否`、`SilentAfterAccept/LiveSession/否`），
这条被夹具写成穷举闸（§五 最后一条），多一格或少一格判据就红。

### 与 Verge 的两处刻意不同（不是没抄完）

1. **`Refused` 不重拨。** Verge 敢在拒收后重启内核，是因为它在 apply **之前**跑过
   `CoreConfigValidator::validate_config_outcome_with(&yaml)`（`config.rs:350-355`），
   能走到 apply 的配置已经证明"重启后起得来"。我们没有等价校验器
   （`SubscriptionShape.ProbeShape` 只验正文形态，不验 mihomo 收不收）。
   ⇒ 半截照抄会把它的安全前提一起抄掉，所以这里判成"保留旧隧道 + 如实失败"。
2. **"重启内核"在我们这是"拆会话重拨"。** 数据面是插件宿主进程内的 `clash_bridge.dll`
   （`Vpn/MihomoBridge.cs`，`Vpn/ClashVpnPlugin.cs:2396/:2755` 里起），
   前台没有任何动词能重启它 ⇒ 等价动作只有把这条会话拆掉再拨一次，新宿主在 Connect 里读 `config.yaml`。

### 为什么自动重拨只此一次、且只在读得出会话时才动

自动重拨动的是整机网络，本项目在这上面有账：Docs/55 三段式、828 无限重拨环
（memory「Redial 828 loop」）、`SessionStateUnknown` 那一族"读数坏了 ≠ 没连着"的实测
（Docs/51 §七.4：两条判据逐字成立，平台照样回 `AlreadyConnected`）。
⇒ 读不出 / 没会话 / 切订阅中 三条一律不动手。节拍侧的兜底沿用 1.0.122：
一轮更新只拨一次，失败进退避（6h 起翻倍，`SubscriptionAutoPolicy`），不会成环。

## 六、★【1.0.123-B】通知的路由入口从后台任务搬到前台

用户口径逐字：「通知的路由入口是后台任务，把他接到前台去」。

### 6.1 上一轮查证得到的三句官方事实（本轮据此动手）

1. **后台任务能发通知** —— 发通知靠 `Windows.UI.Notifications`，任何带包标识的进程都能调；
   官方「处理后台任务」的示例里后台任务代码中直接出现发 toast 的语句
   （`new ToastContentBuilder().AddText("You missed a call")`，注明要 WCT ≥7.0）。
   ⇒ 所以"能不能发"从来不是我们的问题。
2. **通知绑的是"调用应用程序"的身份** —— `CreateToastNotifier()`（无参）官方定义
   「创建并初始化**绑定到调用应用程序**的 ToastNotifier」，注解还写着
   「调用方没有有效的 AppUserModelID 就抛异常」。
3. **平台自己提供了换入口的把手** —— 带参重载官方定义
   「绑定到指定的应用（**通常是同一包中的另一个应用**）」，注解
   「由 *applicationId* 标识的应用**必须属于与调用方相同的包**」「无法发送到辅助磁贴，
   因此必须是**应用磁贴**的 ID」。
   ⇒ 我们的形状正是"同一包内的另一个入口"，这句是逐字对着我们写的。

### 6.2 根因（Docs/63 §一 已实证的，这里只补一句归属）

发通知这件事**必须**住在插件宿主（字节计数在那里，而该进程在会话期间一定活着；
前台会被挂起/节流/关闭）—— 这个判断不变、本批没动。
但 1.0.106 臂 C 把 `vpnClient` 任务挂到了第二个入口 `Application Id="VpnHost"`
（`Package.appxmanifest:233-255`，为了修"关窗 2 秒断流"，隔离性证据在 Docs/53 §五），
于是无参 `CreateToastNotifier()` 把这条通知绑到了 `…!VpnHost`：
**进程是对的，归属是错的**。缺省 `foreground` 激活那句"launch *your* foreground app"
里的"你的前台应用"= 这条通知所属的入口 = 无头宿主 ⇒ 点击拉起 `!VpnHost`，界面从没露过面。

⇒ 上一批（1.0.122）用协议激活把**点击落点**按 URI 归属兜回了 `!App`；
本批把**通知本身的身份**搬正：通知身份、通知设置开关（`notifier.Setting`）、缺省前台激活
三者一起落到带 UI 的 `App` 入口那一格。两道各自成立，不互相替代。

### 6.3 实现（`ClashUWP/Vpn/StatusToast.cs`）

- `CreateSessionNotifier()`：把带参重载试一遍，**成的那个就是本会话的发送器**；
  抛异常原样进日志（`发送器绑不进 <id> err=…`）。
  ★【1.0.124】"把候选试一遍"的循环已经不成立，只剩下面那条候选 —— 见下一条。
- ★【1.0.124 已按装机定论收缩】当初写的是三条候选（`ForegroundEntryCandidates()`，按可信度排：
  ① `<FamilyName>!App` —— 本仓 `Tools/UwpBridge/Program.cs:732` 一直在用、且装机拉起过的那把尺子
  `pfn + "!" + appId`，appId 取清单 `Application/@Id`；② `<FamilyName>!ClashUWP.App`（EntryPoint 全名）；
  ③ `App`（官方那句"必须是应用磁贴的 ID"））。装机读到的实物是**第一条就被接受、`发送器绑不进` 零行**
  （§七 #8），②③ 从未被执行 = 死代码 ⇒ 1.0.124 只留 `<FamilyName>!App` 一条，候选迭代器整个删掉。
  ★ 家族名仍取 `Package.Current.Id.FamilyName` 而不是写死 `…_4tjvwvefxrz66`：
  发布者哈希后缀换一张证书就变（Docs/38 §十四 F5），写死等于把"重签 = 换家族"打进通知通道。
- 读不到包身份 / 绑不进 `!App` 时退回无参重载（= 本改动之前的行为，`发送器=缺省(调用方入口)`），
  不回归、不静默。
- 选择结果记在启动那一行：`发送器=<选中的 id>`（与 `setting=` 同一条 notifier 对象读出来的，
  所以这一行同时证明"绑进去没有"和"横幅权限是哪一个入口的"）。
  ★【1.0.124】当初另有一个 `_notifierId` 静态字段"把选中的 id 存起来"，装机后回看：
  它写三处、读零处，取证靠的始终是那行日志 ⇒ 字段按"不留假想需求"删掉（Docs/65 §二 表第 5 行）。
  ⇒ **装机只需读 `plugin.log` 那一行就能定论绑进去没有**，不需要再改代码再打包。
- 发送器的**唯一**入口是 `LoopAsync` 开头那一次；`Update`/`Hide`/补发全部复用同一个
  `_notifier` 对象 ⇒ 不存在"绑 A 发、绑 B 撤"这种半新半旧的形状。

### 6.4 为什么不做成"通知改由前台进程发"

那样会回到 1.0.66 那个已被实测否掉的位置（前台被挂起 ⇒ 状态通知不再刷新），
而且插件宿主仍然必须活着跑数据面 —— 只是把一次跨进程传参加进热路径。
本批改的是**归属**，不是**发起进程**：官方那句"通常是同一包中的另一个应用"就是为这件事准备的。

## 八、本批没做 / 遗留

1. **没有前置校验器**（Verge 的 `CoreConfigValidator` 那一层）。因此 `Refused` 只能"保留旧隧道 + 报失败"，
   做不到 Verge 那种"拒收后重启仍然安全"。要真正对齐，得先有一份 mihomo 侧的合法性判据 —— 不在本批。
2. **`ReconnectOnce` 走的仍是「断开→拨号」两次平台调用**，不是原子动作：
   中间那几秒整机没网（UI 已明说）。彻底不断流的替代是把插件内核拆成独立进程再单独重启，
   方向与 Docs/29「插件回收进主工程」相反，本批不动。
3. 阶梯只在 `Landed`/`SilentAfterAccept` 才读会话状态。如果哪天真要给 `Accepted`
   也复核会话（例如"核心在线但平台侧会话已掉"），那是**另一个判据**，得先有实测再写。
4. §六 的三条候选装机后必然只剩一条被选中；**下一次改这里时应把没用的两条删掉**，
   别留成"以防万一"的配置项（口径同本仓"不做假想需求"的纪律）。
5. Docs/63 §六 第 4/5/6/9 行仍未跑（协议激活那道的装机证据），本批没有替它补。
