# 51 · 状态读数中毒：一条坏条目拖哑整面管理面 —— 按条目降级 + 复位出口（1.0.96）

**一句话结论（一手，装机的是 1.0.94.0）**：`VpnPlugInProfile.ConnectionStatus` 抛 `0x80070006` 是**按条目**坏的，不是整面坏的 —— 同一毫秒里一条抛、另一条读得好好的。之所以看起来"全都坏了"，是因为我们的状态扫描要**过清单里每一条**，一句裸读抛穿整次调用 ⇒「当前状态」「已连接订阅」「断开」「对账」「prune」「取证 dump」六处一起变哑。本批改三件事：① 读数**按条目降级**（坏一条只让那一条变成「状态读不出」）；② 界面上把动作回话与读数**分槽**，不再把 `未发起=读状态异常…` 当"当前状态"画给用户；③ 给中毒条目一个**复位出口**：拨号前读到中毒 ⇒ 先用两条与那个属性无关的判据证明"确实没有会话"，再把这一条删掉重建、重拨一次。

> 本篇是对 **Docs/45 的订正**（那条写的是"本包所有进程读状态永久抛"）+ **Docs/50 的配套**（面板同步那批把 Add/Update 推得更勤之后，这条读数债必须一起还）。

### ① 读数按条目降级 —— `VpnProfileSetup.StatusOf`

新增 [`StatusOf(VpnPlugInProfile)`](../ClashUWP/Backend/VpnProfileSetup.cs) + `internal const string StatusUnreadable = "状态读不出"`，把裸读换成它的位置：

| `FindActiveSessionAsync` 谓词 | 一条抛 ⇒ 整个"有没有会话"判据拿不到 | 坏那条算「读不出」，其余条照常给结论 |

**为什么这里不记日志**：`StatusOf` 在 3 秒轮询的热路径上，滚动日志的行格式是重拨保险丝的机器契约、热路径禁记（口径同 `Docs/33`）。归因走**已有的逐条面**，不新加行：debug-cmd `profiles`（`ListOurProfilesAsync` 每条一行 `… | 状态=`）与 `ProfileDump` 的 `[名字] ConnectionStatus=`。
★ **顺带订正 `Docs/45` §七 那句探针**："按一次断开、看有没有 `不发=` 这一行"只在 1.0.95 及之前能当"读数活没活"用；改后读数死了那行照样落（死的只是那一条，扫描不再抛穿）。探针从此换成上面那两个**逐条面**里出现的 `状态读不出`。

### ② 「当前状态」槽从此只放读数 —— `MainComponent`

用户看到的 `当前状态:未发起=读状态异常:COMException:句柄无效。(0x80070006)` 不是状态，是**上一次点按钮的动作回话**被写进了读数专用的那个槽：[`RunAsync(_setVpnStatus, …)`](../ClashUWP/Frontend/MainComponent.cs) 把 `ConnectAsync` 的返回值塞进了 `vpnStatus`，而轮询那一轮恰好也抛（改前），槽就永久停在那句内部判据上。

- 连接 / 断开两个按钮的结果改走 `_setActionHint`（与「建/重建 profile」同一个槽），**分工写死：状态槽只放读数，动作回话走提示行**。
- 轮询里的状态读数单独包一层 `try/catch`：它失败只让这一行变成「状态读不出」，既不许把异常文本留在槽里，也不许把同一轮后面的回填与边沿对账一起带走。
- 补上 Docs/45 修法第 3 条：读不出时界面上给一句**出口**（本应用只会拒绝动作、不会瞎拨；真实状态去 系统设置→VPN / `ncpa.cpl` 看）。

### ③ 拨号路径的复位出口 —— `ConnectWithPoisonRepairAsync`

[`ConnectAsync`](../ClashUWP/Backend/VpnProfileSetup.cs) 与 `SwitchToSubscriptionAsync` 的拨号这一步换成共用包装：拨一次，**只有失败形状是 `未发起=读状态异常`**（新增具名判据 `IsStatusReadFailure`）时，才对**那一条**做"删了按原内容重建"，然后**重新取对象**再拨一次（官方硬约束：自建对象拨不动，`CannotFindProfile`）。

判据认形状而不认别的失败：平台明确拒绝（`Connecting`、串行层拦住、`AlreadyConnected`…）各有各的处置口径，**不许拿删除去赌**。

回话形状：`<原来那句 未发起=…>；重建=…；重拨=<第二次 ConnectOnceAsync 的原话>`。保留 `未发起=` 前缀是有目的的 —— `VpnSession.IsNoDialResult` 靠它决定健康哨兵要不要当场解除（Docs/38 F1 那套），改了字符串就会把"没拨出去"当成"拨了"，让哨兵去断平台在途的会话。

★【1.0.99/1.0.100 订正，别照这一段读代码】上面这段是 1.0.96 建档时的设计，装机实测把它**逐条推翻**了："删了按原内容重建"没疗效（§七.3）、`AlreadyConnected` 证明平台一直记着那场会话（§七.7）、`DisconnectProfileAsync` 回 `Ok` 也不治（§七.10/§七.11）。现在这一支**不动存储**，复位=只对这条发一次断开并等读数恢复（`DisconnectAndWaitReadableAsync`），等不到就当场收手；回话形状改成"人话在前、`内部判据：` 在后"（§七.8、§七.11）。`未发起=` 这个 token 仍然留在串里，机器契约那条不变。

### ④ 删除判据从此不许拿"失败的读数"当证据 —— Docs/45 修法第 6 条落地

两处早就存在的假放行（Docs/45 §三 已点名，一直没修）：

- `GracefulTeardown.EnsureTornDownAsync`：`st0 != "Connected"` 就回"无需断开 ⇒ 可以删"，而 `SafeStatus` 在属性抛时回的是 `读状态异常:COMException` ⇒ **读数失败被当成"这条没连着"**。现在这一支直接拒绝删除，并把原因写进 report。
- `WaitSessionDownAsync`：同一把尺子，**两轮"读状态异常"就能把"等到收尾"凑满**（Docs/45 §三 那次"收尾=干净"就是这么来的）。现在失败的一轮只算"这一轮没看见"，不再累加 `downRounds`（`ProfileGone` 才算真消失）。代价照实：中毒期间这条路会走满 `WaitSeconds` 再回"未收到尾"，删除被拒。

### ④′ 复位用的"没有会话"判据为什么必须另找

上面那条纪律把删除闸收紧之后，复位路径自己也不能再用那个坏属性当证据（**它正是坏的那个**）。`ProveNoLiveSessionAsync` 用的两条都与 `ConnectionStatus` 无关：

1. **全清单扫**：改后每条单独降级，任何一条（不含 `Probe`/`Dataface` 残留）报 `Connected`/`Connecting` ⇒ 拒绝。
2. **默认路由的归属**：我们的 profile 是 `0.0.0.0/0` 全路由 ⇒ 会话活着时 `GetInternetConnectionProfile().ProfileName` 就是这条 profile 本身。这一步走网络栈，正好补上判据①唯一的盲区（**中毒那一条自己读不出，谁也不能仅凭"其它条都干净"断定它没会话**）。读不到归属（空串）同样**拒绝动手**，口径与 `PhysicalNetworkProbe` 的 `trusted` 一致。

两条都过 ⇒ 才删；删完按原名重建（快速面板上的条目不会因复位而改名）。**没做的**：不用 `断开=NoConnection` 当"没有会话"的证据 —— 官方条文写的是"没有可用网络连接"，我们断开语境里的历史实测形状是"平台上本就没有活动会话"（`VpnProfileSetup` :1166 那处注释自己就把两种读法并列着），拿一个**读法有争议的返回码**当删除许可，正是 `Docs/44`/`feedback-vpn-forensics-metrics` 反复点破的那类坑。

## 四、还没定的那件事（要用户点头）

**最可疑的成因**：03:05:25.830 在 `iKuuu_V2` 会话挂着的时候 `新建=Ok` 加了「星链机场」，之后首次扫描式读就抛。推断的形状是 **"活动会话期间往 profile 存储里 Add/Update ⇒ 新条目带着一个坏句柄出生"**。

★ 本节写完之后再对一次日志，这条推断**变硬了但也仍未证**，两点都要记下：
- **硬的地方**：坏的那一条恰好就是被 Add 的那一条 —— `[星链机场]` 由 subId 唯一定位，六次直接读它的 `ConnectionStatus`（`03:07:54.047 / 55.608 / 56.421 / 03:28:54.566 / 59.176 / 03:29:02.638`）**全抛**，而同时刻 `[iKuuu_V2]`（03:07:29.628）、`[ClashUWP]`（03:29:01.589）**全读得好**；首抛（03:06:04.390）落在 Add 之后 39 s、且在 03:07:15 那次平台重拨**之前**（本篇 §一 原先写"中间隔着一次平台自己发起的重连"当作削弱项，现在收回：那一次在首抛之后）。细则见 `Docs/45 §八.3`。
- **没证的地方**：**n=1，且同窗口还有别的动作** —— `03:05:26.039 reload PUT /configs?force=true`、`03:05:37~03:06:04` 后台宿主反复 `Run 返回 / 被平台取消 / Suspending / 起新 pid`。Add 与"活动会话"这两件事在这 115 s 里没被拆开过，所以只能说**一手相关**。别据此改代码。

如果这条成立，真正该做的是**预防**：`Ensure*` 的 Add 分支（现在没有任何会话判据，见 `EnsureSubscriptionProfileResultAsync` 的 `existing == null` 那一支）在会话挂着时**不新建、改记一次"欠对账"**，等边沿那一轮（Docs/50 新增的触发点，那时正好是 Disconnected）再补。代价直接把 Docs/50 那条产品承诺打折：**"换了订阅面板条目立刻跟着动"会变成"断开之后才动"**。

⇒ 这一批只做"坏了能读、能复位"，没动 Add 的时机。**要不要按预防改，是产品取舍，得拍板**；要证它，装机做单变量：断开状态下新建一条订阅 profile，再连任何一条，看首抛时刻是否跟着连接走（判据行：`profile-sub … 新建=Ok` ↔ 之后第一次 `ui-poll`/`health-precheck` 抛）。

### 7.5 由 7.3/7.4 得到的补法（1.0.98，两处，都在 `ConnectWithPoisonRepairAsync` 这一支）

1. **复位时先对这一条发一次 `DisconnectProfileAsync`**（`ClearStaleSessionRecordAsync`）——断开是唯一一个"按这条 profile 去拆会话记录"的官方动词，方向上只会拆不会建；平台没会话时它直接回非 `Ok`，返回值原样进日志（`重建=清会话=…+已删+复位…`）不当失败、也不当成功。
2. **三档出口**：①正常拨（官方前置条件）⇒ ②复位后重拨（仍走官方前置条件）⇒ ③**读数依旧抛**时 `BlindDialAsync`：跳过"先读状态再拨"，改由 `ProveNoLiveSessionAsync` 那两条与 `ConnectionStatus` 无关的判据担保（清单内无 `Connected/Connecting` 且默认路由不在我们任何一条条目上），判据不干净一个字都不发。
   ★★ 机器契约：③ 真发出去时，组合回话里**禁止**出现 `未发起=`（改用"首次与重拨的前置读状态都抛…；盲拨=受理=Ok…"），否则 `IsNoDialResult` 会把刚武装的健康哨兵解除 ⇒ 隧道起来却没人兜底，就是 2026-10-15 那次整机被占 20 分钟的形状。

### 7.8 由 7.7 得到的 1.0.99 改道（全部在 `VpnProfileSetup.cs`）

1. **复位这一支不再动存储**：`RepairPoisonedProfileAsync` 从"断开→删→按原内容建"改成**只对这条发一次 `DisconnectProfileAsync` 并等读数自己恢复**（新方法 `DisconnectAndWaitReadableAsync`，500 ms 一次叶子读、上限 15 s）。返回值改成结构化的 `(bool Recovered, string Message)`，调用方据此决定走不走下一步 —— 不再靠嗅探回话字符串。
