## 2. 缺口是什么形状（不是"少个功能"，是路由层旁路）

旧行为（1.0.69 及以前）是三条一起成立的：

1. `StartWithTrafficFilter` 的 `assignedClientIPv6list` 传 **`null`**；
2. 只往 `Ipv4InclusionRoutes` 里加路由，`Ipv6InclusionRoutes` **一条不碰**；
3. 内核配置里的 `ipv6` / `dns.ipv6` / `tun.inet6-address` 完全由订阅原文决定。

后果不是"v6 用不了"，而是 **v6 绕过整条隧道**：Windows 仍会把本机的 IPv6 出站
按物理网卡的 `::/0` 送出去，代理、规则、fake-ip 对它们完全不生效。
先遣项目 docs/96 §3 把这条钉在代码位置与实测上：

- 官方 sample 的 `includev6` 解析与 `routeAssignment.Ipv6InclusionRoutes(...)`
  **早就完备**（`CustomConfiguration.cpp:631-645 / 891`），只是脚本从来不下发；
- 宿主实测 `ms_tcpip6` 在所有网卡上 Enabled —— 换到提供 IPv6 的网络（家宽、热点、公司网）
  就会拿到全局 v6 地址 + `::/0`，旁路立刻真实发生；
- 判据 13（IPv6 泄漏）在本机无法直接连通性验证，因为**没有 v6 可漏**。
  docs/27 判据 1 则证明了另一半：传了 `assignedClientIpv6List` 之后 VPN 接口
  才长出 IPv6 协议实例（含平台自动生成的 `fe80::` link-local），`null` 时没有 —— 3/3 可重复。

我们的桥与先遣项目还有一个关键差异（见 §5.3）：**sing-tun 的 gvisor 栈无条件注册
IPv6 协议**，不会像先遣那套只注册 ipv4 一样把 v6 静默丢弃。因此本批的档 1 不只是
"把 v6 灌进黑洞"，v6 会真正进入 mihomo 的规则与代理；档 2 再把内核 v6 的
DNS/fake-ip 半边补齐。

## 3. 三档与默认

| 档 | 隧道接口 | 路由 | 内核配置 | 预期形态 |
|---|---|---|---|---|
| **0（默认）** | `assignedClientIPv6list` 仍传 `null` | 一条 v6 路由都不加 | 一个字节都不改 | **与 1.0.69 逐字一致**（继续存在 v6 旁路） |
| 1 | 下发 ULA 地址（profile `clientIpV6`，默认 `fd66:6:6600::2`） | `Ipv6InclusionRoutes` = `2000::/3` | 顶层 `ipv6` 不动；`dns.ipv6: false`（不答 AAAA） | 堵泄漏：普通应用拿不到 AAAA；硬编码 v6 字面量的流量进隧道，按规则/代理处理 |
| 2 | 同 1 | `2000::/3` + fake-ip v6 池前缀（默认 `fdfe:dcba:9876::/64`） | 顶层 `ipv6: true`、`dns.ipv6: true`、`dns.fake-ip-range6`、`tun.inet6-address: [<池网络号+1>/126]` | 全链路：AAAA 回假 v6，假地址经 include 进隧道，gvisor 栈承载 v6 |

★ **为什么默认 0**：这台机器没有 v6 网络，1/2 都无法在本轮读回来；而这两档
**碰隧道本体**（改 Start 的地址表与路由表），代价直接落在"整机还能不能上网"上。
口径与 `EncapReturn` 档 5、`SessionReset` 档 1/2 一致：先把臂做出来、可单变量切换，
默认停在已验证的旧行为。

★ **为什么绝不用 `::/0`**：先遣 docs/96 §6.2.1 的四臂实测 —— `::/0` 会让 Windows
把 VPN 也变成 **IPv4 默认路由**（4/4 臂一致），`2000::/3` 不会（0/2）；
最终三臂验收用 `fd00::2 + 2000::/3`，判据 13 连续 3/3 PASS，IPv4 判据 12/12 无回归。

## 4. 实现（按文件）

### 4.1 `VpnPluginConfig`：地址进 profile

- 新增 `public string ClientIpV6 = "fd66:6:6600::2"`（RFC 4193 ULA）。
- `ToXml()` 输出 `<clientIpV6>…</clientIpV6>`；`Parse()` 只接受
  **严格 IPv6 字面量**（`IPAddress.TryParse` + `InterNetworkV6` + 无 `%zone` +
  非 v4-mapped），非法回落默认、不抛。
- 与 `ClientIpV4` 同一条路径：**只有 `ipv6=1/2` 时才被放进 `assignedClientIPv6list`**；
  档 0 时这个值原样存在但不下发。

### 4.2 `LocalSettings`：三个开关

```text
ipv6=0|1|2                 默认 0
ipv6FakeRange=<ULA/48..64> 默认 fdfe:dcba:9876::/64
ipv6ClientAddress=<v6>     默认空 = 用 profile 的 clientIpV6
```

- `ipv6FakeRange` 由 `TryNormalizeV6Prefix` 闸门：必须是 IPv6 前缀、前缀长 48~64、
  **必须是 ULA（`fc00::/7`）**，并归一到网络地址。理由不是洁癖：它同时被当
  **路由目标**下发，写成 `2000::/3` 就把全局 v6 当假池、写成 `::/0` 会触发上面的
  IPv4 默认路由副作用。非法值回落默认并记 `channel=settings` 警告。
- 每轮 `settings` 日志新增 `ipv6=` / `v6addr=(profile)` / `v6pool=` 三列。

### 4.3 `ClashVpnPlugin.Connect`：地址与证据

- arm ≥ 1 才构造 `List<HostName>` 传给 `StartWithTrafficFilter` 的
  `assignedClientIPv6list`；arm 0 仍是 `null`（官方语义：null = DHCPv6/RD）。
- 新增 `_ipv6Diag`：写进会话日志 `evt=start … ipv6=<arm> v6include=[…]`、
  `channel=session` 的 RollingLog，以及 `dataface-plugin.txt` 的 `Ipv6=` 行。
  **arm=0 的 `Ipv6=arm=0 未下发` 是"本次连接与 1.0.69 一致"的凭据。**
- 顺带修正 Docs/21 里写错的交叉引用（G6 注释原写"Docs/22 的待验项"，应为 Docs/21）。

### 4.4 `BuildRoutes`：v6 路由

```text
arm 0 → 空
arm 1 → 2000::/3
arm 2 → 2000::/3 + LocalSettings.Ipv6FakeRange（归一后的 ULA 前缀）
```

地址与路由必须**成对**：先遣 V6D/V6E（只给路由不给地址）→ VPN 接口上一条 v6 路由
都没有；V6F/V6H（给了 `fd00::2`）→ 路由才出现。

★【1.0.119 订正】这段判据已经**搬出** `BuildRoutes`，落在 `ClashUWP/Vpn/RouteInclusion.cs`
（四桶分配 + 族别纠正 + `::/0` 拒绝 + 剔除原因），并进了 `Tools/YamlShapeTest`。
搬出去的直接原因是下面 §9 的两条错配 —— 它们只在 `ipv6≥1` 才咬人，而这台机器没有 v6 网络，
**装机永远读不回来**，只有离线判据能钉住。`BuildRoutes` 现在只做"把四桶装进平台对象"。

### 4.5 `KernelConfig.Transform`：内核配置（第二个参数面）

签名从 3 参变 5 参：

```csharp
Transform(string yaml, AppSplit? split, int ipv6Arm, string ipv6FakeRange, out string splitNote)
```

- **arm 0**：新参数不产生任何字节差异。
- **arm 1**：已有 `dns:` 块时强制 `ipv6: false`（值为空/块形状不动，不拿 YAML 冒险）；
  没有 dns 块时补的最小块里写 `ipv6: false`。
- **arm 2**：
  - 顶层 `ipv6: true`（已有标量就改真，缺失就插在文件头注释/`---` 之后）；
  - `dns.ipv6: true`，并在 `fake-ip-range` 之后补 `fake-ip-range6: <pool>`（已有不重复插）；
  - `tun.inet6-address: [<pool 网络号+1>/126]`：块形状插在 `enable`（或 `dns-hijack`）
    之后；行内流式 `tun: {…}` 也能插，且处理了 `tun: {}` 空映射的逗号边界。
  - 池地址取 `::1/126` 的理由：mihomo 默认就是 `fdfe:dcba:9876::1/126`；
    池从 `::4` 开始分配、`::2` 是 DNS 劫持地址，不冲突（见 §5.2）。
- **行内 `dns: {…}` 整块不动**（沿用 G6 起的 YAML 安全取舍）：这类订阅在 arm 1/2
  只得到"接口地址 + v6 路由"半边，内核 dns.ipv6 由订阅原文决定。见 §6。

### 4.6 `StartMihomoBridge`：环境变量与常驻栈重建

- **arm 2 且在首次全量启动前**设 `SKIP_SYSTEM_IPV6_CHECK=1`（`Environment.SetEnvironmentVariable`，
  try/catch）。原因见 §5.1：mihomo 的 `parseIPV6` 在"系统无全局 v6"时会把
  `tun.inet6-address` / `dns.fake-ip-range6` **静默清空**。只改本进程环境，
  不碰注册表、不改系统设置。
- 新增静态 `s_bridgeKernelV6`：记录当前常驻 gvisor 栈是否**以 v6 形态**建起来的。
  栈的地址族在 `tun.NewStack` 时定死，热重载与"已启动"分支的 rebind 都改不了；
  因此 **0/1 → 2 的连接会先 `clash_bridge_stop()` 再全量 Start**（这正是
  `residentBridge=0` 每次断开都在走的销毁/重建路径，不是"同进程第二次 Start"那条病态路径）。
  反向 2 → 0/1 **不重建**：没有 v6 路由、没有 AAAA，栈里的 v6 能力闲置无害。
  快照里的 `Bridge=…（v6栈=on/off）` 可分辨。

### 4.7 `IpPacket`：v6 校验和与组播（这条是数据面能不能通的前提）

- `Encapsulate` 在喂内核前调用 `FixChecksums`；旧实现 `Version != 4` 直接返回 ——
  **v6 TCP/UDP 一个字节都不补**。而 gvisor 端点没有声明 `RXChecksumOffload`，
  conntrack 对 v6 同样逐包验校验和（v4 在 1.0.15 之前的黑洞病史见
  `IpPacket.FixChecksums` 注释），Windows 的 checksum offload 对 v6 一视同仁。
  不补 = arm 1/2 的 v6 流量重演"包进得去、内核不回话"。
- 实现：`FixChecksumsV6` 只处理 next header 直接是 TCP(6)/UDP(17) 的包
  （扩展头一律不动，保守）；IPv6 伪头 = 16+16 字节地址 + 32 位上层长度 + 3 字节 0 +
  next header；UDP 在 v6 里校验和**必填**，stored==0 也补算，算出 0 写 `0xFFFF`。
- `IsNonUnicastDestination` 增加 IPv6 组播 `ff00::/8`（给接口下发地址后 Windows 会发
  ND/RS 到 `ff02::1:ffxx:xxxx`，不该喂进 gvisor）。
- **离线夹具**（`net10.0` 控制台直接编译 `IpPacket.cs`，独立实现 RFC 1071 对拍）：

  | 用例 | 结果 |
  |---|---|
  | v6 TCP 校验和 0 → 补算值与独立实现一致 | PASS（`0x2580`） |
  | 补算后全包复算（含伪头）折叠为 0 | PASS |
  | 二次调用幂等（不再改任何字节） | PASS |
  | v6 UDP 校验和 0（必填）→ 补算一致 | PASS（`0x7D36`） |
  | v6 ICMPv6 不被触碰 | PASS |
  | v4 TCP 回归（IP 头 + 传输层都补） | PASS（`0xB0D5`） |
  | v6 组播丢弃 / v6 单播保留 / v4 组播回归 | PASS |

  ★ 夹具第一版抓到了真 bug：伪头地址误从包头 0..31 求和（那是 version/flow/length
  等字段），正确范围是 IPv6 头内的 **8..39**。修正后才与独立实现一致 ——
  这也是为什么没有只靠"看起来对"就收工。

### 5.1 `parseIPV6` 与系统校验

`mihomo@v1.19.32/config/config.go:716`：

```go
parseIPV6(rawCfg) // must before DNS and Tun
```

同文件 `:1679-1682`：

```go
func parseIPV6(rawCfg *RawConfig) {
    if !rawCfg.IPv6 || !verifyIP6() {
        rawCfg.DNS.FakeIPRange6 = ""
        rawCfg.Tun.Inet6Address = nil
    }

```

`config/utils.go:205-222`：

```go
func verifyIP6() bool {
    if skip, _ := strconv.ParseBool(os.Getenv("SKIP_SYSTEM_IPV6_CHECK")); skip {
        return true
    }
    if iAddrs, err := net.InterfaceAddrs(); err == nil {
        for _, addr := range iAddrs { … IsGlobalUnicast() … }
    } …
}
```

⇒ 这就是 `SKIP_SYSTEM_IPV6_CHECK=1` 的出处：**官方留的校验逃生口**，不是我们发明的补丁。
★ 一个诚实的注脚：arm ≥ 1 时隧道接口本身已有 ULA（`fd66:…`），而 `IsGlobalUnicast`
对 ULA 返回 true —— 理论上这已经能让校验通过；但"vpnClient 进程能不能枚举到这张接口
的地址"没有实测，所以 arm 2 仍然显式设环境变量，把不确定性压成确定。

### 5.2 fake-ip v6 池的地址布局

`component/fakeip/pool.go:161-163`：

```go
hostAddr = options.IPNet.Masked().Addr()
gateway  = hostAddr.Next()
first    = gateway.Next().Next().Next() // default start with 198.18.0.4
```

⇒ 池 = 网络号；网关/tun 地址 = `::1`；第一个假地址 = `::4`；DNS 劫持地址 =
`::1.Next()` = `::2`（我们的 `bridge/core.go:187-188` 对每条 `Inet6Address`
追加 `Addr().Next():53`）。因此 `Inet6FromPool` 用"网络号+1 /126"与 mihomo 默认形态一致。

### 5.3 gvisor 栈无条件注册 IPv6

`sing-tun@v0.4.27/stack_gvisor.go:126-143`：

```go
NetworkProtocols: { ipv4.NewProtocol, ipv6.NewProtocol }
SetTransportProtocolHandler(icmp.ProtocolNumber4, …)
SetTransportProtocolHandler(icmp.ProtocolNumber6, …)
SetRouteTable({IPv4EmptySubnet, IPv6EmptySubnet})
```

`inet6Address` 只用于 ICMP 假回显与 TCP 回环（`:65-67`），**不决定协议是否注册**。
⇒ 即使 arm 1 不给 `tun.inet6-address`，v6 包进入 gvisor 后仍会被 TCP/UDP forwarder
处理并按规则/代理出网；档 1 的"堵泄漏"因此是"进隧道、按规则处理"，而不是先遣项目
那种"进 ipv4-only 栈、静默丢弃"。

### 5.4 出站 v6 同样绑定物理网卡

`component/dialer/bind_windows.go:14-31`：`IPV6_UNICAST_IF = 31`，`bind6` 用
`IPPROTO_IPV6` 设置接口索引；`bindControl` 按 network 选择 `bind6`/`bind4`。
⇒ G6 的防自环绑定（`dialer.DefaultInterface`）对 v6 拨号同样生效，不会因为开了 v6
出现"节点拨号被自己的 v6 路由抓回来"。

## 6. 明确不做的（写明白，不当成 bug 猜）

1. **不推 v6 DNS 到 NRPT。** `BuildDomainNames` 仍只下发 `_config.DnsServers`（v4）。
   应用查 AAAA 走的是隧道内 v4 DNS 上的 AAAA 查询：arm 1 为空应答，arm 2 为 fake v6。
   代价：应用如果把 v6 DNS 地址硬编码（DoH 直连 v6 字面量），那部分解析不受 NRPT 管 ——
   但它的 TCP 目的地仍是 v6 字面量，arm ≥1 会进隧道（`2000::/3`）。
2. **不支持 v6 节点服务器地址做外层 transport 目标。** `ResolveOuterTarget` 明确跳过
   含 `:` 的候选（v4 socket 的外层目标），保持旧行为。
   ★【1.0.128】这条的作用范围只限 `outerTarget=node`（默认 `auto` 时锚恒为黑洞 `192.0.2.1`，
   与节点族别无关）；别把它读成"v6 节点因此拨不出去"，因果见 §9.6 第 4 条的订正块。
3. **行内 `dns: {…}` 不改写**（YAML 安全取舍，同 G6）。这类订阅在 arm 1/2 只有接口/路由半边。
4. **`fakeIp=0` 时内核半边不生效**：`KernelConfig.Transform` 整体只在 `FakeIp` 为真时进。
   此时 arm 1/2 仍会给接口地址与 v6 路由，但 `dns.ipv6`/`fake-ip-range6`/`inet6-address`
   都不注入 —— 这一点与 G9 的应用分流是同一个总闸，别误判成"v6 配置丢了一半"。
5. **扩展头不补校验和**（Fragment/Routing 等），只处理 next header 直接 TCP/UDP。
6. **没有前台 UI**：开关只在 `LocalState\settings.txt`；本批不改主应用代码。
   ★【1.0.126 订正】这一条**已经不成立**：设置页新增「IPv6 通道」一节（三枚按钮 + 每档代价 +

## 7. 上机验收清单（需要一台**有 IPv6** 的网络）

前置：装 1.0.70 包；`settings.txt` 决定臂号；改档后**重新连接一次**（常驻桥会在
0/1→2 时自动停桥重建，见 §4.6）。

1. **基线（arm 0）**：连接后 `dataface-plugin.txt` 的 `Ipv6=` 必须以 `arm=0 未下发` 开头；
   `Get-NetIPAddress -InterfaceAlias ClashUWP` 只有 v4 —— 与 1.0.69 一致。
   ★【1.0.119】后面会跟着 §9.3 的三档读数之一：在有 v6 的网络上应该看到"⚠ 泄漏"，
   在本机（无全局 v6）应看到"没有 v6 泄漏面"或"读不到 ⇒ 未知"，**不该**是空。
2. **arm 1**：
   - 接口出现 `fd66:6:6600::2` 与平台自动生成的 `fe80::`（对齐先遣 docs/27 判据 1）；
   - 接口上出现 `2000::/3` 路由（`Get-NetRoute -InterfaceAlias ClashUWP`）；
   - ★【1.0.119】订阅里有 v6 节点时，同一张表上必须还能看到**该节点地址的 `/128`**
     （`Get-NetRoute -InterfaceAlias ClashUWP -AddressFamily IPv6`）。看不到就先查快照的
     `Routes=` 那行：`v6ex=0` 说明 `nodeExclusions=0` 或候选里根本没有 v6 节点，
     `v6ex≥1` 而表上没有 ⇒ 是平台把排除路由装到了别的接口（Docs/08 run 14 那个旧伤），
     不是 C# 侧没下发；
   - `nslookup -type=AAAA <域名>` 走隧道 DNS 应为空应答；
   - `curl -6 http://[2606:4700::1111]/` 的行为是"进隧道后按规则处理/失败"，
     而**不是**从物理网卡直接出去（用节点侧/代理 `connections` 面板或包计数判断）。
3. **arm 2**：
   - 配置生成物含 `ipv6: true`、`dns.ipv6: true`、`fake-ip-range6`、`inet6-address`；
   - 系统解析器查一个域名得到 `fdfe:dcba:9876::4+` 的假 v6（`Resolve-DnsName -Type AAAA`）；
   - `curl -6` 与浏览器访问 v6-only 站点（如 `https://ipv6.google.com`）能经代理出网；
   - `dataface-plugin.txt`：`Ipv6=arm=2 …`、`UpBytes/DownBytes` 同向增长、`Injected` 在涨；
   - 换网（G6 事件）后不断流，或至少 `NetFollow=` 行有记录。
4. **退出**：断开后 `nrpt=0`、幽灵路由=0（memory「Orphan NRPT machine blackout」的收工判据）；
   v6 接口随通道销毁，物理网卡 v6 恢复直连。
5. **回退**：任何异常先写一行 `ipv6=0` 再连接（不用重装、不用删 profile）；
   若整机网络异常，用本批稍后提供的恢复脚本清 NRPT/幽灵路由（Docs/23/24 见交付时索引）。

★ 口径陷阱（沿用 memory「VPN forensics metric traps」）：
`Get-NetAdapter` **看不见** VPN 的接口，别拿它判"接口没建"；
`Get-VpnConnection` 与 agent 读的不是同一份 profile 存储；
探一个物理可达的 v6 地址不能证明"整机在隧道里" —— 要用 fake-ip 或隧道专属判据。

## 9. ★【1.0.119】把"档 1/2 的形状"钉住：两条族别错配 + 一条播报

组件/应用随本批（Docs/62）一起走。这一节只做三件事，**没有抬默认档**：`ipv6` 默认仍是 0，
理由与 §3 完全一致（这台机器没有 v6 网络，档 1/2 碰隧道本体，代价落在"整机还能不能上网"）。

### 9.1 档 1/2 缺 v6 节点的排除路由（真缺陷，不是加固）

防自环那道路由层防线（`NodeRoutes` 的节点服务器宿主路由）以前**只往 v4 桶下发**：

| 位置 | 旧代码 | 后果 |
|---|---|---|
| `ClashVpnPlugin.BuildRoutes` 节点排除循环 | 条件里写死 `address.IndexOf(':') < 0` | v6 节点地址**整条被跳过** |
| `NodeRoutes.BuildExclusionCidrs` | 候选串统一 `ip + "/32"` | v6 地址的前缀长度本身就是错的（宿主路由在 v6 上是 `/128`） |

而档 1 下发的正是 `2000::/3` —— 它<b>覆盖全部全局单播 v6，包括 v6 节点自己的地址</b>。
于是"订阅里有 v6 节点 + `ipv6=1`"这个组合下，内核拨向该节点的外层包会命中自家 include，
被自己的隧道抓回去：形态就是 §Docs/08 记过的那类自环黑洞，而这一次没有任何排除路由兜它。

★ 为什么这条以前看不见：`arm=0` 时 v6 桶是空的，跳过 v6 排除**无副作用**；只有抬档才咬人，
而两档从未实机跑过。这条也不是"新能力"，是把档 1/2 从"抬上去会踩新坑"改成"形状自洽"。

现在（`RouteInclusion.Build`）：
```text
arm=0 → v6 include 空、v6 exclude 空（逐字旧行为，v6 排除被丢弃但必须点名）
arm≥1 → 节点 v6 地址作为 /128 进 Ipv6ExclusionRoutes
arm≥1 → profile 里的 v6 排除段进 v6 桶（旧代码会把它当 v4 路由对象装出去）
```

★★【1.0.126 订正】上面这三行**在本批之前是假的** —— 不是判据写错，是**生产端交不出输入**。
上表两处（`BuildRoutes` 的 `IndexOf(':') < 0`、`/32` 统一拼接）1.0.119 确实都改了，
可节点地址的**台账**还筛着族：`NodeRoutes` 把 v6 字面量存成空列表、域名解析只留 A 记录，
所以 `Build` 的 v6 exclude 桶**永远收到空**，那行"→ /128 进 Ipv6ExclusionRoutes"没有对象。
实物在装机 `node-exclusions.txt` 里逐字可见（三条 v6 节点的 value 全空）。
1.0.119 的夹具也没拦住 —— 它往 `Build` 里**手喂** v6 排除串，夹具全绿而产品那条链断在喂串之前。
本节当时那句"为什么这条以前看不见：`arm=0` 时 v6 桶是空的，跳过 v6 排除无副作用"是对的，
但据此以为"补上消费端就自洽了"是把两件事当了一件。
**修法、13 条判据（含端到端那条）与取证见 Docs/67 §二/§六。**

★★★【1.0.127 再订正】上面那句"1.0.126 补齐了生产端"**还是半截** —— 装机拨号验档 1 形状时
读回的是 `routes arm=1 … v6in=[2000::/3] v4ex=37 v6ex=0`，同一进程只加一行 `Stale=` 逼一次
全量重解析才变 `v6ex=3`。根因是**台账读取端**：`NodeRoutes` 在缓存没过 TTL（6 小时）时
**整轮跳过解析**（`if (forceAll || (!fresh && hosts.Count > 0))`），而 1.0.126 修的两处
都在 `RefreshBlocking` 内部 ⇒ 旧文件里 `2604:a00:101:2b:25::1=`（键有、值空）那三行被原样读回、
`SaveCache` 再原样写回 —— **疤自己保自己的鲜**，除非换网或等 6 小时，永远碰不到修好的那条路。
现在补漏搬到读侧：`RouteInclusion.RepairLedgerEntry`（键本身是地址字面量 ⇒ 键就是答案；
域名行的空值按设计保持为空，不许冒充解析结果）。
★ 这条的方法论记账：**一条链断两处的 bug，只修一处等于没修**，而且"生产端已修"这句话
在只有离线夹具（手喂输入）时会被误判成已完成 —— 见 Docs/67 §十一.2。
实物（旧形状台账 + 新鲜缓存 + 无 `Stale=` 的单变量重拨 ⇒ `v6ex=3`、三条 `/128` 落在物理 WLAN）

### 9.3 档 0 的泄漏面第一次被说出来（只播报，不动手）

`Ipv6=arm=0 未下发` 这一列以前是中性的，但它在本机有全局 v6 的网络里等价于
