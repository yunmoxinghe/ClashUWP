## 一、一句话结论

**主应用继续走单实例，不开 `SupportsMultipleInstances`。** 三条理由里只有一条是我们的偏好，前两条是官方条文级别的构造性限制：

1. 本包两条关键通道**都是 in-proc**：`windows.appService`（`Package.appxmanifest:126-128`，不带 `EntryPoint` ⇒ 连接激活的是前台进程本身）与 `windows.backgroundTasks` 的 `vpnClient` 任务（`:130-136` + Package 级 `windows.activatableClass.inProcessServer`，`:192-211`）。而官方口径是**进程内后台任务不支持多实例**、**进程内 AppService 不支持多实例**（条文见 §四 T1/T2）。开多实例不是"多一种选择"，是把这两条通道挪到它们不被支持的形态上。
2. 官方明确承认：**单实例应用可以拥有多个后台进程，仍然算单实例**（T3）。我们现在的形状（UI 一个实例 + 平台按会话拉起的后台宿主）正是官方设计内的正常形态，不是需要被"修"的缺陷。
3. 我们自己的取舍：多实例要求应用自行分割/同步共享状态（T4），而本包的共享状态是**四份进程内静态**——`ProfileStore` 串行闸、插件的 `s_activeChannel`、`HealthMonitor` 的单一武装槽、常驻内核标记。真多实例就把"闸只在各自进程内有效"（Docs/38 §11.4）从边界条件变成常态。换来的收益只有"省掉关窗后约 2 秒的平台重拨间隙"，不值。

> ★【2026-10-23 订正，臂 C】上面第 3 条结尾那句"换来的收益只有省掉 2 s 间隙"已经**过期**：那 2 s 间隙在 1.0.106 由**不开多实例**的另一条路买掉了 —— 把 `windows.backgroundTasks`/`vpnClient` 从 `<Application Id="App">` 挪到第二个入口 `<Application Id="VpnHost" … AppListEntry="none">`，平台按入口分配后台宿主 ⇒ 界面与插件宿主天然是两个 pid，关窗不再触发平台拆会话重拨。装机判据在 [Docs/53 §五](53-关窗2秒断联-臂A臂B注册期被拒-臂C把插件宿主挪到第二个Application入口已修好-1.0.102实验-1.0.106修复.md)。
> 本条决定不变：**仍然不开 `uap10:SupportsMultipleInstances`**，第 1、2 条理由一字未动（臂 A 那条"带 in-proc vpnClient 任务的入口在注册期撞互斥"依旧成立）。
> 同时作废一句旧措辞：本档曾把"加第二个 `<Application>`"当作会把无头豁免问题带回来的代价（§八 原文），那个前提是错的，见 §五。

## 三、三个同名属性的分工（这条最容易读错）

| # | 写法 | 挂在哪个元素上 | 语义（条文） | 最低门槛 |
| --- | --- | --- | --- | --- |
| 1 | `desktop4:SupportsMultipleInstances="true"` | `<Application>` | **应用类型**支持多实例：实例已在跑时，后续激活不再进现有实例，而是新建实例并单独进程运行 | UWP 多实例自 1803（17134）可选；`desktop4` 前缀只对面向桌面的项目有效 |
| 2 | `uap10:SupportsMultipleInstances="true"` | `<Application>` | 同上，是 1 的**新写法**，官方推荐用于面向 2004 及以上的应用 | target 10.0.19041 |
| 3 | `uap4:SupportsMultipleInstances="true"` | `<BackgroundTasks>` 元素 / `<uap:AppService>` 元素 | **扩展级**：每次触发/每次连接都在新进程里跑一个实例 | 必须 target 10.0.15063 或更高 |
| 4 | `ServerName` | `<BackgroundTasks>` / `<uap:AppService>` | "确保运行时只有一个服务器实例存在" —— 与 3 相反方向的旋钮（收拢而不是放开） | —— |

三条必须记住的连带规则（都是条文，见 §四 T5/T6/T7）：

- 应用级已经声明了 `SupportsMultipleInstances` ⇒ 它的扩展**不需要**再声明同名属性；
- 把该属性加到**除后台任务与 AppService 之外**的其它扩展上，而承载它的 `<Application>` 没声明应用级多实例 ⇒ **架构错误**（清单直接被拒）；
- 声明了 `SupportsMultipleInstances` 就**不能**再声明 `ResourceGroup`（多实例是"每次启动进不同宿主"，ResourceGroup 是"把多个后台任务归进同一宿主"，方向相反）；同一条互斥也适用于 `ServerName`。

顺带一句我们上次踩过的：官方那套多实例激活重定向要求**自己写 `Main`** 并加 `DISABLE_XAML_GENERATED_MAIN`（T8）。本包在全 AOT 下本来就是手写 `__managed__Main`（清单注释【事实 1】，`:13-18`），所以"能不能拿到 `AppInstance` 做重定向"不是障碍；障碍在前面 §一 第 1 条。

### 五·甲 口径（逐条对应证据）

> ★★【2026-10-23 同日二次订正，方向改了】本节上一版把"商店侧"判成"几乎不可能被拒"，**这句撤回**。
> 抓到两家第三方一手记录：`HeadlessAppBypass` 不是文档表里的通用能力，而是**账号级豁免**，
> 商店的包验收（package validation）在没有该豁免的账号上会因为入口带 `AppListEntry="none"` 拒提交 ——
> **而且被拒的是"次级"入口，不是"整包只有一个无头入口"**。原文见本节第 9 条（T16/T17）。
> ⇒ 正确切分：**本地打包/注册不拦**（我们 1.0.106 实物，第 1 条）；**商店验收拦**（第 9 条）。两维别再混。

1. **1.0.72 之前**：插件是第二个 `<Application Id="Plugin">`，它没有 UI，只能靠 `AppListEntry="none"` 隐藏。当年那条「你没有权限创建无头应用，请……确保你已与该应用关联了豁免 HeadlessAppBypass」的报错**被记成了这个属性的代价**，实际是同批一起改的两件事之一 —— 当年的修复同时补了 `Executable`/`EntryPoint` **并**移除了 `AppListEntry="none"`（Docs/25 验收报告 §1.3 `:32-36`），从没拆开验过哪一条才是因。⇒ **本条已由 Docs/53 §五.② 证伪**：臂 C 的入口三样齐全（`AppListEntry="none"` + `Executable` + `EntryPoint`），本地打包与注册直接通过。
2. **条文里根本没有这道门**（T11）：官方 `uap:VisualElements` 架构页对 `AppListEntry` 的全部描述是 "The entry in the All Apps List. Select none for entry points that do not need start menu tiles."，取值 `default`/`none`，**没有一个字**提到权限、能力或豁免。

4. **"无头应用不能上架"这句话的适用边界**（T13）：官方对无头合规性的表述是"为了使无外设应用满足 Microsoft Store 合规性，需要有一个与应用关联的'外设'"，微软给的解法是造一个空白应用、借它的 exe/dll 填 `Executable`/`EntryPoint`、再把 `AppListEntry` 属性**删掉**（[Servicing MSIX store apps for Windows Server IoT](https://learn.microsoft.com/zh-cn/windows-hardware/service/iot/servicing-msstore)）。它管的是**产品本身只有无头应用**（包里没有可启动的 UI）这种形状；策略层的对应条款是 10.3 产品可测试、10.4.2/10.4.3 必须能立即启动并保持响应 —— 约束的是**产品有没有可测的启动面**，不是"清单里不许出现隐藏入口"（T14）。⇒ 我们"一个可见主入口 + 一个隐藏插件宿主"与它**不同形**。
5. **VPN 插件的官方姿势本身就是无头入口**：`IVpn*` 侧的口径是"VPN 插件必须始终在其后台任务 `Run()` 方法中调用"，所需能力 `networkingVpnProvider`；官方 `microsoft/UwpVpnPluginSample`（CSharp/TestVpnPluginApp/Package.appxmanifest，`gh api … --jq .content | base64 -d` 取回原文）就是**一个包两个 `<Application>`**：`App` 带 UI，`Plugin` 用 `AppListEntry="none"` 承载 `<uap:Task Type="vpnClient" />`，并自带注释 "Notice how the foreground app and the background app are in two separate applications, this is vital to keep them running in two separate processes, so if one is closed, it won't terminate the other." ⇒ 臂 C（Docs/53）不是我们的发明，是照抄微软给 VPN 插件的上架形状。
6. **开多实例与这条无耦合**（原第 4 条改写）：同仓库反证仍在 —— CLI 包**同时**声明 `desktop4:SupportsMultipleInstances="true"` 与 `AppListEntry="none"`，打得出版、装得上（它当年撞的只是 0x80080204 那条 console/别名配对校验）。但**别再拿"CLI 是 full-trust 所以 `none` 不被拒、UWP 主应用会被拒"当解释**：那是为一条并不存在的拒绝编的机制。臂 C 的 `VpnHost` 是 `windowsApp` 行为、带真 UI 的兄弟入口，同样通过。

8. **商店侧的拦，拦在账号而不是清单**（T16 一手）：`HeadlessAppBypass` 在通用能力表里 0 命中这件事**不等于它不存在** —— 它不是可以写进 `<Capabilities>` 的声明项，而是**微软给开发者账号打的标记**。⇒ 上一版拿"条文表里搜不到"去否掉那句报错，是推理过头，撤回。

## 六、进程/实例模型的一手实测（这部分是本包的行为，不来自条文）

> ⚠️【2026-10-23 订正】本节 P1–P5 是 **1.0.77–1.0.93 单入口时代**的一手读数，原文保留有效，
> 但"关窗后平台另起后台宿主、约 2 s 间隙"那一段**已被臂 C 换掉**：1.0.106 起界面 pid 与插件宿主 pid
> 从注册期就是两个进程，关窗只挂起/回收界面视图，不再有 `Canceled`+重拨间隙（Docs/53 §五.③④）。
> ⇒ 本节末尾"一份静态状态、可能被平台搬到不同宿主进程里跑"这句要读成两代：单入口时代靠平台搬，
> 臂 C 之后是**两个入口各自一个宿主**；"取证永远按调用路径分、不按 pid 分"这条纪律不变，反而更成立。

| # | 一手记录 | 形状 |
| --- | --- | --- |
| P1 | Docs/31 §4.3（1.0.77 真拨号，含三行时序） | 前台在跑时，vpnClient 激活被单实例语义送进**已运行的前台进程**（插件行与 app 行同 pid=15504）。关掉前台窗口时，平台先给旧会话 `Canceled`，随后**另起一个后台宿主**（pid 5160）重拨，隧道自己回来（7 条 `ClashUWP` 路由 + NRPT 1 条），该进程被 `Suspending`/`Resuming` 来回调度过也没掉线；再开界面时激活路由回 5160、窗口挂上去 ⇒ **"关窗只关 UI 层"成立，代价是约 2 s 的平台重拨间隙** |
| P2 | Docs/38 §13.5 `:531` | `session 用户发起订阅连接`（前台路径）与 `connect 平台发起连接`（插件回调）**pid 相同** ⇒ 1.0.77 之后"进程隔离没有成立"，**UI 侧与插件侧共享 `ProfileStore` 那道闸**；闸真正管不到的只有 shell/快速面板那条**另一个进程**直发的路径 |
| P3 | `App.cs:58-86`（1.0.49 起） | `Suspending`/`Resuming`/`Exiting` 三个钩子**只记证据**，刻意不做拆隧道一类动作（`:69-70`：隧道归平台管，插件侧才是宿主）。注释 `:66-68` 同时写明"前台一挂起 `HealthMonitor` 那条兜底就停摆，插件进程里那条 `PhysicalNetworkWatchdog` 才是可靠宿主" |
| P4 | `Backend/VpnSession.cs:156-163` + `Frontend/MainComponent.cs:258/272/304` | 前台没有任何 VPN 状态变更事件可用，只能 3 秒轮询事后跟；快速面板发起的连接前台不参与也不被激活。轮询停了（挂起/关窗）就既不刷状态、也不回填账本 |
| P5 | `VpnSession.cs:46`（`HealthMonitor.Arm()`） | 前台哨兵只在**前台发起连接**这条路径上武装 ⇒ 由面板或平台重拨起来的那段会话，前台根本没有兜底（这条与 P3/P4 是同一条链的三个断面） |

**结论（本包自己的口径）**：我们的进程模型不是"前台=UI、插件=另一个进程"，而是"**一份静态状态、可能被平台搬到不同宿主进程里跑**"。取证永远按调用路径分，不按 pid 分（Docs/31 §四 + `project-rolling-log-channel` 那条记忆）。

净结论（同日两版之后定稿，**分两维，别再混**）：
- **本地这一维**：`AppListEntry="none"` 的次级入口不挡打包、不挡注册、开始菜单不多磁贴（1.0.106 实物）；1.0.72 那次报的 80080204 真因是缺 `Executable`/`EntryPoint`。
- **商店这一维**：用户那句「无头应用不能上架」**基本成立** —— 次级入口带 `none` 会被包验收拒，除非账号已拿到 `HeadlessAppBypass` 豁免（T16/T17 两家一手，其中 T16 撞的就是"主入口可见＋次级想隐藏"这个与我们一模一样的形状）。
- 豁免是**账号级打标**：不在通用能力表里、不能写进清单、没有自助开关，但确实拿得到（NanaZip 带着两条隐藏入口上架 = 反证豁免可得，不是死路）。
