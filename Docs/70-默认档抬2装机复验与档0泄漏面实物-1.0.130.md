## 三、档 0 的泄漏面第一次有流量级实物（22:36:30–22:39:30，1.0.130）

窗口做法：`settings.txt` 末条追加 `ipv6=0`（备份 `D:\tmp\settings.bak-before-arm0leak`）→
`clashuwp-cli --force connect` → 读数 → `disconnect` → 删掉那条键回到"默认档生效"的状态
（`D:\tmp\settings.bak-before-restore-131`）。**这一轮顺带把 2→0 不重建常驻桥的形态
在真 v6 宿主上重看了一遍**：`bridge-start 复用常驻内核（排空 152 包，配置已变 → 尝试热重载）`，
且上一轮的 `SKIP_SYSTEM_IPV6_CHECK` 原值 1 被显式写回 0。

**路由层（这就是"绕过"本身）**：

| 判据 | 读数 |
| --- | --- |
| 隧道接口上的 v6 地址 | **0 条**（档 0 不下发，`v6in=[]`） |
| 指向 `ClashUWP` 的 v6 路由 | **0 条** |
| 默认 v6 路由 | `::/0 → WLAN ifi=22` |
| `Find-NetRoute` 三个全局 v6 目的地位 | `2400:3200::1`、`2606:4700:4700::1111`、`2001:4860:4860::8888` **全部 → WLAN ifi=22** |
| `ping -6` 拨号中 | 前两个地址各 **3/3、0% loss** |
| 内核活动连接里有没有它们 | `clashuwp-cli connections` 按 `2606:4700` 过滤 **0 条**（当时活动连接 29 条，v4 那批照常在里面） |
| v4 那一半仍在隧道里（负对照） | `curl -4 https://api.ipify.org` **200**，出口 `45.90.216.242`（节点出口，不是本机） |

⇒ **写死的 v6 字面量在档 0 下整条绕过隧道**：路由表、选路、连通、内核连接列表四项同向。
这条以前只是 Docs/05 §5 挂着的一条"未收口"，现在 closes。

**一处必须说出口的限定（否则这条结论会被读反）**：同一窗口里，Windows 解析器对
`api6.ipify.org`、`www.baidu.com` 的 AAAA 查询**四个 DNS 服务器全给空应答**——
`192.168.0.1`（路由器）、`240e:40:8000::10`（ISP 下发的真 v6 DNS）、`223.5.5.5`（隧道内）、
`114.114.114.114`，连 `Resolve-DnsName -Server` 指名也不例外；而 `nslookup -type=AAAA
www.baidu.com 114.114.114.114`（自带 DNS 客户端、不走 Windows 解析器）当场给出
`240e:83:205:1cd:0:ff:b0b8:dee9` 与 `240e:83:205:381:0:ff:b00f:96a2`。
原因在 NRPT：档 0 会话里仍有一条**根命名空间**规则（`ns=.`，名字 `VPN_00…ClashUWP_cb74…`），
DNS 被整条拽进隧道，而内核这一档不改写 `dns.ipv6`，订阅原文就是 `dns: ipv6: false` ⇒ 不答 AAAA。

⇒ 所以"档 0 在这条网络上域名那一半不泄漏"**不是 0 档给的保证**，是 NRPT + 这一份订阅的产物；
换一份带 `dns.ipv6: true` 的订阅，域名维度的 v6 也会照物理网卡走。
`LeakNote` 的播报口径因此只说"出站走物理网卡"这一层机制，不替用户保证"应用不会发 v6"
（写进 `RouteInclusion.LeakNote` 的注释，见 §五）。

诚实记录一条没跑通的：`curl -6 https://[2606:4700:4700::1111]/cdn-cgi/trace` 在这条直接通到
物理网卡的 v6 路径上 **rc=28、21 s 超时**，而同地址 ICMP 3/3 ⇒ TCP/TLS 那一层在这条路上
本来就不成（IP 字面量的 HTTPS 无 SNI/证书），所以泄漏的证据链是**选路 + ICMP + 内核列表里没有**，
不是"v6 HTTPS 跑赢了"。
