## 2. 测法：一条命令 + 三个判据

### 2.1 为什么不能直接 `connect`

`connect` 会真正拉起隧道 ⇒ 整机流量走 L3。
所以**必须有人在场、并且人在看着网络**的时候才发。

### 2.2 步骤

```bash
# ① 先看当前基线（纯读，不碰隧道）
clashuwp-cli logtail plugin 30

# ② 发那一枪（碰隧道，耗时可能 20~30 秒）
clashuwp-cli --timeout 60 connect

# ③ 立刻抓日志（纯读）
clashuwp-cli logtail plugin 80
```

**不要**在同一分钟里连发 `connect`。平台在拆旧会话时**直接换新进程重新 Connect，从不回调 Disconnect**
（这是本项目已确认的平台行为），连发会让两条会话叠在一起，读数全废。

### 2.3 判据一：`bridge-start` 这一组 tag 落在哪一档

`plugin.log` 里 `tag=bridge-start` 的行只有三种落点，对应 Docs/14 猜的两个根因：

| 看到的行 | 落点 | 含义 | 下一步 |
| --- | --- | --- | --- |
| `本进程首次启动桥 mtu=… drained=… mmdbDir=…` | **正常** | 走了首次启动路径 | 继续看第二行 |
| `clash_bridge_start 返回 rc=0 用时=…ms` | **正常** | Start 成功返回 | 桥起来了 |
| `mihomo bridge 已启动，回程泵运行中.` | **正常** | 数据面就绪 | 桥这一层没病 |
| `取 s_bridgeGate 锁超时 10s（上一会话的桥收尾/Stop 仍卡在 native P/Invoke）` | **根因 ①** | 上一会话收尾卡在 native 调用 | 端口无关，是 native 侧死锁 ⇒ 查 `clash_bridge_stop` |
| `clash_bridge_start 超时 20s（疑似卡死在 P/Invoke / hub.ApplyConfig / 9090 被上一进程占用）` | **根因 ②** | Start 撞死 | **端口冲突嫌疑** ⇒ 走"每进程唯一端口 + 前端发现" |
| `start 失败 rc=…: …` | **失败** | Start 返回非 0（配置解析/参数问题） | 看 `lastErr` 原文 |
| `KernelHome.Ensure 异常: …` / `退回包目录` | **前置失败** | LocalState 写不了，home 退回只读包目录 | **G2/G11/热重载三样都别开工** |

★ **`rc=0` 但用户仍然"连不上"** 是第三种可能：桥起来了、隧道装上了，但**排除路由或 DNS 不对**。
那就不是本轮要查的桥卡死，而是要回 Docs/08 / Docs/04 的隧道质量线。

### 2.4 判据二：会话事件汇

```bash
clashuwp-cli logtail sessions 40
```

看 `dataface-sessions.txt` 那一列。**要确认的形状**：

- 有 `evt=connect-begin` ⇒ 平台真的把连接请求交给了插件
- 有 `evt=start`（且不是"全新内核"以外的形态）⇒ 插件的 `Start` 走完了
- ★ **有没有 `evt=disconnect`**：Docs/14 那个"卡死"样本里，pid=8964 的 connect#2 **从头到尾没有 disconnect**，
  一直 hb 到 23:39:41 —— 那是"平台换新进程重连、旧会话没收到 Disconnect"的形状
- ★ **重拨计数**：连续出现两次以上 `connect-begin` ⇒ 平台在自动重拨，
  那是另一个问题（`HealthMonitor` 的哨兵按设计会拆掉它）

### 2.5 判据三：内核控制器的真实读数

```bash
clashuwp-cli controller     # 探 127.0.0.1:9090 能不能应答
clashuwp-cli status        # 读 mode / log-level / interface-name
clashuwp-cli groups        # 列可切换组
```

`controller` 这一条是 Docs/12 §8 里挂了很久的那条：
**我们那颗桥内 mihomo 的行为到底与官方 v1.19.32 是否一致**，全靠它。
如果 `controller` 应答，`groups` 的返回形状就能拿来跟 Docs/12 §7.1 钉死的那份对照。

### 2.6 收工判据（三条，缺一不可）

1. **没有自动重拨** —— `sessions` 里 `connect-begin` 只出现一次
2. **`nrpt=0`** —— 名字解析仍走系统，别让隧道把 DNS 吞掉
3. **死接口路由 = 0** —— 没有指向已消失网卡的路由

三条任一不满足 ⇒ **立刻 `clashuwp-cli disconnect`**。

### 4.1 判据一：`bridge-start` 三行全在正常档


⇒ **既没有"取 s_bridgeGate 锁超时 10s"，也没有"clash_bridge_start 超时 20s"。**
Docs/14 §"端口冲突的正解"那条线**本轮不成立** —— 端口冲突与取锁卡死这两个假设都没被触发。
**但注意这不等于它们被否证**：本轮是"干净起点"（9090 无占用、无残留进程），
而 Docs/14 那个样本是"上一会话还热着就换进程重连"的形状。
**要证伪它们得专门造那个场景**（连上 → 不拔网线 → 强杀主应用 → 立刻重连），本轮没造。

### 4.4 判据二的一个坑（记下来免得下次误判）

`dataface-plugin.txt` **是会话结束时才落盘的**，不是周期写。
本轮 17:03:11 去读它时读到的还是 10-17 23:33 的旧文件，一度以为"插件侧快照没更新、1.0.46/47 引入了回归"。
**17:03:25 断开后重读，时间戳与内容才是本轮的。**
⇒ 读这个快照的时机必须是**会话结束后**；会话进行中要读实时的读 `watchdog.txt`（每 25 秒刷一次）。

### 4.5 NRPT 判据的口径澄清

连接中确实有一条 NRPT 规则：`Name=VPN_00 0ClashUWP_1fef4881-…`，`Namespace={.}`，`NameServers={223.5.5.5, 119.29.29.29}`。
**它不是孤儿残留** —— `ClashVpnPlugin.cs:2621` 明确是"对齐安卓版 DNS 收进内核"，`dnsInTunnel=1` 时用根后缀 `.` 下发，
名字带 `ClashUWP_` 前缀是**平台为当前会话装的**。
Docs/07 §2 那条 `NRPT 条数=0` 是**拆连接之后**的判据（"profile 已删但 NRPT 还在"才是孤儿）。
本轮断开后复查：**条数=0** ⇒ 平台随会话把它收走了，**没有留下孤儿**。这一条恰好也是"收尾闸干净"的证据。

   要专门造"上一会话还热着就换进程重连"（连上 → 强杀主应用 → 立刻重连）才能验。

3. **T1 的 post-start 分支**没被触发（本轮桥一次就起来了，没有 FailFast）。
4. **G2 选节点的持久化**（`cache.db` 跨进程重开）本轮没测 —— `groups` 只读不写选择。
