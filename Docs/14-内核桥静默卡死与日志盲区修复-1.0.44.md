# 14 · 内核桥"静默卡死"与日志盲区修复（1.0.44）

## 背景：一次被误读的"连不上"

用户报 1.0.38 连不上。第一直觉是"内核没起来"——因为 `plugin.log` 里 `kernel-home home=LocalState…` 之后一片安静，既没有"mihomo bridge 已启动"，也没有"start 失败"。

但读**数据面文件**（不是 plugin.log）后，这个判断被推翻：

- `watchdog.txt` / `dataface-sessions.txt`：pid=6020 有一次 `alive=960s encap=73084 inj=105057` 的 16 分钟健康会话；pid=8964 connect#2 `内核=OK:1.10.0`（REST 9090 有应答）、`fake-ip=OK:198.18.0.9`。
- `dataface-plugin.txt`：`inj=17618 / EchoReplies=0` —— 注入的是内核回的真包，不是假 echo。

⇒ **内核本身跑得好好的。** "安静"是个假象。

## 根因一：日志盲区（把我一开始带偏的元凶）

桥的生命周期三行日志（"已启动"/"start 失败 rc=…"/"启动异常"）过去**只走 `channel.LogDiagnosticMessage`**（发给平台，不进 RollingLog）。而 `KernelHome.Ensure()` 走的是 `RollingLog.Info("kernel-home", …)`。于是 plugin.log 里 kernel-home 之后必然什么都不剩——不是没跑，是没记。

## 根因二（疑似）：跨进程抢桥 / 卡死，且无记录

唯一真异常是**重启应用后那一次**：pid=8964 的 connect#2 从来没有 `evt=disconnect`（一直 hb 到 23:39:41），紧接着 pid=3196 新进程 `全新内核`、`evt=start` 之后**彻底静默**（无 disconnect、无 hb）。

结合平台行为（见项目记忆：OS 拆通道时直接换新进程重新 Connect，从不回调 Disconnect），最像两种卡死：

1. **取锁卡死**：上一会话的 `Disconnect` 在 `lock(s_bridgeGate)` 内做 `clash_bridge_stop` / `BoundInterface` 的 native 调用没返回 → 新进程 `StartMihomoBridge` 卡在取锁。
2. **Start 卡死**：旧进程残留的常驻桥还占着 `127.0.0.1:9090`（配置里 `external-controller: 127.0.0.1:9090`），新进程 `clash_bridge_start → hub.ApplyConfig` 撞端口卡死。

两种都会把 Connect 线程**永久 wedge**，而且因为根因一，日志里什么都不留。

## 1.0.44 改了什么

文件：`ClashUWP.Vpn/ClashVpnPlugin.cs` 的 `StartMihomoBridge`。

1. **补日志**：桥的每个分支（首次启动 begin、Start 返回 rc+用时、复用常驻、start 失败、启动成功、Ensure 异常、整体异常）都写一条 `RollingLog`，tag=`bridge-start`。盲区关闭。
2. **取锁超时**：`lock` 改 `Monitor.TryEnter(s_bridgeGate, 10s)`；拿不到 → 记"取锁超时（上一会话收尾卡在 native）"→ failFast 抛。
3. **Start 超时**：`clash_bridge_start` 丢到 `Task.Run` 并 `Wait(20s)`；超时 → 记"Start 超时（疑似卡死在 P/Invoke / hub.ApplyConfig / 9090 被上一进程占用）"→ failFast 抛。
4. **整体 try/catch + finally**：任何异常都进 RollingLog 后再按 failFast 决定 rethrow；`finally` 里按 `lockTaken` 释放锁。

效果：把"静默永久卡死"变成"有记录的失败 + failFast 拆连接、物理网卡立刻恢复"。代价：超时的 native 调用线程被弃用（它不持锁，弃用不影响锁）。

## 仍未闭合的

- **端口冲突的正解没做**：让旧进程释放 9090，或把 external-controller 改成每进程唯一端口 + 前端发现。这需要**先部署带修复的包、复现一次**，看日志到底是"取锁超时"还是"Start 超时"，再对症下药——现在做属于没验证的臆测。
- Go 侧 `hub.ApplyConfig` 前后加的两行 `log.Infoln` 已回退：mihomo logger 在桥模式下不外显，且要重编 112MB 的 clash_bridge.dll，是半截活。

## 部署实况（2026-10-18 16:55）：1.0.47 上机成功

把 1.0.45 → 1.0.47 这一步补上，同一条路径复跑一遍，这次把**每次装包都该做的自检**固定下来（前三轮的判据都靠临时想起来）。

**装机前（只读，`.local/` 不落盘也不入库）**：

1. `Get-AppxPackage *421769c5*` → `Status` 不是 `DeploymentInProgress` 才继续。队列被孤儿 Remove 占死过一次（Docs/13 §6.1），那次的形状是状态旗标一直挂着。
2. 组件一致性（Docs/09 §13.3 那条自检，机器可验）：
   `sha256(组件 bin/Release) == sha256(~/.nuget/packages/clashuwp.vpn/1.0.27/lib/…/ClashUWP.Vpn.dll) == sha256(前台 bin/x64/Release/…/ClashUWP.Vpn.dll)`，三处同为 `30ca6562…`；
   且**缓存份 mtime（07:34:06）≥ 源码最新 mtime（07:21:19）** —— 后半条才是治同版本号 repack 不刷新缓存的那条。
3. `Get-AuthenticodeSignature` → `Status=Valid` / `CN=gold`。
4. `tr -d '\0' < publish/ClashUWP.dll | grep -c <串>` 取证关键串各命中 ≥1（`kernel-home` / `LocalState` / `hot-reload` / `bridge-start` / `cache.db`）。

**装机**：`Start-Process <msix>` → 等 `AppInstaller.exe` 起（**别去 `list-windows` 里找 Microsoft Store 窗口**，这一版系统弹的是 Store 的下载页，`AppInstaller` 是另一个进程，用 `list-windows -a AppInstaller` 才抓得到）→ `inspect -a AppInstaller` 读页面：

- `appName` = "更新 ClashUWP?"、`appPublisher` = "发布者: gold"、`appVersion` = "版本: 1.0.47.0"、`appSource` 指向本项目 AppPackages
- **主按钮文案是 `primaryButton` "更新" 而不是"安装"** ⇒ 系统认定这是升级，走 Add 路径，不删 LocalState。**这行文案是"会不会丢 LocalState"的唯一提前判据**，比点完再看强。
- `launchWhenReadyCheckbox` 默认 on —— 装完会自动拉起主应用，`Diagnostics.MaybeRunProbesAsync` 那条启动路会跑一遍（默认跳过，除非 `settings.txt` 写了 `autoProbe=1`）。
