## 2. G9 按应用分流：为什么不走平台 traffic filter

这一步是**先否掉一条看起来最"正统"的路**，再走另一条。不写下来，下一轮一定会重走。

平台侧原语我们确实有，而且 1.0.21 就接过一次（`settings.txt: selfSplitTunnel` 0/1/2）。
两次独立实测把它判死了，判据是同一个形状：

- 先遣项目 docs/76 的 tfmode 三臂：**空 assignment** ⇒ 数据面**默认 deny**（GenFail=23，只有装 filter 前那一瞬间溜过 1 个包）；`Allow*=true` ⇒ `reqSeen=0`；只有**传 null** 才是"全部进隧道"的正常形态（`reqSeen=24`）。
- 我们自己的 run 19（Docs/08 §5.2）：filter 列表**非空**的两臂 `Encapsulated` 从数千掉到 **17**、`Injected=0`，宿主所有应用 20~30 ms **本地瞬败**，连本包的 `127.0.0.1:9090` 回路都变成"积极拒绝"。

合起来一句：**assignment 一非空，平台就把"没匹配上 filter 的应用"按 deny 处理，而不是"照旧进隧道"**。
而官方文档在这里是空的 —— `VpnTrafficFilterAssignment` 的 `AllowInbound/AllowOutbound` 只有
"Gets or sets whether … is allowed or not" 一句，`VpnRoutingPolicyType` 也只有两个成员、
没说不匹配时怎么走。⇒ 想表达"这几个应用例外、其余照常"，在 traffic filter 这条路上要付**整机断网**的代价。

于是改走**内核规则层**：流量照常全部进隧道，由 mihomo 在规则匹配阶段按"这条连接是谁发的"决定去向。

### 2.1 内核那三步是怎么反查进程的（照 pin 住的源码读，不是记忆）

`go.mod` pin 的是 `github.com/metacubex/mihomo v1.19.32`，本机 `%GOROOT%` 包缓存里有全量源码，逐行对过：

| 步骤 | 位置（v1.19.32） | 内容 |
|---|---|---|
| 常量 | `component/process/process_windows.go:16-20` | `tcpTableFunc="GetExtendedTcpTable"`、`tcpTablePidConn=4`、`udpTableFunc="GetExtendedUdpTable"`、`queryProcNameFunc="QueryFullProcessImageNameW"`（后两个函数名走 `GetProcAddress`，不是静态导入） |
| 取表 + 查行 | `:63-101` `findProcessName` | `AF_INET`/`AF_INET6` 按地址族选，TCP 用 class 4；`getTransportTable` 拿整张表，`newSearcher(family==AF_INET, network==TCP)` 按 **(本地地址, 本地端口)** 找 pid ⇒ TCP 那一臂**要求本地 IP 精确相等**，UDP 只看端口 |
| pid → 名字/路径 | `:200-229` `getExecPathFromPID` | `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)`（`:210`）+ `QueryFullProcessImageNameW`，缓冲区 `syscall.MAX_LONG_PATH`（32768，`:216`）；pid 0/4 走保留名 `:System Idle Process` / `:System` |
| 初始化失败时 | `:64-71` | `once.Do(initWin32API)` 里 `GetProcAddress` 失败会打 `All PROCESS-NAMES rules will be skipped` —— 内核自己是**降级跳过**，不是崩 |

规则类型是 `PROCESS-NAME` / `PROCESS-PATH`（`rules/common/process.go`：**整串大小写不敏感相等比较**，
没有"竖线并列多个应用"的写法 ⇒ 一条名单 = 一行规则）。本名单**不用** `-REGEX` / `-WILDCARD`：
`component/wildcard/wildcard.go` 的 `*` 会匹配到空串，而"没查到进程"恰恰就是空串 ——
那是个把"查不到"误判成"命中"的坑。

`find-process-mode` 默认 `strict`：只在真撞上 PROCESS 规则时才查、每连接一次。
⇒ **名单为空时，内核行为与本批改动之前逐字相同**（这条是"默认无副作用"的机制依据）。
查不到进程 ⇒ `metadata.Process` 是空串 ⇒ 与任何 pattern 都不相等 ⇒ 不命中 ⇒ 走订阅原有规则 ——
**失败落在安全的一侧**，但代价是"配了没生效也不报错"，所以 §5 的前端把注入结果读回来显示。

### 2.2 与安卓的差别（如实写）

安卓在 `TunService.kt:84-96` 用 `addAllowedApplication`/`addDisallowedApplication` 把应用
**整个排除在隧道之外**；我们是在**已进隧道的流量**上按进程判，命中 `DIRECT` 由内核自己
从物理网卡发出去（`interface-name` 绑定那条路，Docs/09）。用户看到的结果一样
"这个应用走直连"，机制不同，而且这条机制**不碰 VPN 会话的建立**。

### 2.3 为什么去向只收 `DIRECT` / `REJECT`

`config/config.go` 的 `parseRules` 会校验规则 target 必须存在于 proxies，
**一条不存在的组名会让整份配置解析失败**。这不是理论，本批实测了两次（同一颗二进制，
`C:\Program Files\Clash Verge\verge-mihomo.exe -v` = **`Mihomo Meta v1.19.32 windows amd64 with go1.26.8`**
⇒ 与我们 pin 的版本**逐字相同**，不是"差不多的一版"）：

```
# 正例：注入后的真实订阅配置（574 → 577 行）
verge-mihomo -t -d .local/kcfg-harness/ktest
  → configuration file … config.yaml test is successful

# 负例：把去向换成一个不存在的组名
rules:
  - 'PROCESS-NAME,chrome.exe,不存在的组'
  → level=error msg="rules[0] [PROCESS-NAME,chrome.exe,不存在的组] error: proxy [不存在的组] not found"
  → configuration file … test failed
```

解析失败 ⇒ 桥 `start rc=-2` ⇒ `failFast` 放弃连接。不是黑洞，但**"改个名单就连不上"不能留给用户**，
而组名会随订阅变（换一份订阅，"星链机场"可能就没了）。⇒ "强制走某个组"这一档
必须等有组名校验之后再做；`DIRECT` / `REJECT` 是内核内建、恒存在，恰好覆盖"旁路"和"屏蔽"两个真实需求。

## 3. G9 的实现：名单 → 注入 → 读取点

### 3.1 名单文件

`LocalState\split-apps.txt`，一行一条 `kind|标识|去向`，`#` 开头是注释，上限 100 条。
★ **故意不混进 `settings.txt`**：那个文件是 15 个实验把手（现在 16 个，见 §4）的入口、
是取证通道的命门，写坏一行等于一整批实验臂失效（Docs/19 §6 同一条纪律）。

字符闸门 `AppSplit.IsSafeToken`（`ClashUWP.Vpn/AppSplit.cs:225`）拒绝
`|`（拆行符）、`,`（mihomo 规则分隔符）、`'`（我们生成的 YAML 用单引号包住整条规则）、
控制字符与换行，长度上限 260。

模型与解析器**只有一份**，在组件里并且是 `public`（`AppSplit.cs`）：前台与插件读同一个文件，
必须读出同一个结果 —— 两边各写一份解析器就是给自己留第二套真值表。
★ 三个成员刻意写成 **static 属性而不是 `const`**（`FileName:87`、`MaxRules:91`、`AllowedTargets:100`）：
`const` 是编译期内联字面量、**不穿过 CsWinRT 投影**，前台拿不到同一个文件名常量；
`AllowedTargets` 的类型是 `IList<string>` 而不是 `string[]`，因为 WinRT 元数据里**没有"字段"**，
数组成员投影出来必须是 `IVector`。

### 3.2 注入：`KernelConfig.Transform` 现在做四件事

签名从 1-arg 变成 3-arg（`KernelConfig.cs:80`）：

```csharp
internal static string Transform(string yaml, AppSplit? split, out string splitNote)
```

`dns` 块 / `tun` 块 / `url-test` 容忍度三项是原有的，第四项是新的 `InjectAppSplitRules`（`:402`）。
做法是**纯文本行操作**，不引 YAML 库：找到顶层 `rules:` → 取第一条 `- ` 子项的缩进 →
把名单**倒序插到同一位置**（`List.Insert` 会把先插的下推，倒序插入 = 正序排在订阅规则之前）→
每行拼成 `    - 'PROCESS-NAME,chrome.exe,DIRECT'`。

★ 单参数版 `Transform(string)` **删掉了**，不是留着"兼容"：留着就会有第三个调用点漏传名单，
而漏传的表现是**静默不注入**。两个读取点都必须显式交名单（Docs/12 §9.4 的"单源"约定）。

三种"不注入"各有明确文案，全部回给调用方（`:414`/`:419`/`:436`，句式在 `DescribeSkip:461`）：
配置里没有 `rules:` 块 / `rules` 是行内流式写法 / `rules` 块里没有任何条目。
外加两条前置回落：JSON 兜底配置不注入（`:93`）、改写异常退回原文（`:114`）。

### 3.3 两个读取点

| 时机 | 位置 | 进程 | 证据行 |
|---|---|---|---|
| 每次连接（步 4.1） | `ClashVpnPlugin.cs:450-463` | vpnClient 后台 | `plugin.log` 的 `channel=config 应用分流=…` + 快照 `dataface-plugin.txt` 的 `AppSplit=…`（`:1757`） |
| 每次热重载 | `SubscriptionReload.cs:46-47` | **前台** | `app.log` 的 `channel=config 热重载配置已重生成 应用分流=…` |

⇒ **改完名单不是只能靠断开重连**：点「订阅 → 重新加载配置」也会重新生成并注入。
（这条最初在界面文案里被我写成"必须重连"，是错的 —— 组件与界面上的文案都已改过来，
`AppSplitStore.SaveAsync:118` 那句就是判据。）

★ 与 `fakeIp` 总闸的**耦合写进代码**：`KernelConfig.Transform` 整体只在 `LocalSettings.FakeIp` 为真时进，
所以 `fakeIp=0` 时名单也不会注入，`splitNote` 直接给
`"fakeIp=0 → 整份改写关闭，名单未注入"`（`ClashVpnPlugin.cs:453-460`）。
把耦合说明白，是为了让它别变成"未知原因失效"。

## 4. G5 会话重置：只做"重置"那一半，"挂起"明说没做

### 4.1 三个端点，照源码钉死

新文件 `ClashUWP.Vpn/SessionReset.cs`。控制器基址收敛成一个常量
`ControllerBase = "http://127.0.0.1:9090"`（`:50`），`TryHotReload` 原先写死的同一个地址改成读它
（`ClashVpnPlugin.cs:2109`）⇒ 换端口只改一处。

| 端点 | 源码位置 | 语义 | 返回 |
|---|---|---|---|
| `DELETE /connections` | `hub/route/connections.go:16-20` + `:81-87` | `closeAllConnections` 遍历 `statistic.DefaultManager` 逐个 `c.Close()` | 恒 **204** |
| `POST /cache/dns/flush` | `hub/route/cache.go:12-15` | 清 DNS 缓存 | **204** |
| `POST /cache/fakeip/flush` | 同上 | `resolver.FlushFakeIP()` —— **整个池重置**（`component/fakeip/pool.go`：`cycle=false`、`offset=p.first.Prev()`） | 恒 **204** |

★ 两条读法上的坑都写进了类注释：
① 前缀来自 `hub/route/server.go:132,135` 的 `r.Mount("/connections"/"/cache")`，
且 flush 是 **POST**（GET 会 405）；
② **不能把 204 读成"清掉了"** —— `component/resolver/enhancer.go:73-78` 在
`DefaultHostMapper == nil`（redir-host）时返回 `nil`，于是也是 204。
204 只证明"控制器活着、端点在"。

执行顺序固定 `conns → dns → fakeip`（越靠后越不可逆：fake-ip 池是落盘的），
单个端点失败**不中断其余两个** —— 这条链的产出是"哪些端点通了"的证据，不是必须原子的操作
（`SessionReset.cs:91-102`、`:126`）。

### 4.2 三档，默认 0

`settings.txt: sessionReset=0|1|2`（`LocalSettings.cs:398` 字段、`:425` 恢复默认、`:459` 钳位 0..2、
`:479` 进那条"本次真正生效"的证据行）：

- `0`（默认）= 什么都不做，`Run()` 一次判断就返回，不产生任何 HTTP。
- `1` = `DELETE /connections` + `POST /cache/dns/flush`。
- `2` = 再加 `POST /cache/fakeip/flush`。

★ **默认必须是 0**，两个前提都没验过（口径同 `ReceiveBatch` 的档 0：没有实测证据之前不改产品默认）：
① 控制器在**包内**是否真可达仍未确认（Docs/12 §8：宿主侧 `netstat` 看得见 `127.0.0.1:9090 LISTENING`，
但包外 curl 超时 = AppContainer 回环隔离）—— 热重载早就踩在同一前提上，可它的成败只有返回码能说明；
② `fakeip/flush` 会把在途连接的"域名↔假 IP"映射连着池一起清掉，时机不对就是自己制造一次短暂无响应。
⇒ 判据在 `plugin.log` 的 `channel=session-reset` 那一行：**三个码都是 204 才算成立**，
出现 `连接失败`/异常类型名就是前提 ① 不成立。

两个调用点：

- 会话开始：`ClashVpnPlugin.cs:1990`，紧跟 `s_lastConfigFingerprint = Fingerprint(config)` 之后，
  自带 **1.5 s 延迟** —— 先清再热重载等于白清（`PUT /configs?force=true` 会重建配置）。
- 会话结束：`ClashVpnPlugin.cs:1691`，在收尾锁块把 `s_bridgeGlobal` 置假**之前**
  （它读的就是那个门闩 `BridgeRunningForReset`，`:75`）。

两处都是 **fire-and-forget**：`Connect`/`Disconnect` 是平台同步回调，在里面等 HTTP
就是把网络延迟挂到平台状态机上（同 `TryHotReload` 的理由）；而 `Disconnect` 之后进程随时可能被挂起
⇒ 会话结束那一臂本来就是尽力而为，**真正保证"干净起点"的是会话开始那一臂**。
会话结束那一臂还有 `BridgeRunningForReset` 这道门：内核从没起来的轮次不该留下三条无意义的失败码，把证据搅浑。

### 4.3 "挂起"为什么没做 —— 这条是**未修**，不是半截修

mihomo 的挂起入口是 golang bind 直调的 `Clash.suspendCore(...)`（安卓
`SuspendModule.kt:17,28,34` 按亮灭屏用它）。我们：

- 桥 ABI 只有 `start/stop/put_packet/get_packet/last_error/bound_iface`（`MihomoBridge.cs:31-52`），**没有 suspend**；
- REST 侧也没有对应端点；
- 要加就得改 Go 重编 `clash_bridge.dll` —— 本机没有 Go 工具链，而**装工具链属于改用户机器**，
  Docs/12 §5 第 12 项明确"未获同意不动"；
- 唯一"看起来能挂起"的 `POST /restart` 是**地雷**：它重新 spawn 进程，而我们的内核就跑在
  承载隧道的 vpnClient 进程里，调它等于把数据面和平台通道一起掀掉。
  ⇒ 本仓库任何入口都不得调用它（`SessionReset.cs:33-35` 与 `LocalSettings` 注释各写了一遍）。

⇒ 本批交付的是"重置"这一半，"挂起"保持 Docs/12 里的**阻塞状态**，没有伪装成已完成。

## 5. 前端：设置页区块 + 能力探针

### 5.1 设置页「应用分流」（`MainComponent.cs:448-476`，插在「背景材质」与「诊断」之间）

一条名单一行，带独立「删除」；下面依次是 kind/target 四个选择按钮
（`▶` 标当前档，沿用 `MaterialPicker` 的写法）、标识输入框 + 「添加」、
「保存名单 / 重新读取 / 探测进程可见性」、消息行、**「上次连接实际注入：…」读回行**、
生效时机提示、traffic filter 判死的那句警告。

两个设计决定：

- ★ **状态里存的是规范化后的行数组**，不是 `AppSplit` 对象（`MainComponent.cs:112-124`）：
  增删都换一个**新 List** 交给 `UseState` —— 把同一个 List 原地改了再 set 回去，
  引用相等，很可能一次重渲染都不触发。
- ★ **保存只回读、不猜**：`AppSplitStore.SaveAsync` 返回的是"重新解析后的结果"（含被挡掉的行），
  而不是"写成功了"；界面把它原样显示。`AddSplitRule` 用**同一个解析器**做校验
  （`MainComponent.cs:758`），判据与实际注入的完全相同 —— 否则界面放过、插件丢掉，
  就成了"存下了但内核不认"。
- 「上次连接实际注入」取的是 `dataface-plugin.txt` 的 `AppSplit=` 行（`AppSplitStore.cs:71`）。
  这个功能最坏的失败形态是"界面存下了、内核配置里没那几行"（`rules` 块缺失 / 行内写法 / `fakeIp=0`），
  **三条都是静默路径**，所以把插件写下来的注入结果读回界面，用户才分得清"我没写"和"写了但没进去"。
  取不到就明说 `(没有记录：本机还没用这个版本连过一次)`，不猜。

★ 踩到一个现成的坑并修了：`LocalState.ReadIfExistsAsync` 的"缺文件"回落值是字面量
`"(无结果文件)"`（`LocalState.cs:85`），把它当文件内容送进解析器会得到一条
`字段数不是 3：(无结果文件)` 的**假拒绝行** —— 全新装包本该是干净的空名单。
⇒ `AppSplitStore` 的读与回读都改成 `TryGetFileAsync` + 缺文件即真空串（`AppSplitStore.cs:37`、`:95`）。

### 5.2 只读能力探针（`ClashUWP/Backend/ProcessLookupProbe.cs`）

回答 Docs/12 §5 第 11 项留给 G9 的前置问题：**"在我们的沙箱里，能不能按连接拿到别的可执行路径？"**
三步全部照内核将要走的那条 API 写，一步比一步更接近失败点：

1. `Process.GetProcesses()` —— 能不能看见别的进程、能不能读到名字（回样本前 60 字符）；
2. `iphlpapi!GetExtendedTcpTable(class=4, AF_INET)` —— **只读表头那个行数 DWORD**，
   不解析行（行结构的字段偏移在 x64/arm64 上不同，而这个探针要回答的是"给不给结果"，
   解析由内核自己做）；rc=122（缓冲区不足）也算"调用可达"；
3. ≤12 个 pid 走 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageNameW`，
   回 `成功 N / 被拒 M(err=) / 样例路径` + 一句判读：
   `⇒ PROCESS-NAME/PROCESS-PATH 有戏` 或 `⇒ 读不到别人进程的路径，规则层会静默不命中`。

边界写进类注释：它跑在**前台进程**，与插件同包同 family 同 capability，所以是**旁证**
不是插件进程内的直接证据；最终判据仍是"设一条名单，看那个应用的行为变不变"。
全程只读（不发请求、不动路由、不碰会话、不开监听），★ **不自动跑**，由那个按钮点出来
（口径同 `AppSettings.AutoProbe`）。

★★ 这一节顺带学到一条 AOT 教训，值得单独记：**主工程开了 `DisableRuntimeMarshalling`
（`ClashUWP.csproj:15`），`DllImport` 就不能用了**。
`SetLastError=true`、`ref` 参数、`StringBuilder` 参数全靠运行时封送，
编译器只给 `CA1420` **警告** —— 第一次构建是那 5 条警告**和两个真正的 CS 错误混在一起**报出来的，
所以很容易被当成"顺手修掉错误就绿了"，而那 5 条警告代表的东西在 AOT 里是运行时要炸的。
改成源生成的 `LibraryImport` 后立刻露出真约束：`SYSLIB1051` 是**错误** ——
bool 返回值必须写明封送（`[return: MarshalAs(UnmanagedType.Bool)]`），
而缓冲区直接用 blittable 的 `uint[]` / `char[]`（生成固定指针，不复制、不用 unsafe）。
⇒ 本包以后加 P/Invoke，一律 `LibraryImport`；探针的路径缓冲是 520 字符（2×MAX_PATH），
**比内核自己用的 32768 短**，判读时别把"探针截断"当成"读不到"。

## 6. 离线验证结果（本批唯一已成立的验证）

工具：`.local/kcfg-harness/`（gitignored）—— 一个 net10.0 控制台，用 `<Compile Include>`
把 `AppSplit.cs` + `KernelConfig.cs` 编进去，直接对**真订阅配置**跑 `Transform`。
这样测的是**生产代码本身**，不是"我另写了一份一模一样的"。

```
parsed=3 rejected=4 empty=False
  REJ: 去向只认 DIRECT / REJECT（写组名会让整份配置解析失败）：name|nothaha.exe|星链机场
  REJ: 字段数不是 3（应为 kind|标识|去向）：bad line without pipes
  REJ: 标识非法（空 / 含 | , ' 或超长）：name||DIRECT
  REJ: 标识非法（空 / 含 | , ' 或超长）：name|has'quote.exe|DIRECT
note=注入 3 条（PROCESS-NAME×2, PROCESS-PATH×1），畸形 4 行已忽略
noteEmpty=无名单，rules 未动
--- 注入后的 rules 头部 ---
  53: rules:
  54:     - 'PROCESS-NAME,chrome.exe,DIRECT'
  55:     - 'PROCESS-PATH,C:\Program Files\Mozilla Firefox\firefox.exe,DIRECT'
  56:     - 'PROCESS-NAME,Discord.exe,REJECT'
  57:     - 'DOMAIN,starlink.aliyundeepsearch.sbs,DIRECT'   ← 订阅原有规则，从这里开始被推下去

首个差异行 54   roundTrip=3 条, 一致=True
```

四个结论：**位置对**（注入的 3 行排在订阅所有规则之前，mihomo 是首条命中即停）、

**往返对**（`Parse → ToText → Parse` 稳定，界面显示的就是会注入的）。

`-t` 那次会顺带下一份 GeoIP MMDB（`Can't find MMDB, start download`，几 MB、一次性），

## 7. 上机验收清单（每条都给判据，不做 = 未验证）

G9 · 应用分流

1. 设置页出现「应用分流」区块，且名单为空时那行写 `(名单为空 —— 内核配置不会被改动)`。
2. 点「探测进程可见性」：三步各回一行。**第 ③ 步是关键** ——
   `成功 0` 就说明规则层会静默不命中，此时第 3~6 条全部不用做，先回去改机制。
3. 加一条 `name | 一个正在用的进程名.exe | DIRECT`，保存 → 消息行回"已存 1 条…"。
4. 断开再连，看设置页读回行变成 `注入 1 条（PROCESS-NAME×1, …）`；
   `plugin.log` 里 `channel=config 应用分流=…` 同一句。
5. `GET /configs`（设置页「查看配置」）里 `rules` 头部**确实有那三行引号包住的 PROCESS 规则**。
6. 行为判据：那个应用的目标流量从**物理网卡**出去（`/connections` 里该连接的 `chains` 首项是 `DIRECT`）。
   ★ 只有"速度变快"不算证据，要看 chain。
7. 换成 `REJECT`：该应用连不上，且**其他应用不受影响**（这条是"没把整机一起拦掉"的反证）。
8. 名单为空时重连一次，`app.log`/`plugin.log` 出现 `无名单，rules 未动`，
   且 `config.kernel.yaml` 与改动前的旧版逐字相同（拿 `fc` 比一份留档）。

G5 · 会话重置

9. 默认（不写 `sessionReset`）连一次：`plugin.log` 里**不该出现** `channel=session-reset` 那一行
   —— 档 0 在 `Run()` 开头就返回，只写 `LastNote`、不发 HTTP、也不记日志；
   判据是 `dataface-plugin.txt` 的 `SessionReset=when=start 跳过（sessionReset=0）`。
   这一条同时确认"默认无副作用"成立。
10. 写 `sessionReset=1` 重连：`when=start arm=1 conns=204 dns=204 fakeip=skip`
    —— ★ **两个 204 才算控制器在包内可达**；这同时是热重载那条路的判据（Docs/12 §8 未决项）。
11. 写 `sessionReset=2` 重连：三个码都 204。出现 `连接失败`/`TaskException` ⇒ 前提 ① 不成立，
    本开关整体退回 0 并把结论写回 Docs/12 §8。
12. `settings.txt` 里加 `sessionReset=2` 之后，`plugin.log` 那条 `channel=settings` 的
    证据行必须出现 `sessionReset=2` —— 没有这行说明开关根本没读到（这条抓过 run 35 的老事故）。
13. 断开时看 `dataface-plugin.txt` 的 `SessionReset=…` 行：会话结束那一臂允许失败（尽力而为），
    但**行必须存在**，否则 `AtSessionEnd` 根本没被调用。

## 8. 明确没做 / 下一步

- **G5 的"挂起"半壁**：见 §4.3，阻塞在 Go 工具链授权上，不是工作量问题。
- **名单里指定走某个代理组**：需要先做组名校验（§2.3 的负例就是它的理由），本批只放 `DIRECT`/`REJECT`。
- **按包名（PFN）分流**：内核那三步读的是进程路径与名字，包装应用也能覆盖，
  但"UWP 进程的 `chrome.exe` 式名字"这一档怎么填（`ApplicationContainer` 里的实际镜像路径）没实测，
  等 §7 第 2 条的探针结果出来再定要不要加第三种 kind。
- **热重载后 `SessionReset` 不重跑**：热重载只重建配置，不清缓存。要不要在重载后再清一次是产品决定，
  本批没擅自加。
- 设置页那 15 个实验把手（`settings.txt`）仍未界面化（Docs/17 计划表里的独立一项）。
  本批新加的把手 `sessionReset` **也一样只有手改**：前台没有 `settings.txt` 的 writer，
  这条纪律没变。★ 本批**新出现的 writer 只有一个**，而且写的是另一个文件 ——
  `AppSplitStore.SaveAsync` 写 `split-apps.txt`（名单文件只归 G9 一个功能，
  写坏不会连坐一整批实验臂，理由见 §3.1）。
- 把手总数：`settings.txt` 现在 **16 个键**（原 15 + `sessionReset`），
  其中前台会读的仍是 `autoProbe` 那一个（`AppSettings`）。
- 没有新增 debug-cmd（碰隧道那条纪律），也没有把任何探测改成自动跑。
