## 一、结论：目录按「归属进程」划，不按「话题」划

```
ClashUWP/
  App.cs                    前台入口（含 in-proc AppService 调试通道）      仅前台
  Frontend/MainComponent.cs 界面：画状态 + 把用户意图转成一个后端动作          仅前台
  Backend/                  前台编排层 —— 23 个手写 .cs                     仅前台 23 · 两边都用 0
  Vpn/                      插件宿主 + 共享层 —— 21 个手写 .cs               仅插件 11 · 两边都用 10
```

全仓手写 `.cs` 共 **46** 个（`App.cs` 1 + `Frontend` 1 + `Backend` 23 + `Vpn` 21），
归属统计：**仅前台 25 · 仅插件 11 · 两边都用 10**。

三条判据（本批实测所得，非规范转述）：

1. **插件侧可达集完全封闭在 `Vpn\` 内**。以 `VpnBackgroundTask.cs` / `ClashVpnPlugin.cs` 为根的闭包
   共 21 个文件，全部落在 `Vpn\`；`Vpn\*.cs` 里出现的 `Backend.` 字样**只存在于注释与 `<see cref>`**，
   代码行零命中（本批复验命令见 §六）。⇒ 插件宿主不执行任何 `Backend\` 代码。
2. **前台反向吃进 `Vpn\` 共 12 个文件**（10 个「两边都用」+ `App.cs`/`MainComponent` 直接引用的
   `RollingLog`、`LocalSettings` 那类）。这是**单向依赖**，方向与 Docs/10 §2 那句
   `Frontend → Backend → Vpn/platform` 一致，只是当时 `Vpn\` 同时被当成了「平台 API 层」和「插件工程」，
   两个含义挤在一个目录名里 —— **这就是这次要修的根**。
3. **同一程序集内不需要任何跨工程授权**。1.0.76 合并工程后前台与插件同属 `ClashUWP.dll`，
   `internal` 天然互相可见；全仓 `rg InternalsVisibleTo` 命中 **0 处**（Docs/10 §1 第二条与
   `Vpn\GracefulTeardown.cs` 旧注释里那句「靠 AssemblyInfo.cs 的 InternalsVisibleTo」都是两工程时代的写法，
   本批已订正）。

## 二、`Vpn\` 里「两边都用」的 10 个文件凭什么留下

共享层不是垃圾桶。准入条件只有两条，**必须同时满足**：

- **(a) 无可变状态**（纯函数/只读常量），或者
- **(b) 它那个可变状态本身就是跨进程契约的一部分**（不是缓存，是协议）。

| 文件 | 满足 | 为什么必须两边共用 |
|---|---|---|
| `Vpn\KernelConfig.cs` | (a) | 内核配置 transform 的**单源**。插件连接时（`ClashVpnPlugin` 步 4.1）与前台热重载时（`Backend\SubscriptionReload.cs`）必须产出**逐字相同**的 `config.kernel.yaml`；分两份就重演 run 24「热重载把 fake-ip 覆盖回 redir-host」的黑洞（Docs/08 §9）。仅 `[GeneratedRegex]` 源生成缓存，线程安全 |
| `Vpn\AppSplit.cs` | (a) | 应用分流名单是 transform 的**输入之一**，漏一路就等于静默不注入。`L88/92/101` 皆 `{ get; } =` 只读 |
| `Vpn\DnsConfig.cs` | (a) | 同上，DNS 覆盖口径单源（`L70/73/76` 只读） |
| `Vpn\PhysicalNetworkProbe.cs` | (a) | 「物理网络可达」这一把尺子前台哨兵与插件看门狗共用（`L57` 是 `static readonly` 数组） |
| `Vpn\SettingsParse.cs` | (a) | **本批新增**，见 §四 |
| `Vpn\GracefulTeardown.cs` | (b) | 「拆 VPN 不留孤儿 NRPT」的唯一一道闸（2026-10-16 00:21 整机断网事故换来的，见 Docs/08）。前台删除路径与插件看门狗**必须走同一份实现**，否则两条路两种拆法，残留判据无法归因 |
| `Vpn\ProfileStore.cs` | (b) | profile 存储 RPC 的**串行闸**：`L78 Agent`、`L80 Gate`、`L113 private static volatile string? _abandonedOp`（读 `L124`／写 `L169`／清 `L176`）。这条闸存在的理由就是「连接 RPC 在飞的同时枚举 profile 存储会抛 0x80070006」，**跨调用路径共享才有意义**（Docs/33 §三、Docs/45） |

## 三、状态归属三条规矩

1. **跨进程只能靠文件**。前台与插件是两个可能不同 pid 的宿主（形态与实测见 Docs/47 §六 P1–P5），
   唯一的通路是 `LocalState\`（`settings.txt` / `config.yaml` / `debug-cmd.txt` …）与平台侧的 profile。
   ⇒ **任何"前台改了插件立刻知道"的设计都不成立**，别再去凑共享静态。
2. **`Vpn\LocalSettings.cs` 的 21 个静态字段是两份缓存，不是一份状态**。
   每个进程调自己的 `Load()`，写自己的那份；同名的两个值**可以不同**（例如插件会话跑着的时候前台改了文件）。
   这是进程模型的结果，不是缺陷。真正会咬人的是**取值口径分叉**，所以解析收成了一份（§四）。
3. **只有 (b) 类可变状态允许跨调用路径共享**，且必须在字段注释里写清"为什么共享才是对的"
   —— 目前全仓就三处：`RollingLog._role`、`ProfileStore` 的闸、`GracefulTeardown` 的收尾序。
   新增第四处之前先回本文改这一条。

## 四、本批把「同一个文件两个解析器」收成了一份

改之前的形状：`Vpn\LocalSettings.cs` 里 `ReadString/ReadInt/ReadBool` 三个私有解析器，
`Backend\AppSettings.cs` 里一份 `ParseBool` + 一份行切分循环，**逐字相同**，
一致性靠 `AppSettings` 注释里那句「★ 布尔口径 —— 逐字照搬插件侧 `LocalSettings.ReadBool`」维系。
注释不能编译，分叉不会报警 —— 分叉的表现形式就是本文 §三 那条「前台以为开了、插件以为关了」。

改之后：新增 `Vpn\SettingsParse.cs`（namespace `ClashUWP.Vpn`，无状态纯函数），
`Parse()`（`L44`）/ `Bool()`（`L65`）/ `Int()`（`L81` 默认 0..2、`L85` 区间由调用方给）/ `String()`（`L97`）
成为唯一实现；两个读者各自只剩一行调用：

- `Vpn\LocalSettings.cs:563` → `var map = SettingsParse.Parse(text);`
- `Backend\AppSettings.cs:81/83` → `SettingsParse.Parse(text)` + `SettingsParse.Bool(map, "autoProbe", AutoProbe)`

★ **统一的是「文本→值」，没统一也没打算统一「怎么把文本读出来」**：
插件在 `Connect` 这个**同步** WinRT 回调里取值，只能同步等异步
（`LocalSettings.cs:557-559` 的 `AsTask().GetAwaiter().GetResult()`）；
前台的读取在 `MainComponent.Render()` 的渲染线程上点火，阻塞一次 WinRT 存储调用就是挂住渲染线程
（`AppSettings.cs:61 LoadAsync`，走 `LocalState.TryGetFileAsync` 全异步）。
这条缝是**对的**，保留；`AppSettings.cs:13-22` 类注释已按此订正。

回落纪律原样搬，一个字没改：缺键/空串/非数字/越界一律回落调用方给的 fallback；
整数区间由调用方给（`Docs/09 C5` 那个真缺陷换来的 —— 老实现硬编码 0..2，
`encapReturn=3` 被静默回落成 2，实验臂「看着切了其实没切」）。
