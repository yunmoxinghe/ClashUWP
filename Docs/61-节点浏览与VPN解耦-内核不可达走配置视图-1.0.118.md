# 61 · 节点浏览与 VPN 解耦：内核不可达时的"配置视图"（1.0.118）

任务书原文口径：**节点浏览属于代理客户端的管理功能，不应被错误地等同于 VPN 隧道已建立。**
本篇记的是这条判据在本工程第一次真正落地：改动全部从数据流与服务生命周期入手，没有一处是"只放宽 UI 可见性"。

---

## 一、根因（带代码位置）

代理页唯一的节点数据源是内核 REST。证据链三段，每一段都在改前实测读码确认：

1. **UI 只吃一个源**：`KernelView.LoadAsync`（`ClashUWP/Backend/Mihomo/KernelView.cs`）打
   `127.0.0.1:9090` 的 `/configs` `/proxies` `/connections` 三连；任何一段失败即
   `Snapshot.Failed(error)`，组表为空。代理页（`Frontend/MainComponent.cs` 的 `ProxyPage`）
   没有任何别的来源——**它不是"被 VPN 状态禁用了"，是根本没数据可画**。
2. **内核只在拨号链路里被起**：`ClashVpnPlugin.StartMihomoBridge`（`Vpn/ClashVpnPlugin.cs:932`，
   Connect 步 7）。插件宿主是独立进程（清单里的第二个入口 `VpnHost`），前台没有任何
   不拨 VPN 就能激活它的路径。
3. **于是"从未连接过" = REST 必 refused = 代理页只剩一句"(没有可切换的组)"**。
   而节点的**定义**本来就在磁盘上：`LocalState\config.yaml`（订阅原文），读它不需要内核、
   不需要隧道、不碰网络。

顺带查实的一条（避免重复劳动）：**"已断开+内核常驻"今天就是好的**——`residentBridge=1`
默认（Disconnect 不关内核，`ClashVpnPlugin.cs:2100-2123`），REST 活着，实时路径原样可用。
所以本批真正的靶心是"从未连接"与"内核不在"这两态。

## 二、改了什么

### 1. 新后端：配置视图 `Backend/Mihomo/ConfigNodeView.cs`（新文件）

- `LoadAsync` 读 `config.yaml`（**刻意读原文不读 kernel.yaml**，口径与 `SubscriptionView` 一致：
  kernel.yaml 被我们改写过，拿它当"订阅里的节点"会把改写误显示成订阅）。
- `Parse` 是纯函数，产出**同一套** `KernelView.Group/Member` 模型（Docs/48"不另立第二套数据"）：
  - 节点定义表 `name → type/server/port`（§4.1 要的详情字段；REST 的 `/proxies` 不返回
    server/port，只有配置文件里有）；
  - 组成员分类：嵌套组 / 内置策略 / 真节点 / 认不出的名如实列"未知节点"（不藏）；
  - `use:` 的提供方成 `Type="Provider"` 占位行 + Note（节点要内核运行时才拉，配置列不出，不猜）；
  - 组的"现值"只从 `selection.txt` 台账给**手动组**落（自动组的现值是运行态事实，配置里没有）。
- 行式判据**复用** `SubscriptionView` 的同一套段/列函数（`FindTopLevel` 等四条由 private 转
  internal）——两处数出来的条目必须一致，不许有第三套口径。顶层**键名**在本类额外认大小写
  不敏感（`Proxy-Groups:` 见过），**值一律原样**（Ordinal，emoji/空格纪律不变）。
- 每种"列不出"都有明确出口：兜底 JSON、空文件、纯节点无组、纯提供方、不认的 YAML 形态——
  全部回人话，绝不空白、绝不抛。

### 2. 回退接线：`KernelView.Snapshot` + 两个新字段

```
Snapshot(..., bool FromConfigFile = false, string ConfigNote = "")
```
`LoadAsync` 在 REST 失败那支改为回退到配置视图后返回：`Ok=false` **照旧**（绝不把"列出了组"
画成"内核在跑"），`Groups` 来自配置解析，`FromConfigFile/ConfigNote` 标来源。
`Member` 同样加默认值字段 `Server/Port`（只有配置视图填）。三秒轮询不用改——回退长在同一入口里。

### 3. 切换（§4.2 三情形）

- **A：内核在跑（含断开后常驻）**→ 实时 `PUT /proxies` + 回读，**行为一字未改**。
- **B：内核不可达** → `MainComponent.SelectAsync` 先探可达性，不可达走
  `ConfigNodeView.RecordPreset`：写 `selection.txt`（与实时切换成功后记的是**同一个**台账），
  内核下次可达由既有的 `MihomoController.ReplaySelectionsAsync` 回放生效。
  校验在写之前（组存在/手动组/成员在表里/提供方占位行拒收），文案如实：
  "记为预设、回放生效；本次没有改动内核，也没有发起 VPN 连接"——不是 UI-only 假成功。
- **C：启动/停止中** → 回环拒绝是瞬时的，回退落得快；卡在半死的 10 s 超时窗记为已知限制（§五）。

### 4. 测速（§4.4）

`HealthCheckAsync` 进门先探内核：不可达直接回"内核未运行：无法测速（测速走内核 REST，
不会为此发起 VPN 连接）"，不进"测速中"（那是"已在跑"的口径）；成员页头在 `!s.Ok` 时
把 ⚡ 按钮换成同话术的静态文本。**五档**：未测试（Delay=-1 不画）/ 测试中（actionHint）/
成功（>0 ms）/ 失败（0=本轮不通）/ 核心不可用（本批新增）。

### 5. UI 三态（§4.1/§六）

代理页顶部一条来源横幅：加载中（`(尚未查询)` 哨兵）/ 内核实时 / 配置视图（含"本地也没有
节点定义 → 先去订阅页拉取"的出口）。**没有**新增任何按 VPN 状态的隐藏或整页禁用；
VPN 状态变化不清空节点数据（快照本来就按来源各自渲染）。`MemberSubtitle` 在
`Server` 非空时补 ` · server:port`（配置视图行才有）。

### 6. §4.3 调查结论：订阅管理与 VPN **本来就已解耦**，未改动

`SubscriptionManager` 的拉取/更新走系统代理通道；`ActivateAsync` 是"先断开→后修改→再重连"
三段式（Docs/55），无会话时不拨号；内核不可达时 `ReloadActiveConfigAsync` 回如实的
"内核未运行"文案。本条无需修，也按纪律不去"顺手重构"。

## 三、状态行为矩阵

| VPN/内核状态 | 节点浏览 | 切节点 | 测速 | 订阅更新 |
|---|---|---|---|---|
| 从未连接（内核无） | 配置视图：组/成员/类型/server:port/预设现值 | 记预设台账，回放生效 | 明示核心不可用，不拨 VPN | 可用（不需隧道） |
| 已断开，内核常驻 | 实时 REST（原样） | 实时 PUT+回读 | 实时 | 可用 |
| 已断开，宿主已回收 | 配置视图 | 记预设 | 核心不可用 | 可用 |
| 连接中/失败 | 实时或配置视图（取决于内核是否已起步） | 同上按可达性 | 同上 | 可用 |
| config.yaml 也没有 | 空态+出口文案（"先去订阅页拉取"） | 拒绝并说明 | 核心不可用 | 可用 |

五个状态槽（VPN/内核/订阅/列表加载/动作）依旧**没有一个被合并**：`Snapshot.Ok` 只表内核，
`FromConfigFile` 只表来源，VPN 状态仍走 `ProfileGate` 独立槽（Docs/48 分工不破）。

## 五、已知限制（如实）

1. 内核"半死"（TCP 挂起非拒绝）时回退要等最长 10 s 超时——与既有 `KernelStatusPanel` 同窗，未收紧。
2. 配置视图无延迟、无活动连接；提供方成员只列磁盘上有的（inline 的 payload 已按内核口径并进
   组，见 §七第 4 行），http/file 的节点在远端/缓存文件里 ⇒ 占位行+Note。
3. 不认的 YAML 形态（锚点/多文档/顶层 flow 整表）降级为"列不出+判据文案"，**不做猜测**——
   代价是界面没数据，不是内核起不来，所以保守是对的一侧。
4. `selection.txt` 的 `Now` 是"上次手选"，不是内核实时 now；横幅与行标签都带"预设"字样区分。

## 七、对照官方内核语义（mihomo Meta 分支，本地全量源码 `clashUWP研究\baseline\_mihomo`）

逐条拿内核解析路径核配置视图的判据，找到七处差异，全部落进 `ConfigNodeView.cs`；
下表行号均为现读实物（不是记忆）。

| # | 内核事实（文件:行） | 我们原先的差 | 现状 |
|---|---|---|---|
| 1 | 顶层字段是强类型标签 `yaml:"proxy-providers"`(:450)/`yaml:"proxies"`(:452)/`yaml:"proxy-groups"`(:453)，解码器 `go.yaml.in/yaml/v3`（`common/yaml/yaml.go:5`）⇒ **顶层键大小写敏感**，且**没有 `proxy` 单数别名** | 视图忽略大小写列数据，什么都不说 | 数据照列（磁盘事实），`UnknownTopLevelKeys`（ConfigNodeView.cs:549）把"等值小写键不存在、原样大小写存在"的键点名进 Note：`Proxies:`/`proxy:` ⇒ "内核不会加载" |
| 2 | 条目内部字段名走 structure decoder 的 `EqualFold`（`common/structure/structure.go:522`）⇒ 节点/组**字段名**大小写不敏感；但 `type` 取的是**精确键** `mapping["type"]`（`adapter/parser.go:13`）且类型值 switch 精确匹配 | 无（标量表本就 OrdinalIgnoreCase） | 一致，不动；类头记录差异（`adapter/parser.go:13` 那个精确键是理论边角，订阅实物没见过 `Type:` 写法，不为它加猜） |
| 3 | 内置策略 `DIRECT/REJECT/REJECT-DROP/COMPATIBLE/PASS/PASS-RULE`（config.go:891-896）+ 隐式 `default` 提供方（:973） | 无 | `MihomoController.BuiltinProxyNames` 与之逐字对齐（复核过，零改动） |
| 4 | **inline 提供方的 `payload:` 就在配置原文里**（`adapter/provider/parser.go:95-96` `NewInlineProvider(name, schema.Payload, …)`）；`use:` 的语义是"该提供方的节点并进组成员"（`adapter/outboundgroup/parser.go:132-152`），REST 的 `all` 即合并结果 | 提供方只有一行 `Type=Provider` 占位，inline 的磁盘节点不展开 ⇒ 组里看不到 n1/n2 | `ProviderEntries` 按提供方登记 payload 节点（映射写法与列表写法、块 payload 与行内 payload 四种形态，ConfigNodeView.cs:384/462/494/512），组段折算成员时把 `use:` 展开成真成员带 server/port 与来源名（:226-245）；http/file 磁盘无节点才留占位行 |
| 5 | 节点重名是**硬失败**：`proxy %s is the duplicate name`（config.go:907），组重名同样（:959）⇒ 内核整个起不来 | 重名被后写覆盖，无声 | `dupNames` 收集 + Note 警示"这份配置起不来"（ConfigNodeView.cs:130-132/169-172） |
| 6 | `include-all/include-all-proxies/include-all-providers` 在解析期展开（`outboundgroup/parser.go:41-43/87-111`），`filter/exclude-filter/exclude-type` 由内核运行态筛 ⇒ 组成员可能多于/少于磁盘写法 | 视图静默按磁盘列，不声明 | 命中这些键的组 ⇒ Note"成员名单由内核运行态展开，配置视图可能少于内核实际"（:157-161/246-247） |
| 7 | 提供方名 `default` 是保留名，定义即报错（`adapter/provider/provider.go:28` ReservedName + config.go:934-935）；空组（`proxies` 与 `use` 都缺）也报错（`outboundgroup/parser.go:117-118` errMissProxy） | 无 | Note 警示保留名（:250）；组无成员时成员表为空、由"未知节点/占位行"判据如实呈现。`errMissProxy` 未加专门警示：这种配置内核起不来，隧道侧自有失败路径，视图列空组即是如实 |

配套判据一条：`proxy-providers` 的 vehicle 类型 switch 在内核是**精确匹配**
（parser.go:80/86/95 `file/http/inline`，大小写不同即不认识）；本视图对 `type: inline`
按忽略大小写认——认识的后果只是"多列出磁盘上真有的节点"，与 #1 的"大写顶层键要警示"
不同构，不额外出口。
