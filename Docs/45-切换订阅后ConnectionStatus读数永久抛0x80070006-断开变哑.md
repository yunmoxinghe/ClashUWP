## 三、这次顺手钉死的一条旧含糊：`收尾=干净` 有一半是"读不到 ⇒ 当它没了"

`GracefulTeardown.WaitSessionDownAsync` 等收尾靠轮询 `ConnectionStatus`。本轮那一句完整形状是：

```
收尾=干净（状态=Connected → 发起平台断开 断开请求=Ok 等到收尾=读状态异常:COMException>读状态异常:COMException（2 s））
```

即**两次读数都抛异常之后判"干净"**。这一次结论是对的 —— 平台自己那侧在同一秒（06:43:55.780）打了 `会话结束，存活 5s`，新会话也在 06:44:02 正常起来，两条独立证据都支持"旧会话确实收掉了"。但**判据的形状要看清**：`读状态异常` 在我们的收尾闸里等价于"这条已经没了"，而本轮实测它同样等价于"这台机器上的状态读数已经废了"。这两种解释在日志里长得一模一样。所以 Docs/44 §三 臂 B 的"成"要带这条注释读，不能当满分（写回 Docs/44 时同样带上了）。

## 八、【2026-10-23 订正】真实形状是**按条目中毒**，不是"整个存储读死"（一手，同一台机器第二轮取证，装机 `8B8CC4F4.ClashUWP/1.0.94.0`）

本篇头部和 §一 第 3 条那句"所有读取都抛 / 两种形状分不开"是**错的**，错在把扫描的失败当成了存储的失败。下面这一对行是分界线（同一个 pid，相隔 **21 ms**）：

```
2026-10-23 03:07:29.607 pid=21260 plugin W health-precheck 第 1 次读状态异常：COMException: 句柄无效。 (0x80070006)
2026-10-23 03:07:29.628 pid=21260 plugin I profile-connect [iKuuu_V2] 发起前状态=Connected 未发起=平台报告这条已经 Connected（会话已在，不再拨第二次）
```

前一条走的是全清单扫（`PickOurs` 对每条读 `ConnectionStatus`，第一条抛整读报废），后一条读的是**指定那一条** `[iKuuu_V2]` —— 同一进程同一毫秒级窗口里**一条抛、一条读得好好的**。⇒ `ConnectionStatus` 的中毒是**按条目（且按属性）**成立的。

### 九.2 【2026-10-24 联网核对官方口径】这个形状微软自己有一篇 KB 定案：rasman 断开流程失败 ⇒ 不重启就再也拨不上

**预防实践（联网核对到的官方/一手口径，全部落到"我们怎么不触发"）**：

1. **★ 活动会话期间不得删除或并发改写 VPN 条目** —— 官方文档在 Intune/VPNv2 的「已知问题」里写死了这条：*"在分配新 VPN 配置文件的同时删除活动 VPN 配置文件"* 与 *"设备同时处理对 VPN 配置文件的多个更改"* 都会**导致失去 VPN 连接**（[Intune VPN 配置文件](https://learn.microsoft.com/zh-cn/mem/intune/configuration/vpn-settings-configure)、[Azure P2S 故障排除](https://learn.microsoft.com/zh-cn/troubleshoot/azure/vpn-gateway/vpn-gateway-troubleshoot-vpn-point-to-site-connection-problems)；那边甚至给了一个"格式差异导致每次都删了重建 ⇒ 掉线"的真实事故形状）。⇒ **1.0.101 的写入闸（`ProveStoreWriteSafeAsync`，[VpnProfileSetup.cs:755](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnProfileSetup.cs)）方向被官方背书**，本轮之前它只是我们自己定的纪律。
2. **★ 升级安装之前必须先断开并等会话收尾** —— 本篇出生时刻（10-22 06:43:51 连上、06:43:56 吃 631）吻合的形状就是"会话还在激活窗口里，进程被拦腰砍"。1.0.106 臂 C 已经消掉"关窗 ⇒ Canceled"这一支，但**装机流程里那支还在**：`Add-AppxPackage` 吃 0x80073D02 时习惯性 `Stop-Process -Name ClashUWP -Force`。从此这条写成硬规矩：**升级安装前先确认 `rasdial`=No connections 且 VPN 接口全 Disconnected，绝不在有会话时杀进程装包**。
3. **比重启轻的出口，官方无背书、只有一手社区案例**：设备管理器卸载 `WAN Miniport (IP/PPTP/SSTP)` + 「扫描硬件改动」（[Spiceworks 一手复现](https://community.spiceworks.com/t/netextender-ras-error-on-windows-10/660656)、微软 [错误 720 文档同法](https://learn.microsoft.com/zh-cn/troubleshoot/windows-server/networking/troubleshoot-error-720-when-establishing-a-vpn-connection)）。**优先级排在重启之后**，因为我们有一条反证：同一 `Port = VPN1-1` 在 23:30:52 被 iKuuu_V2 正常拨用 ⇒ 设备/驱动本身是好的，占死的是 rasman 里按连接名记的 transport，重装设备未必对症。另注：`Restart-Service RemoteAccess` 那类 CLI 重启有副作用的一手报告（[RRAS 重启后客户端连上但访问不到网络](https://community.spiceworks.com/t/rras-service-restart-issue/791709)），那是服务器侧 RRAS、不是客户端 RasMan，但足以说明"重启服务清状态"不是零风险动作。
4. 602/633/4328 这三个"端口/设备被占"家族，微软自己的处理口径也是**先找占用者、找不到就重启**（[错误 633 KB](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/error-633-the-modem-is-already-in-use-vpn) 给的是 `netstat -aon` + `taskkill` + 重启）⇒ 我们的 `rasdial` 查占用者这一步是走对了的，只是这次占用者不是任何活进程。

### 九.3 【2026-10-24 第二轮联网】本机正踩在一个微软已承认、已修的 Windows 回归上 —— §九.2 那句"只能重启"要降级

**官方 KB5127648**（2026-10-13 累积更新，OS build **26300.9711**）的修复条目原文：

> [Always On VPN] 此更新修复了安装 **KB5124008** 后影响 Always On VPN 连接的问题。配置自动协议选择或协议回退时，受影响的 VPN 连接可能**一直停留在"正在连接"状态，或者在初始连接尝试失败后无法连接**。在某些情况下，后续连接尝试可能会显示错误**"指定的端口已在使用"**。

**本机现读**（`HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion` + `Win32_QuickFixEngineering`）：`CurrentBuildNumber=26300`、**`UBR=9550`**，9 月批 `KB5124009`/`KB5124010` 装在 2026-09-24，10 月的 `KB5127648` **未装** ⇒ **这台机就落在"引入回归的那批补丁、且没拿到修复"的窗口里**。

**逐条对照本篇实物**：症状两半全中（"初始连接尝试失败"= 10-22 06:43:51 连上、06:43:56 吃 631；"后续连接尝试显示指定的端口已在使用"= 23:37:42 的 4328）。**不吻合的一半也要写清**：官方列的触发条件是"配置了自动协议选择或协议回退"，而我们**代码里根本没设这些**（全仓 grep `VpnProtocolOptions|VpnStrategy|Fallback|Automatic` 在 `Vpn/` 与 `VpnProfileSetup.cs` 里零命中；RasClient 20221 报的是 `VpnStrategy = SSTP` 单协议），且官方条目说的是 AOVPN（设备/用户隧道），我们是 UWP VPN 插件。⇒ **只能说同一 build、同一症状族，不能说已证同一个根因**；要证它是唯一解释，得等装上 KB5127648 后看这条僵尸是否仍会诞生（这是本修法第一个可做的单变量实验，见下）。

**据此改动两条口径**：
1. §九.2 那句"出口只剩重启"**降级成"重启只清内存态，回归还在、还会再犯"**。**对症的修法是打 10 月批（Windows Update 到 26300.9711+）**，且它顺带把"下次会不会再犯"这个变量消掉。装不装由用户决定（整机动作）。
2. §九.1 那句"占用点分两层"不变；但"我们只能不触发它"前面要加一句：**触发之后不释放，很可能不是我们够得着的层，而是这批补丁的层**。

**仍然成立、且与该回归无关的三条纪律**（回归只解释"为什么不释放"，不解释"为什么第一次会失败"）：会话期间不写 profile 存储（1.0.101 写入闸，官方 Intune/VPNv2 已知问题背书）；升级安装前必须无活会话（官方 Windows 升级指南也是这个口径：**升级前先断开 VPN 并关掉 VPN 软件**）；不拿"读数从抛变能读"之外的证据当"会话没了"。

**这一轮另外三条有用的官方/一手口径（都已核过原文）**：

1. **官方语义：插件外部拆不了会话** —— `VpnChannel.Stop()` 文档明写*"在连接的 VPN 插件外部调用此 API 将失败，因为活动和交互由 VPN 配置文件控制；每个进程只能有一个 VPN 配置文件"*，`TerminateConnection` 只适用于 `IVpnPlugIn.Connect` 内的建连尝试且*"不应在重新连接场景调用"* ⇒ memory「VpnChannel API at 26100：插件侧没有自主退出原语」拿到官方原文，不是我们翻 API 没翻到。
2. **RAS 侧拆连接要用它自己给你的句柄** —— 官方 RRAS 文档：`RasDial` 成功返回连接句柄，`RasHangUp` 用**那个句柄**终止。平台代我们拨，句柄在平台手里 ⇒ 我们从包外用 `VpnManagementAgent` 那套动词拆，本质是隔着一层，"受理≠拆掉"（§七.10 那条实测）有了机制解释。
3. **一手同款卡死，社区的实际处置是"改 profile 排到别的窗口"** —— AOVPN 权威博客评论区问的正是我们这个问题（*"活动连接在的时候没法推更新，脚本必须先终止连接再重建，流量会闪断"*），给出的做法是**把脚本+XML 复制到本地、用计划任务在合适窗口执行**，而不是当场改。⇒ 与我们 1.0.104 的"台账欠账 + 边沿/补扫/挂载三个出口"是同一个形状：**当场不推，欠着，等干净的窗口再推**。另有一条一手：断开 VPN 后整机网络坏、只能靠**禁用/启用 WAN Miniport 驱动**恢复（MSDN 归档帖），与 §九.2.3 那个次选出口同源。
