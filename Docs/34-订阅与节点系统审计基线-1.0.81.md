# ClashUWP 订阅 / 节点 / 代理组系统 审计基线（1.0.81）

> 阶段：第一阶段只读审计 + 修复基线。
> 审计对象：`ClashUWP/Backend/`、`ClashUWP/Vpn/`、`ClashUWP/Frontend/`。
> 官方依据版本：**MetaCubeX/mihomo v1.19.32**（本仓库 `go.mod` 所 pin，`DnsConfig.cs`/`KernelHome.cs` 注释为证）。
> 标注约定：`【官方已证实】`=`已对照官方 wiki / 仓库实现`；`【代码已证实】`=`已读源码定位`；`【推断】`=`尚未运行验证。

---

## 1. 结论（最严重的三个问题）

1. **订阅形态校验用错官方键并整体拒收 provider 型订阅。**
   `SubscriptionManager.FetchAsync` 用 `text.Contains("proxies-providers")` 判定（[`SubscriptionManager.cs:136`](ClashUWP/Backend/SubscriptionManager.cs)），官方顶层键是 `proxy-providers`（[官方 wiki 已证实](https://wiki.metacubex.one/en/config/proxy-providers/)）。后果：一份**只有 `proxy-providers:`、没有顶层 `proxies:`** 的纯提供者订阅（官方标准做法）会被判为「内容不像 Clash 订阅」而**根本无法添加**。

2. **刷新若抓到含 `proxies` 字样的 HTML 错误页 / 登录页，会被当成订阅写入并覆盖旧的有效 `config.yaml`。**
   形态校验只做 `text.Contains("proxies")`（[`SubscriptionManager.cs:133-137`](ClashUWP/Backend/SubscriptionManager.cs)），且写在落盘之前但判定太弱 → 下载成功但内容非 YAML 时仍覆盖缓存，违反「刷新失败不得无条件覆盖缓存」的硬约束。

3. **选择持久化缺失 + 并发/过期响应无防护。**
   - 节点选择由内核写入 `cache.db`，而 home 是只读的 `InstalledLocation` → 重启 / 重装后选择不保留（[`MihomoController.cs:855-860`](ClashUWP/Backend/Mihomo/MihomoController.cs)，G10 已知缺口）。
   - `FetchAsync` 无信号量、无世代号（[`SubscriptionManager.cs:87-195`](ClashUWP/Backend/SubscriptionManager.cs)）→ 重复点「更新」可交叉写 `config.yaml`，旧请求结果可能覆盖新请求。

> 次重要但确定的问题：UI 元信息统计完全不认 `proxy-providers`（节点数恒为 0）；代理组类型漏 `relay`（v1.19.32 支持）；未读取 `provider-name` 做节点归属；异常消息路径可能把带 token 的订阅 URL 带进日志。详见第 4 节。

## 3. 现有数据流（订阅 → UI / 核心 调用链）

**实际采用模式：B（客户端自行管理）。** UWP 自己下载 / 解析 / 落盘，再把配置交给 Mihomo；Mihomo 不通过 `proxy-providers` 的远程拉取（除非订阅自带该段，改写器原样保留）。

```
[UI 订阅页] MainComponent.FetchSubscriptionAsync
  └─ SubscriptionManager.FetchAsync(url, activate:true)        [Backend/SubscriptionManager.cs:87]
       1. 校验 URL (http/https)            :93-95
       2. HttpClient 下载 (UseProxy=true) :101-114   ← 与内核侧 UseProxy=false 相反，注释已说明
       3. 响应头取订阅名 Profile-Title/Content-Disposition :121  SubscriptionName.FromHeaders
       4. 弱形态校验 text.Contains("proxies") :133-137   ★ Bug：用错键 + 太弱
       5. 写 subscriptions/{id}.yaml + (激活时) config.yaml :139-144,179
       6. SubscriptionView.Parse 统计节点/规则/组 :152
       7. VpnProfileSetup.EnsureSubscriptionProfile 注册系统 VPN profile :165
       8. 若激活 → ReloadActiveConfigAsync → SubscriptionReload.RegenerateEffectiveFile
          → KernelConfig.Transform → PUT /configs?force=true 热重载 :182,379

[内核加载] ClashVpnPlugin → clash_bridge_start(config.kernel.yaml)  [Vpn/clash_bridge.dll, mihomo v1.19.32]
   └─ external-controller 127.0.0.1:9090

[UI 代理页 3s 轮询] KernelView.LoadAsync
  └─ GET /configs → GET /proxies → GET /connections            [Backend/Mihomo/KernelView.cs:99]
       切节点 → MihomoController.SelectAsync(group, node)
          → GET /proxies (取组表) → PUT /proxies/{group} {"name":node} → 回读 now :824,931
```

**数据所有权：**
- UWP 管理：`settings.txt`（subUrl/subActive/subName）、`subscriptions/{id}.yaml`、`config.yaml`、`config.kernel.yaml`、系统 VPN profile 列表、节点选择（仅靠内核 `cache.db`，而该文件在只读 home）。
- Mihomo 管理：`cache.db` 选择、provider 缓存、运行时测速、连接表。
- 只能经核心 API 查：当前 `now`、`all`、节点延迟 `history`、连接、provider 状态。

## 5. 修改清单（拟定 · 最小必要）

> 落地情况见第 6 节。所有改动走源码内联、复用现有离线测试，不碰部署与包结构。

1. **M1（修 Q1/Q2）** `SubscriptionManager`：抽出可测的 `ProbeShape(text)`——用顶层键识别（`proxies:` / `proxy-providers:` / `proxy-groups:`）+ 拒绝 HTML（`<html`/`<!DOCTYPE`/首字符 `<`）。取代原 substring 判据；校验在落盘之前，保证失败不覆盖缓存。
2. **M2（修 Q3）** `SubscriptionView.Parse`：识别 `proxy-providers` 段；`inline` 提供者数 `payload:` 里的节点，`http`/`file` 提供者标记「由内核动态加载」（新增 `ProviderCount`/`HasProviders` 字段，UI 显示而非虚 0）。
3. **M3（修 Q6/Q7）** 把 `relay`/`Relay` 纳入 `IsSelectableGroupType` 与 `KernelView.Group.IsUserSelectable`；保持 `LoadBalance` 不可手选（自动组语义）。
4. **M4（修 Q8/Q11）** `ReadProxiesTable` 读取 `provider-name` 进 `ProxyInfo`/`Member`，UI 用副标题显示来源；`ByName` 碰撞仅在类型/延迟展示层，不影响以组为作用域的切换。
5. **M5（修 Q5）** `SubscriptionManager` 加 `SemaphoreSlim(1,1)` + `long _generation`；`FetchAsync`/`UpdateActiveAsync` 串行化，过期的旧响应不允许覆盖新响应写出的 `config.yaml`。
6. **M6（修 Q9）** 日志路径只记 `uri.Host`，不把完整 URL（含 token）进 `RollingLog`；异常消息做脱敏。
7. **M7（修 Q10，可选增强）** 新增 `MihomoController` 对 `/providers/proxies` 的只读枚举 + `/providers/proxies/{name}/healthcheck` 触发，让提供者刷新状态可见（不阻塞切换，纯信息面）。
8. **M8（修 Q12，可选）** `FetchAsync` 在激活且内核在线时，重载后追加「核心是否真接受该配置」的判据（读 `/version` 或在 reload 失败时明确提示），避免「落盘即成功」。

## 7. 遗留风险

1. **选择持久化（Q4）**：要真正持久化需把 Mihomo home 迁到可写 `LocalState`，属于运行态改动，需评估是否触碰「UWP 包结构 / VPN 数据平面」边界。已记录 G10；本轮**不擅自改动**，备选方案为「客户端在 `LocalState` 记选择、启动时对核心 API 回放 `PUT /proxies/{group}`」（纯客户端管理，不改 home）。
2. **provider 远程节点的真实延迟 / 健康**：依赖 `/providers/proxies` 的 M7 为可选增强，若不做则 provider 节点的延迟只来自 `/proxies` 的 promoted 条目（已可用），但 provider 级刷新状态不可见。
3. **核心集成 / 端到端**需实机 + v1.19.32 内核与隔离配置，离线夹具无法覆盖（第 6 节已声明）。

## 8. 最终判定（基线）

- **官方语义对齐程度**：后端 API 对接（切换 / 运行态 / 组分类 / 内置策略排除）对齐度高；**订阅侧形态判定与 provider 元信息存在明确偏差**（Q1–Q3），代理组类型漏 `relay`（Q6）。
- **核心集成程度**：经 REST API 对接，已实测可切节点、读组、读延迟；provider 型订阅的核心加载未专门验证（本机为顶层 `proxies` 型订阅）。
- **是否具备发布条件**：**否**。Q1/Q2（P0）会导致标准 provider 订阅无法添加且刷新可能覆盖有效配置，修复前不应发布。修复 M1–M6 并通过离线回归后可进入实机验收。
