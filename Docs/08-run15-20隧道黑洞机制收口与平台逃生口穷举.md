# 08 · run 15–20：隧道黑洞的机制收口，以及平台侧逃生口为什么全被关死

目标只有一个：**连上 VPN 后其它应用能出外网**。1.0.20 装好之后（`Docs/07` §4 记录了装包差分），
用 `settings.txt` 文件开关 + 应用内 debug 动词跑了三轮单变量实验
（`.local/measure-15.log`、`measure-16.log`、`measure-17.log`，驱动脚本同名 `run-testNN.sh`）。
本篇是这三轮的结论，口径：**只有实测过的才写成结论，其余标「未验证」**。

---

## 0. 一句话

mihomo 内核跑在**自己下发 0.0.0.0/0 的那条隧道的宿主进程里**，
所以它的每一条出站拨号都被自家隧道抓回去 —— 这不是配置错、不是节点死、不是 DNS，
而 Windows VPN 插件平台在**路由层没有任何等价于安卓 `VpnService.protect()` 的原语**，
剩下的唯一出口是按**应用**分流的 traffic filter（1.0.21 正在验的那条）。

## 2. 三条被排除的假设

1. **H-a「节点 /32 排除路由本身有害」—— 否。** 16B 把它一条不留地摘掉（环回 /32 从 24 降到 6），
   错误原文、`delay` 结果、宿主判据**没有任何一项变化**。摘掉之后节点 IP 只是从环回
   改落到隧道接口 —— 换一种死法，不是活路。
2. **H-b「排除路由装错接口是因为 profile `ServerUris=127.0.0.1`」—— 否。** 15B 换成网关
   `192.168.0.1` 后路由归属逐字不变（回读 `ServerUris=1个(http://192.168.0.1/)` 已确认写进去了）。
3. **H-c「节点侧/订阅侧死了」—— 否。** 离线用官方内核跑过同一份订阅，26/32 节点活
   （见项目记忆 + `Docs/` 里的先遣对照），且 17-1 的错误是内核自己打的 `reject loopback connection`，
   包根本没出网卡。

## 3. 机制（这一轮的新增认知，两条都是可执行的硬事实）

### 3.1 `VpnRoute` 表达不了「把这条排除路由装到物理网卡」

官方 `VpnRoute` 只有 `Address`/`PrefixSize`，构造器是 `VpnRoute(HostName, byte)` ——
**没有 NextHop，也没有 Metric**。所以我们下发的 /32 只能由平台自行挑接口，
实测挑到了 `Loopback Pseudo-Interface 1`（16A：18 条节点 /32 全在 ifIdx=1）。
结论：安卓 `protect()`（per-socket 顶到物理网卡）在本平台**没有路由层等价物**，
「靠排除路由防自环」这条路在 API 层面就是死的，不是我们参数没调对。

### 3.2 绑网卡只会把「被抓回隧道」变成「瞬败」，两种都是死

Winsock 的 `IP_UNICAST_IF`（mihomo `bind_windows.go`，`interface-name` 走的就是它）
**不覆盖路由表**：绑定只决定源地址/出接口选择，目的地路由到环回/隧道就照样失败 ——
17-2 的 `connectex: unreachable host`（TCP）与 `wsasendto: unreachable network`（TUIC UDP）
就是这个；17-1 取消绑定后包重新进入隧道，被 mihomo 自己的防回环守卫挡掉
（`reject loopback connection to:`），UDP 侧表现为 `context deadline exceeded`。

### 3.3 顺带确认的两个缺陷（不在本轮变量上，记下来别丢）

- **健康哨兵测不到东西**：它的探针是应用内发起，连接已被自家隧道接管，
  16A/16B 判据拿到的是 `schannel: failed to receive handshake` / `Empty reply from server`，
  而不是「隧道干净失败」的形状 ⇒ 哨兵的判据得改成隧道内证据（任务 #11）。
- **热重载从来没生效**：插件 `TryHotReload` 打的是 `PUT /configs` 且无 body；
  官方 `PUT` 从 JSON body 取 path/payload，逐字段即时生效的是 `PATCH`（见 `RunBindAsync` 注释）。

## 4. 下一刀：traffic filter（1.0.21，run 18 的设计）

`Docs/06` 已经把 traffic filter 的三态实测过一遍：空对象 = **默认 deny**（tfmode=0，
`GenFail=23`、`reqSeen=1`），`AllowOutbound=true` = **绕过 VPN**（tfmode=1，`reqSeen=0`），
`nullptr` = 全部进隧道（tfmode=2，`reqSeen=24` ✅）。1.0.16 之后一直走 `nullptr`。

`nullptr` 的代价正是本轮的根因：**它无差别地连自己包也强制进隧道**，
而内核就在同一个包里。剩下的官方原语只有 per-app 分流：

```csharp
var a = new VpnTrafficFilterAssignment { AllowOutbound = <臂> };
a.TrafficFilterList.Add(new VpnTrafficFilter(
    new VpnAppId(VpnAppIdType.PackageFamilyName, Package.Current.Id.FamilyName))
    { RoutingPolicyType = VpnRoutingPolicyType.SplitRouting });   // 0 = 拆隧道，允许走别的接口
channel.StartWithTrafficFilter(..., a);                            // 臂 0 时仍传 null
```

`settings.txt` 开关 `selfSplitTunnel`（`LocalSettings.SelfSplitTunnel`，0/1/2，越界回落 0）：

| 臂 | 传入 | 预期 | 用来判什么 |
|---|---|---|---|
| 0 | `null` | 与 1.0.20 逐字一致：其它应用进隧道、内核拨号 `reject loopback` | 基线（必须复现 run 17-1 的形状，否则说明包/环境变了） |
| 1 | filter + `AllowOutbound=false` | 本包 SplitRouting ⇒ 内核从物理网卡出网（`delay` 应有真实 ms）；其它应用仍进 `0.0.0.0/0` | **期望臂**：修好数据面 |
| 2 | filter + `AllowOutbound=true` | 不匹配 filter 的流量允许旁路直连（`Docs/06` §5.4 语义） | 把「filter 到底生效没有」与「AllowOutbound 语义」两件事拆开；兼作隧道挂掉时不黑洞整机的兜底形态 |

判据（run 18 每臂都跑，缺一不可）：`conf` 回读 → `delay`（节点 + DIRECT）→ 造流量 16 s → `logs` 原文；
宿主侧 `OS-via-node`（google 204）与 `CN-DIRECT`（223.5.5.5）；
收尾必过 `Docs/07` §1 四条（NRPT=0、默认路由只剩 WLAN idx=6、无残留 VPN 连接、baidu:443 True）。

⚠️ 已知风险，如实写在这儿：traffic filter 一旦装错，最坏是**数据面整机旁路**（2 号臂的预期行为），
而不是现在这样只能等 600 s 硬上限断开。恢复路径照 `Docs/07`：L1 哨兵、L2 `rasdial "ClashUWP" /delete`、
L3 管理员强拆 NRPT。1 号臂若成立，才是「其它应用能出外网」第一次有可复现的正面证据。

## 5. run 18/19/20 实测结果：三条出路全部证伪（1.0.21，`ClashUWP.Vpn 1.0.9`）

代码落地情况：`LocalSettings.SelfSplitTunnel`（`settings.txt: selfSplitTunnel=0|1|2`，越界回落 0）
→ `ClashVpnPlugin.BuildSelfSplitFilter()` → `StartWithTrafficFilter` 最后一个实参；
形态写进 `dataface-plugin.txt` 的 `SelfSplitTunnel=` 行。三臂都跑过，**结论是这条路不通**。

### 5.1 run 18（`.local/measure-18.log`）——仪器缺陷，数据只能算半个

基线 18-0 复现了 run 17-1 的形状（`reject loopback connection` + TUIC UDP `wsasendto: unreachable network`）
⇒ 新版本没把默认臂改坏。18-1/18-2 的宿主判据**形状变了**（23–34 ms 本地瞬败、内核日志窗口 0 行），
但这两臂读到的 `dataface-plugin.txt` mtime 仍停在 18-0 断开那一刻（03:13:02）
⇒ **臂的真实形态一次都没读到**，快照是陈的。教训写进驱动脚本：读快照前必须有「新鲜度门」。

### 5.2 run 19（`.local/measure-19.log`）——每臂全新进程 + 新鲜快照，判决成立

| 臂 | 快照里的 filter 形态 | Encapsulated | Injected | 宿主判据（curl） | 内核日志窗口 |
|---|---|---|---|---|---|
| 19-0 `selfSplitTunnel=0` | 未调用（传 null） | 7188 量级（流量正常进隧道） | 正常 | `schannel: failed to receive handshake` / `Empty reply from server`（= 包进了隧道、内核拨不出去） | 80 行 `reject loopback connection` |
| 19-1 `=1` | `arm=1 pfn=421769c5-…_y0tg80em3rma2 AllowOutbound=False` | **17** | **0** | google `000 … after 23 ms: Could not connect to server`；223.5.5.5 `after 1 ms` | 0 行 |
| 19-2 `=2` | `arm=2 … AllowOutbound=True` | 个位数量级 | 0 | 同样 27 ms / 0 ms 本地瞬败 | 0 行 |

判读（这就是 `Docs/06` §1 那张表的延伸，只是这次 filter 列表**非空**）：

- filter 确实装上了（快照 `arm=1/2` 是插件自己写的，不是猜的），但**代价是数据面整体停摆**：
  进隧道的包从数千掉到 17，回程注入 0 个，宿主所有应用 20–30 ms 本地瞬败。
- 19-1 的瞬败 = 不匹配 filter 的流量被 ALE 默认 deny；
  19-2 的瞬败说明 `AllowOutbound=true` **也没能把别的应用放回物理网卡**（本机直连 223.5.5.5 本来是通的）。
- 附带一条：本包的 REST 回路 `127.0.0.1:9090` 在这两臂变成「积极拒绝」
  —— filter 一装，连应用自己的环回控制通道都被打断，观测面一起没了。
- ⇒ **「按应用分流让内核逃出隧道」在本平台不可用**：filter 是全局开关式的，
  要么数据面正常（null），要么整机连不上（非 null）。

### 5.3 run 20（`.local/measure-20.log`）——最后一个 profile 级自由度也关了

假设：内建 VPN 类型自带「VPN 服务器地址免隧道」逻辑，平台会为 `ServerUris` 指向的地址
装一条走物理网卡的路由（否则任何 VPN 都连不上自己的服务器）。我们一直把 `ServerUris`
写成 `127.0.0.1`/网关，从没写成真节点 IP。

单变量：`profile-server.txt` 写 `http://82.39.109.155`（`US高速-迈阿密03` 的 tuic 服务器），
`recreate` 回读确认 `ServerUris=1个(http://82.39.109.155/)`，对照组 `185.34.144.19` 不进列表。

实测：`20-B` 的 `Find-NetRoute` 对**两个 IP 都还是 `Loopback Pseudo-Interface 1 ifIdx=1`**
（与 20-A 逐字相同），`delay` 仍 `HTTP 503`，判据形状与基线一致。
收尾已删 `profile-server.txt` 并 `recreate` 回 `http://127.0.0.1`，`Docs/07` §1 四条全过
（NRPT=0、默认路由只剩 WLAN idx=6、无残留连接、baidu 200）。
⇒ `ServerUris` 不参与排除路由的接口选择（H-b 在「写网关」和「写节点 IP」两种取值上都被否）。

## 6. 现在的边界（写清楚，别再重复试）

平台侧能让「内核出站 socket 逃出自家隧道」的原语，已经实测穷举完这四条：

| 试过的出路 | 结果 |
|---|---|
| 节点 IP /32 排除路由（`Ipv4ExclusionRoutes`） | 装到环回 = 黑洞；摘掉 = 被抓回隧道。两种死法，无第三种 |
| `VpnRoute` 指定网关/metric | API 不存在（只有 Address/PrefixSize），无从表达 |
| mihomo `interface-name` 绑物理网卡（`IP_UNICAST_IF`） | 不覆盖路由表 ⇒ `connectex: unreachable host`；清空 ⇒ `reject loopback connection` |
| per-app traffic filter（本包 `SplitRouting`，`AllowOutbound` 两态） | 数据面整体停摆（Encapsulated 7188→17），宿主 20–30 ms 瞬败，REST 环回也被拒 |
| profile `ServerUris` = 127.0.0.1 / 网关 / 节点 IP | 路由归属逐字不变 |

也就是说：**在「VPN 插件进程内跑内核 + 下发 0.0.0.0/0 强制隧道」这个形态下，
数据面在 Windows VPN 插件 API 上没有逃生口**。
下一步只能换形态（内核挪出被隧道抓取的进程/包，或不靠 VPN 插件做全路由），
先遣项目 `D:\fluentapps\repos\clashUWP研究` 曾在同一条路线上 PASS 过判据 8，
它到底靠哪一条逃生，正在按文档核查（见本篇 §7，结论出来再补）。


## 7. 先遣项目核查结果：判据 8 的 PASS 不是靠"在全隧道下修好回环"

核查方式：把 `D:\fluentapps\repos\clashUWP研究`（105 篇 docs）交给独立 agent 按四个问题
取证（回环怎么解 / 路由与 metric 实值 / 同进程为什么 `IP_UNICAST_IF` 在他们手里活 / 可抄代码），
要求引用原文。结论汇总如下（原文位置随附）。

**① 它的 PASS 臂根本没有 `0.0.0.0/0`。**
docs/96 §8.2 三臂实测栏写着「VPN 上是否出现 0.0.0.0/0 | 无 / 无 / 无」，并明说三臂的
`0.0.0.0/0` 都只落在 `Meta(ifIdx=3)` 与 `WLAN(ifIdx=6)` 上。它的 inclusion 集合是
`192.168.21.0/24` + `208.67.222.222/32` + fake-ip `100.64.0.0/16`（`scripts/99-b1-config-arm.ps1:153`），
判据 8 打的就是那条**为测试故意加的公网裸 IP /32**。
⇒ 节点 IP 与任意公网目的地的选路天然留在 WLAN，核心拨号不可能被抓回。
**这条路线的前提是"不做全路由"，与我们的目标（其他应用的流量全部进隧道）相反。**

**② 它对那条 /32 用的才是 `dialer.DefaultInterface` + `IP_UNICAST_IF`**（docs/89 §0：
`setsockopt(IPPROTO_IP, IP_UNICAST_IF=31, idx)`，探针 `verdict 2/4 → 1`，判据 8 FAIL→PASS），
注入方式是进程内直接 Store 到 atomic 全局，不写配置文件（`component/dialer/options.go:11-21`）。

**③ per-app traffic filter 在它手里也是"未验证"**（docs/89 §5 标为优先度低），
唯一确定的结论就是 docs/76 §5.4 的第三参必须传 `nullptr`。我们 run 19 关掉它，
与先遣项目"没做出来"一致 —— 两边互证，第 3 条出路可以永久划掉。

**④ 外层 transport 它是哑地址**：`Server=http://192.0.2.1`（TEST-NET-1）+ `noEncapOut=1`
（docs/93 §1），真实节点 IP 从不参与平台层路由；而 docs/06:179 记 `UWPToyVpn` 反过来
靠 `127.0.0.1` transport 绕开「单 IP 排除无效」的平台 bug。
⇒ 我们正准备测的 `outerTarget` 变量，他们两边都没给出定论，只能自己实测。

**⑤ 排除路由（`Ipv4ExclusionRoutes`）他们零使用**：route-A 时代没用过，docs/32 用过
`v4Excl=3` 并判「不是原因」。**所以"排除 /32 会落到哪块网卡"这件事他们没有实测过**，
我们的 run 14/16/20 三轮 `Loopback ifIdx=1` 归属是本项目独有证据，没有现成答案可抄。

**⑥ 它留下的最硬一条 metric 结论（docs/34:234）**：隧道接口若声明 `0.0.0.0/0`，
`routeMetric=256 + ifMetric=55 = 311` 输给 WLAN 的 `0 + 35 = 45`，
**必须拆成 `0.0.0.0/1 + 128.0.0.0/1`（更特定 ⇒ 与 metric 无关地胜出）才能真正抢走默认路由**；
另：下发 `::/0` 会把 VPN 变成 IPv4 默认路由并把 WLAN metric 抬到 ~4265（docs/96 §6.2），禁止。

**⑦ 同进程下 `IP_UNICAST_IF` 在他们手里活、在我们手里死的原因（docs/99 Bug1 + docs/89 §2）**：
他们的 WLAN **保留** `0.0.0.0/0 metric=0` ⇒ `IP_UNICAST_IF` 的受限路由查找有路可走；
我们下发 0/0 后 WLAN 默认路由被压 ⇒ 受限查找无路 ⇒ `10051 unreachable host`（与我们 run 13 原文一致）。
另外两个必须核对的实现细节：
`interface-name` 喂 `"auto"` 字面量会 `ResolveInterface → ErrIfaceNotFound` 全链瞬败（`ifacebind.go:68-88`）；
挑网卡的硬判据是 **TUN 网卡 MAC 为空、物理网卡必有 MAC**，按 index 取小会绑到另一块 TUN 上，
症状与没绑一模一样。

**一句话总结**：先遣项目从未跨过「机器级 `0.0.0.0/0` + 包内进程的内核出站」这道坎，
**没有 known-good 配置可抄**。它给的可用资产是两条纪律：
要么"窄 include（放弃全路由）"，要么在抢走默认路由之前先把出站逃生做实 —— 而逃生这条路
的 Windows 原生表达（排除路由 / 绑网卡 / per-app filter / ServerUris）已被本篇 §6 穷举否掉。

## 8. run 21 的单变量阶梯（本轮唯一还没测的平台输入）

§6 表里 `ServerUris` 那行是 profile 侧，`AssociateTransport` 那个 socket 的
**已连接远端**是它没覆盖的另一半：我们 1.0.20 之前恒连 `127.0.0.1:53`，
而"排除 /32 落环回"与"transport 落环回"是同一个形状。1.0.22 把它做成开关
（`ClashUWP.Vpn/LocalSettings.OuterTarget` / `OuterPort`，默认为旧行为）后分三臂测：

| 臂 | `outerTarget` | 预期（若假设成立） |
|---|---|---|
| 21-A | `127.0.0.1` | 基线：`Find-NetRoute <节点IP>` 仍 `ifIdx=1` |
| 21-B | `192.168.0.1`（WLAN 网关） | 排除 /32 归属可能改到 `WLAN ifIdx=6` |
| 21-C | `82.39.109.155`（活节点服务器） | 同上，且语义上是"外层目的地"的正解 |

判决位只看三件事，都不需要整机全路由：
`Find-NetRoute` 归属、内核 `delay` 是否不再 `503`、日志里 `connectex: unreachable host` 是否消失。
**`splitDefault`（0/1+128/1 抢默认路由）不在本轮**：它是"让隧道真的吃掉整机"的开关，
在逃生口做实之前打开就是把用户锁在网外（见记忆 [[feedback-never-hog-machine-network]]）。

## 9. run 21~24 定论：黑洞是外层 transport，域名出网靠 fake-ip（1.0.23 的三个默认值）

本篇 §6 把"平台侧可能的逃生口"列成四行，§8 只测了最后一行。接下来四跑把这条链走完，
**结论是：隧道黑洞的根因不在路由、不在 filter、不在 profile，而在 `AssociateTransport`
那个 socket 的已连接远端；而"连上 VPN 后按域名打不开外网"的第二道坎是 DNS 污染，
只有 fake-ip 能绕开。** 四跑全部同一次部署（1.0.22）+ 只改 `LocalState` 文件，
判据一律 `measure-2X.log` 原文，未复述。

### 9.1 run 21 · 单变量 = `outerTarget`，判决位 = 排除路由落在哪个接口

| 臂 | `outerTarget` | `Find-NetRoute <节点IP>` ×3 | `delay` 美/俄 | 快照 Encapsulated/Injected |
|---|---|---|---|---|
| 21-A | `127.0.0.1`（旧默认） | **Loopback Pseudo-Interface 1 ifIdx=1 nh=127.0.0.1** | 503 / 503 | — |
| 21-B | `192.168.0.1`（WLAN 网关） | **WLAN ifIdx=6 nh=192.168.0.100** | **200 delay=230** / **200 delay=256** | 3162 / 3321 |
| 21-C | `82.39.109.155`（迈阿密节点） | **WLAN ifIdx=6 nh=192.168.0.100** | **200 delay=229** / 200 delay=260 | 1277 / 1289 |

同一时刻 `223.5.5.5` 在三臂都是 `ClashUWP ifIdx=45`（隧道），说明隧道的 `0.0.0.0/0` 本身是赢的
—— 先遣项目担心的 metric 抢占（docs/76 的 `311 vs 45`）在这台机器上不是障碍。

**定论**：平台按"这个 transport socket 会走哪条路"来决定 `Ipv4ExclusionRoutes` 装在哪个接口上。
`127.0.0.1` ⇒ 节点 /32 全落环回（比隧道 0/0 更特定 ⇒ 拨号包进黑洞，`connectex: unreachable host/network`）；
非环回目标 ⇒ 全落物理网卡，内核第一次拨得动节点。
`VpnRoute` 没有 NextHop/Metric，路由层无法表达"装到物理网卡"，所以这个 socket 是**唯一**的纠正入口。
§6 里 `ServerUris`（run 15B/20B 换网关、换节点 IP，归属逐字不变）与 per-app filter（9.3 复验）就此双双排除。

## 10 run 25 · 1.0.23 装机即黑洞：一处 YAML 改写把内核写死

这一节的价值是**把"改写 YAML 的坑"和"隧道黑洞的坑"分开**，前者是我自己造的。

### 10.1 实测到的失败链（`dataface-plugin.txt` 原文）

```
Bridge=start 失败 rc=-2: parse mihomo config: yaml: line 573: did not find expected key
OuterTarget=104.223.85.121:53（要求=auto）        ← 9.1 的正解生效了
Encapsulated=883 / Injected=0                     ← 包进了隧道，内核没接
```

（行号 573/576 随实验时对 `config.yaml` 尾部的扰动行数漂移，指向的都是 `tun:` 块那一处。）

三点都有诊断意义：

1. `OuterTarget` 自动取到节点 IP，**外层目标这条改对了** —— 黑洞不再来自环回。
2. 内核**根本没起来**（rc=-2，YAML 解析失败），但隧道已经由平台装好 0.0.0.0/0 ⇒
   流量全进了一条没人接管的隧道。883/0 就是这个形态的量化：进得去、出不来。
3. 表现与 §9 之前所有黑洞不同：**连 DNS 都不回**（`Resolve-DnsName` 无输出、curl 全部超时），
   因为劫持者（内核）不存在，NRPT 又把查询指向了隧道里的假 DNS。

恢复：健康哨兵在 **60~75 s** 内自己断开（`断开=NoConnection`），断开后 nrpt=0、直连 baidu=200，
整机黑洞时长约 60~75 s —— 这是 §7 那套兜底第一次在真实黑洞里被验证有效。

### 10.2 根因：`dns-hijack:` 是"块式序列的父键"，不是空值行

订阅原文写的是

```yaml
tun:
  dns-hijack:
    - any:53
    - tcp:53
```

`KernelConfig.EnsureTunBlock` 当时按"键行有值就替换"处理，把父键行整行改成了
`dns-hijack: [any:53]`，于是底下那几条 `- any:53` 变成没有父键的孤儿序列
⇒ mihomo `did not find expected key`。`diff` 出来的唯一改动就是这一处。

1.0.24 的两道修正（都是"失败也不能把机器锁在外面"这一条的具体化）：

1. **块式/流式分治**：`ValueOf(lines[hijack]).Length > 0` 才走行内替换；值为空时向下扫描
   `- ` 开头的条目，已含 `any:53` 就不动，确实缺才在同缩进处 `Insert` 一条 `- any:53`。
   同一条规则推广到 `enable`/`enhanced-mode`：**行内没有值的键行不替换**（`IsInlineBlock`
   只解决 `dns: {…}` 这种父块，块内子键的空值同样致命）。
2. **`failFast`（默认开）**：`StartMihomoBridge` 返回非 0 时**抛异常放弃本次连接**，
   而不是"隧道留着、内核没了"。少一个内核远好过一条没人接管的默认路由 ——
   这正是 10.1 那 883/0 的教训。`settings.txt: failFast=0` 可关，用于专门测桥接失败形态。

### 10.4 ★★ run 26 没跑成的原因不重要，重要的是它顺带挖出的 96 秒必掉线 + 无限自动重拨

26-A 在握手阶段就超时（`status` 发出去 90 s 无回口），直接原因是 1.0.24 这个 **Debug AOT 包首启动被系统判挂起并关闭**
（`Application Hang` 1002 + WER `MoAppHang`，`reactor-startup.log` 连 `RUNTIME OS` 都没写出来）。
但顺着事件日志查下去，挖到一条比 fake-ip 优先级高得多的缺陷：

```
RasClient（在 Application 日志里）关于 ClashUWP 的记录，按时间统计：
  dial(20221)=413   connected(20225)=413   terminated(20226)=414
  终止 reason code：828×411 / 829×2 / 631×1     ← 631 才是"主动断开"
  相邻两次 dial 间隔：稳定 97±2 s（偶发 182/184 s = 跳过一轮）
  发起者：user SYSTEM —— 平台/服务侧重拨，不是前台点击
```

⇒ **连接连上约 96~98 秒必然被拆（828），而 profile 带自动重拨，于是 Windows 在这台机器上
一天内重装/重拆了 413 次全路由隧道 + DNS。** 用户当天的反馈"网卡炸了，重置网络才恢复"与日志吻合：
`22:00:36` WLAN Extensibility Module 停止、`22:00:38` WLAN AutoConfig 服务停止、
`22:00:54` Dhcp-Client/DHCPv6-Client 停止、`22:01:29~22:01:37` 全部重启；
最后一次拨号之后没有再出现 dial，重置顺带把 profile 删掉了
（现在 `Get-VpnConnection -AllUserConnection` 为空、无 ClashUWP 网卡、隧道 0 条、nrpt 0、baidu=200）。

⚠️ 时间轴的一处不确定性要先说明：本机时钟在这段实验期间明显不自洽
（同一批 `RasClient` 事件在两次查询里分别显示 `05:5x/06:2x` 与 `21:5x/22:0x`，差约 15.6 小时，
疑似被纠正过），所以上面的**绝对时刻只能当相对顺序参考**；但 `413 次` 与 `~97 s` 周期
是同一批事件的计数，不受影响。

三条纪律，优先级高于 §9 的全部结论：

1. **"能连上"不等于"稳定"**。§9 每个臂的观测窗口只有 30~60 s，正好短于这个 96 s 必死周期，
   所以"隧道=1、baidu 通、26-A 204"这类判据都没资格叫修好。以后每臂必须跨过 **2 个 96 s 周期
   （≥200 s）** 仍在连、且期间不产生 828，才算"连上"。
2. **判机器干净不能只看瞬时值**。`Get-NetRoute 0/0`、`nrpt`、`Get-VpnConnection` 在自动重拨的
   两次循环之间恰好会显示"正常"。必须查 `RasClient` 的 dial 计数与相邻间隔：稳定 ~97 s = 还在循环。
3. **副作用要认账**。重置之后 WLAN 的 `InterfaceIndex` 由 6 变 10，DNS 变成 DHCP 下发的
   `192.168.1.1,192.168.0.1`（`netsh interface ip show dns` 写明 "configured through DHCP"）。
   我一度把这两处归因给"VPN 装拆重排编号"，那是错的，实际来自用户的网络重置；
   脚本里"默认路由只剩 WLAN idx=6"这类判据应改成按 alias 匹配，别写死编号。

我的两处操作失误也记在这（都属 [[feedback-never-hog-machine-network]] 的红线）：
杀掉 run 26 脚本前没清 `debug-cmd.txt`，残留的 `connect` 被随后手工启动的 app 直接消费，
**真实拨了一次号**（`debug-out.txt`：`发起前状态=Disconnected, 连接请求=Ok, 实际状态=Connected`）；
以及在发现 828 循环之前，没把"是否存在自动重拨"列进收工检查。

### 10.6 ★★ 96 秒掉线的机制找到了：外层 socket 被对端拒绝 ⇒ OS 自己重启 VPN

先遣项目 **docs/93** 已经把同一条风暴钉死过，机制出处是微软官方答复
（Learn 问答 *VPN Plugin framework and detection of closed peer connection*）原文：

> **"The OS will detect that the outer socket has been closed and will automatically restart
> (you'll get a new connect call)."**

docs/93 的单变量：把出站包灌进外层传输 ⇒ 外层 socket 报错 ⇒ OS 拆通道 ⇒
**全新 pid 重新 Connect、从不回调 `Disconnect`**；灌包侧 8/8 臂 churn，
关掉灌包侧 4/4 臂 `Connect=1`。docs/79 进一步给出可用的外层取值：
`udp` + 黑洞 `192.0.2.1:9` ⇒ 45/90/60/60/60 s 稳定。

对着我们的形状看，两处都对得上：`20226` 的发起者是 **SYSTEM** 不是用户，
`20225/20226` 成对反复出现 ⇒ 不是"连接失败"，是**平台自己拆了再拨**。
而我们的外层 socket 一直是 `auto` ⇒ **订阅里第一个节点 IP**、端口 53 ——
节点机器的 UDP/53 多半没人监听，一次 ICMP port unreachable 就足够被判"对端关闭"。

**1.0.25 落的四处改动**（三处防护 + 一处仪表）：

| 位置 | 改动 | 为什么 |
|---|---|---|
| `ClashVpnPlugin.ResolveOuterTarget` | `auto` ⇒ 黑洞 `192.0.2.1`（RFC 5737 TEST-NET-1），旧行为改为显式 `node`；默认端口 `53` ⇒ `9`(discard) | 黑洞到网关即丢弃、**无应答也无 ICMP 回程** ⇒ 外层 socket 永不报错；仍是公网地址 ⇒ run 21 的排除路由归属不变（这条要实测复核，不靠推理） |
| `ClashVpnPlugin.GetKeepAlivePayload` | 照 sample 写回 `VPN_CONTROL_KEEP_ALIVE`(=3) 字节；计数 + 记录间隔；整段包 try/catch，异常绝不逃出平台回调 | 官方 C# sample 的 `VpnPlugin.cs:871` 就是这么做的；旧实现申请了 Send 池的 buffer 却**只改 Length 不写字节**，平台拿不到合法 keep-alive 就可能判定通道死亡。同时它现在是**仪表**：`距上次 X s` 直接量出平台的超时节奏 |

快照 `dataface-plugin.txt` 新增 `SessionSeconds=` / `KeepAlives=` 两行，
断开日志新增「会话存活 X s，keep-alive 索取 N 次」—— 下次不必再靠事件日志反推。

发现**越过容许值的 dial** 或**窗口内出现 828** ⇒ 立刻 `rasdial ClashUWP /disconnect`
+ `rasdial ClashUWP /delete`。app 内的哨兵只覆盖"已连接"那一段，
平台在两次会话之间自己拨的号它看不见，所以这道闸必须在外面。

2. 连 IP 字面量 `https://223.5.5.5`（不需要解析）也 000/10 s 超时 ⇒ 不是单纯 DNS 故障，
   是**路由侧**把宿主的包送进了一个不应答的地方。
3. 看门狗自己探 `223.5.5.5:443` 依旧 OK ⇒ **插件自己进程的流量不代表宿主**：
   隧道塌回物理网卡时，这个 IP 物理可达（run 32 的直连基线同一命令 `dnsip=404` 就是证据）。
   判据一量的是"这个地址可达"，不是"别的应用还在走我的隧道"——**它结构上就看不见这个故障**。
4. 断开瞬间（01:16:38）整机立刻复活（01:17:19 直连 baidu=200/0.083 s）
   ⇒ 病灶确实在我们下发的策略上，且**只走平台级断开就能干净收掉**（判据⑤逐字回到基线）。

这与 run 30 的"整机没了但没人断开"是同一件事的两种写法：30 那次是**我们删 profile 删早了**
制造的残留；31 这次是平台侧把会话的一半拆了、却仍记 `CONN=1` 且不回调我们的 `Disconnect`
（sessions 日志到 seq=18 都没有 `evt=disconnect`）。两次都不是"内核坏了"，而是
**宿主流量与隧道脱钩**，而我们的判据里没有一列能代表宿主。

⇒ 由此定死三条（组件 1.0.17 已实现，见 `SessionWatchdog` 类注释）：

1. **判据二 · 整机口径的 fake-ip**：每轮让**系统解析器**查 `www.google.com`，
   答案必须是 `198.18.x.x`。这是"只有隧道活着才可能成立"的形态 —— 直连解析给的是
   污染真 IP（本轮基线实测 `2001::1`），隧道 DNS 死了则报错/超时，两种坏形状都判 NO；
   连续两轮 NO 且已过 30 s 宽限期才拆。另有两个**弃权**条件必须写进心跳而不是猜：
   `dnsInTunnel=0`（解析不进隧道，fake-ip 无从出现）、`selfSplitTunnel!=0`
   （本包被 filter 拆到物理网卡，我们自己的解析结果代表不了宿主）。
2. **判据三 · 内核控制器 `/version` 只作归因，不判死**。控制器活在插件自己进程里，
   拿它判死等于拿自己量自己；Docs/08 §10 又记录过本包回环 REST 在某些臂里"积极拒绝"。
   它的用途是和 fake-ip 列交叉：`内核=OK` 而 `fake-ip=NO` ⇒ 病灶在路由/接口侧，不在内核。
3. **宿主侧深度快照进循环**（`.local/snap32.txt`）：故障再现时同一行里既有
   "哪个接口在收这个前缀"，也有"应用通不通"，#20 的归因不再靠事后猜。

顺带修掉一个**取证口径本身的错**：v1 快照用 `Get-NetAdapter -InterfaceIndex` 给路由的
ifIndex 配接口名，隧道明明活着（`198.18.0.9`、`google=204`、根 NRPT 在）却报
`ROUTE 223.5.5.5/32 n=1 [45:已消失] / VPNADAPTER n=0` —— `Get-NetAdapter` 的 CIM 视图
**不包含 VPN 的 Ppp 型接口**，`Get-NetIPInterface` 才看得见（`45:ClashUWP:Connected ip=10.7.0.2`）。
⇒ `resid()` 里"幽灵路由 = 路由挂在 `Get-NetAdapter` 数不到的 ifIndex 上"这个口径，
**只在断开之后成立**（断开后隧道接口才真的消失）；连接期间读到的"幽灵路由"就是隧道自己的路由，
不能当残留。快照 v2 一律改用 `Get-NetIPInterface` 的 ifIndex 表。

还有一个 profile 计数口径的坑，run 31 收尾时没发现、run 32 开局暴露：
UWP 包的 VPN profile 存在**包自己的** `LocalState\rasphone.pbk`，
`Get-VpnConnection -AllUserConnection` 读的是系统存储 ⇒ 两边不一致。
run 31 报 `profile=0`（系统侧确实干净），而 app 的 agent 侧一直能看到
`profile 数=1 [ClashUWP] ConnectionStatus=Disconnected` —— 那是产品正常留档
（arm 收尾走的是 `disconnect`，不含删 profile），14 分钟内也没有任何重拨。
两个口径都要记，只信一个会得出相反结论。

**根因（官方口径 + 先遣项目实测双向对上）**：`Encapsulate` 里
`VpnPacketBufferList.RemoveAtBegin()` 只是把 buffer **从列表摘出来**，
平台并没有收回它 —— 官方对 `IVpnPacketBuffer` 的所有权写得很直白
（先遣项目 docs/105 §4.1 引 sample 注释原文）：

> "…must eventually be returned to the VPN platform (i.e. via IVpnPlugIn.Encapsulate or IVpnPlugIn.Decapsulate)"

我们的数据面在插件内被 mihomo 消化，**没有封装结果可交**给第三个参数
`encapulatedPackets`（那个列表的语义是"交给平台经 outerTunnelTransport 发出去"，
硬塞等于把每个出站包 UDP 打到外层目标 —— 黑洞地址白占上行，还会撞上 10.6 那条
"外层 socket 被对端拒绝 ⇒ OS 自己重启 VPN"的老病）。于是旧实现摘出来拷一份就撒手，
`send` 池被逐包借空 ⇒ 平台**静默停止交付出站包**：会话照记 `Connected`、不报错、
不回调 `Disconnect`。这正是"其他应用连不上外网"的最终形态，而且它和
run 30 的"删早了制造残留"是两种病：那次是收尾不干净，这次是**跑着跑着数据面自己没了**。

先遣项目 mode 80 已经把归还的两个动作分工测清楚了（逐字）：

- `AppendVpnSendPacketBuffer` = **归还 buffer 给平台池**；
- `FlushVpnSendPacketBuffers` = **提交并送去 transport**；
- "不归还 → 平台 send 池被借空 → 之后一切 `RequestVpnPacketBuffer` 永久返回 `0x8007045B`
  （`ERROR_NO_SYSTEM_RESOURCES`）"；
- "不 Flush → 包不会被送去 transport，达到「在插件内终止」的效果"。

⇒ 正确组合对"在插件内终止"是 **只 Append、不 Flush**。

**修复（组件 1.0.18 / 1.0.30）**：

1. `Encapsulate` 对**每一个**摘出来的 buffer 调 `TryReturnSendBuffer()`，位置紧跟
   `_encapsulatedPackets++` 之后 —— 刻意丢掉的组播/广播包也在归还之前，否则
   这些包继续漏池子。归还失败**只计数绝不抛出**：`Encapsulate` 是平台同步回调，
   从这里抛出去会让整个会话被平台拆掉，比"少还一个 buffer"严重得多。
2. `settings.txt: encapReturn` 留三档做单变量 A/B：`0`=旧行为（只为反向复现留档）、
   `1`=Append 不 Flush（默认，官方正确组合）、`2`=Append+Flush（判别臂）。
3. 心跳新增 `ret=` / `retFail=` / `injFail=` 三列，`ret` 与 `encap` **必须同步涨**：
   一旦分叉就是"包进来了、buffer 没还"，这个形状下次不用等四臂才能认出来。
4. 对称补 receive 侧两个漏：超 MTU 那支旧代码直接 `return` 把借来的 receive buffer
   撒手（同一个病，只是配额还没撞上），现在置 `Length=0` 原样 Append+Flush 还回池子；
   `Inject()` 改为返回 `bool`，泵失败时**丢这一个包 + 背压 20 ms**，绝不退出泵
   （退出泵 = 回程永久断 = 和黑洞无法区分），也绝不热转。

**头条判据（run 33 唯一的成败线）**：`encap` 越过 7188 且 google 仍是 204，同时 `ret≈encap`。
过了 ⇒ 归还生效、定性成立；**若仍停在 7188 而 `ret` 已经跟上** ⇒ "Append 不 Flush"
并不等于把 buffer 还给池子，立刻转 `encapReturn=2` 做判别臂 —— 两种结果都是结论，
所以这条同时是修复验证和归因验证。本臂另加一条流程改动：**故障即时取证**
（每轮先用便宜的 google 码 + fake-ip 判一下，这一轮变坏就当场跑深度快照并落心跳原文），
因为看门狗要连续 2 轮才判死，等它收尾时现场已经被拆掉了。

**为什么 Append 不算归还（官方 remarks 里其实写了入口，先遣项目已逐字抄下）**：

> docs/65:129 引 MSDN： "The VPN framework will then send the IVpnPacketBuffer objects in
> *encapsulatedPackets* via one of the transports specified during Connect **and will clean up
> the remaining IVpnPacketBuffer objects in *packets***."

⇒ 平台在 `Encapsulate` 返回时回收的是**还留在 `packets` 里**的 buffer。docs/105 §4.4 又把
Append/Flush 的分工说死了："`AppendVpn*PacketBuffer` 只是**入队**，必须调用
`FlushVpn*PacketBuffers()` 才真正发出"；docs/13:216 同口径："攒批只能攒在 `Append` 到
`Flush` 之间"。所以"摘出来 + Append + 不 Flush"= buffer 被通道的待发队列一直占着，
和撒手不还是同一个后果。docs/65 对官方 sample 的审计（A1）说的正是这件事：
"Sample 把 `packets` 全部 `RemoveAtBegin()` 取走…既不填 `encapsulatedPackets`，
也不让平台回收 `packets` … **脱离平台对缓冲池的生命周期管理**"；docs/75:266-270 也写：
"官方 sample 在 `Encapsulate`/`Decapsulate` 里不归还会直接把缓冲池耗尽——自研时必须显式归还"。

**两条能回池子的路，代价差别很大**：

- **档 2 = Append + Flush**：先遣项目的吞吐基线就是这条（`P3-吞吐基线-2026-10-04.md:52-58`：
  30 s `sent=502378`、`17380 pps`、`97.33 Mbps`，无停摆）⇒ 大概率能越过 7188。
  但 Flush 的语义是"提交并送去 transport"，等于把机器每个出站包**再 UDP 抄一份**打到外层目标
  （我们是静默黑洞 `192.0.2.1:9`，不泄漏内容但上行翻倍）。而且 docs/93 记过这条路的 P0：
  一旦外层 socket 收到 ICMP unreachable，"OS will detect that the outer socket has been closed
  and will automatically restart" ⇒ 直接回到 run 24 之前那种 413 次重拨风暴。
  ⇒ **只作判别臂，不作产品形态**。
- **档 3（组件 1.0.19 新增，改为默认）= 压根不摘列表**：只遍历 `packets`、深拷贝喂内核，
  返回时列表原样留着，让平台按那句 remarks `clean up the remaining IVpnPacketBuffer objects`
  自己回收。零 Append、零 Flush、零外层传输代价 —— 这是唯一"在插件内终止"与"回池子"能同时成立的形态。

**实现时撞到的一个投影事实（别再按文档想当然）**：`VpnPacketBufferList` 在本工程
（CsWinRT + TFM 10.0.26100）的投影成员实测只有
`AddAtBegin / Append / Clear / RemoveAtBegin / RemoveAtEnd / Size / Status / GetEnumerator`
—— **没有 `GetAt`、也没有索引器**（它不是 `IVector<T>`，而是自定义的 `IVpnPacketBufferList`），
所以档 3 只能用 `foreach` 遍历，写 `packets[i]` 直接 CS0021。
口径存在 `.local/ifc34.txt`（`[Reflection.Assembly]::LoadFrom(Microsoft.Windows.SDK.NET.dll)`
列成员），臂脚本 `run-test34.sh` 的头部也抄了一份。

顺带修了本臂暴露的两个观测缺陷：`MAXENCAP` 只从心跳取，判死后心跳被 `TRIP` 文本覆盖会偏低
（run 33 报 6841 而权威终值是 7188）⇒ run 34 起结账一律以 `dataface-plugin.txt` 的
`Encapsulated=` 为准；压力源也从"手工外挂 curl"改成写进脚本（3 路并行、`trap` 收工必杀），
这样"撞到配额"是可复现条件而不是运气。
