# Docs/55 · 切订阅改走「先断开 → 后修改 → 再重连」（1.0.109~1.0.110）

日期：2026-10-24。用户指令原文：**「修复代码，更换订阅遵循"先断开、后修改、再重连"的流程。」**

★ 本篇跨两个版本：**§一~§七 = 1.0.109**（三段式本身，已装机）；**§八 = 1.0.110**（回读第一段时抓出的"无会话"冒充，改判据 + 新增 `SessionStateUnknown` 一档）。

★ 这条是**对 [Docs/46 #3](46-删前台非官方hook-连接切换断开三路径对齐官方-1.0.93.md) 的反向修订**：1.0.93 那一批为了对齐官方 sample，把切换路径里"先拆旧会话、等它落地、否则拒绝新连接"那道 `EnsureTornDownAsync` 当成非官方 hook 删掉了，理由是"官方没有切换这个动作，旧会话完全交给平台"。装机之后这条的代价变成两笔实测（§一），而官方文档侧对"会话期间动 profile 存储"给的正是**禁止**口径（§二）⇒ 本批把它装回去，并且把顺序钉死成三段：**只拆会话、不删条目 → 在没有会话的时刻改 → 只有真拆掉过才重连**。

## 一、症状定位（不是猜的，是读出来的 + 一手行）

1.0.93~1.0.107 的切换路径三段各在干什么：

| 相位 | 旧实现 | 问题 |
| --- | --- | --- |
| 判"有没有会话" | `SwitchToSubscriptionAsync` 只读 `FindActiveSessionAsync`，用来回答"有没有 / 是否已在这条上" | **读到了却什么都不做** —— 旧会话继续挂着 |
| 改 | `SubscriptionManager.ActivateAsync` 紧接着写 `config.yaml`、记 `subActive`、热重载、`SyncSystemProfilesAsync("切换")`（往 profile 存储 Add/Update 整份清单） | 这些写入**全发生在活动会话期间** |
| 拨 | 直接对目标 profile 发一次 `ConnectProfileAsync` | 旧半起半落的会话与新请求并发 |

于是"改了等于没改"：[Docs/52 §五.①](52-会话期间不往profile存储写条目-Add加Update全局闸加欠对账台账-1.0.101.md) 那批一手行就是切订阅那一次里跑出来的 ——

```
07:20:00.292 profile-sub-sync 切换对账：订阅 3 份 + 基础 profile 1 条，新增 0 / 更新 0 / 已就位 0 / 跳过 4 / 失败 0；仍欠：…
07:20:00.087 profile-sub    订阅profile[addbranch-localtest] 待新建但本包 [iKuuu_V2] 状态=Connected，跳过（会话期间不写存储，断开后自动补）
07:20:49.243 profile-sub   订阅profile[addbranch-localtest] 新建=Ok     ← 要等 284 s 后的边沿那一轮才落地
```

用户报的"换了订阅、面板条目没跟着动"就是这条链的末端观感。更糟的一半是 [Docs/45 §八.3](45-切换订阅后ConnectionStatus读数永久抛0x80070006-断开变哑弹.md)：那条至今不可自愈的僵尸条目，诞生窗口里"活动会话期间往 profile 存储 Add 一条"这个形状**正是切换这几秒**（n=1，因果仍未证 —— 本批只把它从"会发生"改成"结构上不会发生"，不宣称修掉了中毒）。

## 二、官方口径（原文与链接在 Docs/45 §九.2/§九.3，这里只落点）

1. **Intune / VPNv2 已知问题**：「在分配新 VPN 配置文件的同时删除活动 VPN 配置文件」「设备同时处理对 VPN 配置文件的多个更改」都会**导致失去 VPN 连接**；那边甚至给了"格式差异导致每次都删了重建 ⇒ 掉线"的真实事故形状。
2. **Windows 升级指引**：升级系统前先断开 VPN 并关掉 VPN 软件 —— 同一句话的另一种主语：**动系统之前把会话收干净**。
3. **KB2826164**：rasman 的断开流程失败 ⇒ 连接显示仍在、不重启再也拨不上 ⇒ "拆不干净就停手"不能改成"拆不干净也照改"。
4. **官方 sample 的建模**：`VpnPlugin.cs:1509` 找的是"我自己家族名下 `ConnectionStatus == Connected` 的那一条"，`MainPage.xaml.cs:80` 写"There should be zero or one of these at all times" ⇒ **至多一条**，没有"两条会话并发过渡"这种官方形状。

⇒ 落点：**写入与拨号都必须落在"没有会话"的时刻**。1.0.101 的写入闸是这个口径的"守"，本批是这个口径的"攻"——不靠闸去欠，而是制造那个时刻。

★ 一条要说清的分工：后台那三路（启动对账 / 边沿对账 / 补账）**继续用"当场不推、欠着、等干净窗口再推"**（Docs/45 §九.3 第 3 条那个社区一手形状），因为它们没有任何权利打断用户正在跑的隧道。用户**亲手点「切到这条订阅」**不一样——他要的就是"这条换成那条"，此时正确动作是把会话收干净再改，而不是把改动欠到下次断开。

## 三、改动

### ① `VpnProfileSetup.TearDownSessionForSwitchAsync` + `SwitchSeat`

[VpnProfileSetup.cs:1366](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnProfileSetup.cs#L1366)／[:1415](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnProfileSetup.cs#L1415)。第一段只回答"台上有没有会话、在哪条上、能不能收干净"，**绝不删条目**（面板上那条订阅还得可点）：

| 返回 | 含义 | 调用方动作 |
| --- | --- | --- |
| `NoSession` | 本来就没会话 | 改，**不重连**（「空壳不拨号」是已验收口径） |
| `AlreadyTarget` | 会话已经切在目标上 | 不拆、改，**不重拨** |
| `TornDown` | 旧会话确认收干净 | 改，改完**必须**重连（不能把用户留在断的上面） |
| `SessionStateUnknown` | ★【1.0.110 · §八】有条目读数不可信，且无法从网络栈指认出会话 ⇒ 有没有会话是**不知道的** | 改，**不拆也不重拨**，回话如实说"没拆隧道" |
| `Refused` | 拆不干净 | **一个字都不改**，整段停手 |

写成枚举而不是让调用方嗅探回话字符串：调用方要靠它决定"改完要不要重连"，而嗅探文本正是 Docs/45 §八.5 那条"声称改了盘、只看自己写的日志行"的同族坑。

`Refused` 的成因（1.0.109 是三种，1.0.110 加第四种）：`Connecting`（官方 `DisconnectOnClick:532` 只在 `Connected` 上发断开，前台也没有取消建连的动词 —— `TerminateConnection` 在插件侧）；`Disconnecting` 等满 `GracefulTeardown.WaitSeconds`=20 s 仍没落地（此时**不再发第二次断开**，只等，用 `WaitSessionDownAsync`）；读数不可信（`EnsureTornDownAsync` 从 1.0.96 起不把"失败的读数"当"没连着"）；★ 中毒条目**且默认路由就在它身上**、对它发断开后 15 s 读数仍不恢复（§八）。

### ② 顺序本身收进 `VpnSession.SwitchSubscriptionAsync`

[VpnSession.cs:172](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnSession.cs#L172)。签名从"自己做切换"改成**接收一个"修改"回调**，由本方法拥有三相位的顺序 —— 顺序写在编排层，正文与账本归 `SubscriptionManager`。整个动作包在 `Interlocked` 的 `SwitchInProgress` 作用域里，`finally` 归零（②③ 里任何一处抛穿都不许把标记留成"永远在切"）。③ 复用 `ConnectAsync` ⇒ 与点「连接 VPN」完全同一条路径（同一个哨兵纪律、同一套中毒复位档位），`IsNoDialResult` 那两个前缀（`未发起=` / `新连接=跳过`）原样有效。

### ③ `ActivateAsync` 把"改"交出去

[SubscriptionManager.cs:252](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/SubscriptionManager.cs#L252)：写 `config.yaml` + 记生效 + 热重载 + `SyncSystemProfilesAsync("切换")` 整块搬进 ② 的回调；1.0.101 那套 `PrepareStoreWriteForSwitchAsync` + `sessionWasTorn` 分支删掉。热重载失败**不拦重连**（会话已经拆了，这时候停手就是把用户留在断的上面），但它的成败照样并进总成败（`ok = reloadOk && switched`），不许报"已切到"假成功 —— 口径同 Docs/35 M8/Q12。异常从②③里冒出去时回话带出口：`（隧道若已断开，点「连接 VPN」重拨）`。

### ④ 删除两个死方法

`SwitchToSubscriptionAsync`（1.0.93 那版）、`PrepareStoreWriteForSwitchAsync`（1.0.101）。`GracefulTeardown.WaitSessionDownAsync` 从 `private` 放开成 `internal`（[GracefulTeardown.cs:308](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Vpn/GracefulTeardown.cs#L308)），供 `Disconnecting` 相位"只等不重发断开"。

### ⑤ ★ 读代码读出来的一处自我拆台：写入闸判据 ③

[ProveStoreWriteSafeAsync](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnProfileSetup.cs#L755) 从 1.0.101 起有三条判据，第 ③ 条是「前台有一次订阅切换在飞（`VpnSession.SwitchInProgress`）⇒ 不写」。**三段式之后这条正好挡住②自己** —— ② 跑在 `SwitchInProgress` 窗口之内，而它要往存储里 Add/Update。1.0.108 装机那一次没暴露，纯粹因为当时三条面板条目"已就位"（`Ensure` 走 `Unchanged` 分支，在问闸之前就返回了）。真到"切到另一条订阅、条目名要跟着改"那一支，③ 会把这次切换自己需要的写入又欠进台账，要等下一次断开才跟 ⇒ **本批要消灭的症状原地复发**。

本批删掉 ③，判据只剩两条真值：① 任一本包条目 `Connected`/`Connecting`（逐条降级读）；② 默认路由落在本包条目上（走网络栈，补①的中毒盲区）。理由写进了方法注释：③ 当年是"旧会话未必收尾"的**近似**，而 ① 段已经用官方那把尺子把这件事证实或证伪了，近似该让位给真值。`SwitchInProgress` 本身留着 —— 轮询那三处让路（回填 / `pendingRealign` / 补账）靠的是它，与闸无关。

### ⑥ 界面提示

`MainComponent` 点下条目那一刻的 hint 从"切换到 …"改成 **`切换到 ……（先断开 → 后修改 → 再重连）`**（[MainComponent.cs:1243](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Frontend/MainComponent.cs#L1243)）—— 用户要预期到"这一下会断几秒"。

## 五、装机顺手钉死的一条：`0x80073D02` 与"第二个 pid"

1.0.106 臂 C 之后，插件宿主挂在清单里第二个 `Application Id="VpnHost"`，于是**装机关窗之后机器上是两个 `ClashUWP.exe` pid**（一手：`-ServerName:VpnHost.AppX…` 与 `-ServerName:App.AppX…`）。`Add-AppxPackage` 在这种情况下直接吃

```
HRESULT: 0x80073D02  无法安装，因为需要关闭以下应用: 8B8CC4F4.ClashUWP_1.0.107.0_x64__4tjvwvefxrz66
```

—— 只关前台窗口不够，**无头宿主也占着包**。规矩写下来：升级装机前 ① `rasdial` 必须是 No connections 且 VPN 接口全 Disconnected（Docs/45 §九.2 第 2 条的硬闸，绝不带会话杀进程），② 再 `Stop-Process -Name ClashUWP`（它会一次带走两个 pid），③ `Get-Process ClashUWP` 计数为 0 才发 `Add-AppxPackage`。本轮按这个顺序走完：装成功、PFN 家族仍是 `4tjvwvefxrz66`、`LocalState` 原样（`Country.mmdb`/`cache.db`/`subscriptions` 都在），装完 `Get-AppxPackage` 读回 `1.0.109.0`（回读盘，不看自己写的日志行）。

## 七、已知代价与没做到的部分

- **连接中切订阅从此会真断一次**。`Connected` 分支要等 `EnsureTornDownAsync` 收干净（最多 20 s）+ 热重载 + 对账 + 重拨，用户视角是"点了之后断十几秒才回来"。这是指令要的语义（改在没会话的时刻），不是回归；hint 文案把预期写在点之前。
- **重连失败不复原旧订阅**。① 拆完、② 改完、③ 拨不出去 ⇒ 用户手上是"没有隧道 + 生效订阅已经换了一条"。回话如实说 `切到「X」未完成` 并给出口（点「连接 VPN」重拨 / 系统设置→VPN）。不做自动回滚到旧订阅：那要在同一次里再拆再改再拨，等于把三段式跑两遍，而失败原因多半正是平台拨不动（Docs/45 那类中毒），第二遍只会更糟。
- **`AlreadyTarget` 不拆会话**：此时若清单里别的条目需要 Add/Update，写入闸①照旧把它们欠给边沿 —— 这是有意保留的（不为一次"你已经连在这条上"的点击去打断健康隧道）。
- **中毒本身没修**，本批只是把最可疑的触发形状从代码里去掉。归零判据仍然是 Docs/45 那一条：装机后**不再诞生**新的 `ConnectionStatus` 永久抛 0x80070006 的条目。现有的 `[星链机场]` 那条按已证结论不会自愈（重启系统 / 打 KB5127648 才是出口，两件都由用户决定）。
- **判据 B/C 未跑**（§四），两支都要拨号或造平台中间态 ⇒ 按 memory 那条"碰隧道要用户点头"，没自己发。判据 D 已用零拨号手段（本地复制一份订阅正文）实机跑通，见 §四.②。

## 八、1.0.110 补漏：第一段的"当前无活动会话"当初是冒充的

发现方式：**回读自己刚写的代码**，不是装机撞出来的 —— 这点要写清，因为上一轮我对着用户说"装机判据过了"，而 §三.① 那个 null 分支的语义是错的。

### ① 漏在哪

`FindActiveSessionAsync`（[VpnProfileSetup.cs:897](file:///D:/fluentapps/repos/ClashUWP/ClashUWP/Backend/VpnProfileSetup.cs#L897)）的谓词是 `IsActiveSessionStatus(StatusOf(pp))`，而 `StatusOf` 对中毒条目回的是 `状态读不出` —— 它**不在** `Connected`/`Connecting` 词表里。于是：

```
条目读数抛 ⇒ 谓词假 ⇒ FindActiveSessionAsync 回 null ⇒ 第一段回 NoSession「当前无活动会话」⇒ 第二段照写 profile 存储
```

也就是"**在一条可能正活着的隧道期间往 profile 存储写条目**"——本批 §一/§二 立起来要消灭的正是这个形状，而它从第一段那句肯定句里漏了进来。1.0.109 写在那一分支上的注释（"读数不可信的条目根本进不了 `FindActiveSessionAsync` 的谓词，所以这里不必为它另写一支"）把这件事当成了安全性，实际是漏洞的自述：进不了谓词≠没有会话，正是 Docs/45/51 那条中毒的形状。本机此刻就有这样一条（`[星链机场]`）。

### ② 为什么不许拿写入闸那两条判据替它担保

[Docs/51 §七.4](51-切换订阅后vpn管理面读数永久抛0x80070006-按条目降级加会话期间不写.md) 两次一手（05:29:24 / 05:31:09）：清单内无 `Connected`/`Connecting`、默认路由在 WLAN —— 判据①②**逐字成立**，`ConnectProfileAsync` 照样回 `AlreadyConnected`。⇒ "默认路由不在本包条目上"是**不充分**判据，不许换成"当前无活动会话"这种肯定句式。
