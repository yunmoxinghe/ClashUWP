# 10 · 前端抽离与前后端分层（app 1.0.35）

> 对象：`ClashUWP/` 前台工程（MSIX 主包）
> 起因：09 号审计里 P1/P3 两条都指着同一件事 —— **UI 组件里藏着会自动连 VPN 的代码**。
> `MainComponent.cs` 1262 行只有 30 行是界面，其余 1230 行是 dump、探测、健康哨兵、
> debug 命令回路、mihomo 控制器，还通过 `Action<string> setStatus` 反向持有 UI 回调。
> 性质：**结构重构**，不改变数据面、不改默认档、不碰平台 API 的调用形态。

---

## 1. 为什么选「工程内分层」而不是「新建前端工程」

用户选的这条，理由记下来免得下次重新讨论：

* 打包链一个字不动。`ClashUWP.csproj` 里那 40 行注释（`PublishAot` +
  `CsWinRTMergeReferencedActivationFactories` + `IncludePublishItemsOutputGroup` +
  清单 `inProcessServer` 必须填 `ClashUWP.dll`）每一条都是实测换来的坑。新增工程要
  复验 AOT 能不能把新 assembly 收进包 —— 上一轮 0x80073CFB 就是包结构没验干净。
* `GracefulTeardown` 是插件工程里的 `internal`，靠 `InternalsVisibleTo("ClashUWP")`
  暴露给前台。搬家就得多改一处授权，而它偏偏是"拆 VPN 不留孤儿 NRPT"那道闸的入口。
* 组件必须走 PackageReference（本地 feed）而非 ProjectReference，这是 CsWinRT
  Authoring.targets 覆盖 `GetTargetPath` 导致的既成事实；再加一个工程只会多一套
  版本同步负担（插件改一行就要 pack + 抬版本 + 改引用，见 09 §10）。

结论：**逻辑边界用目录和可见性表达，物理边界留给平台强制的那个（app / vpn 组件）**。

## 2. 分层规则

```
ClashUWP/
  App.cs                     入口，只做两件事：起探针、起应用
  Frontend/MainComponent.cs  界面：画状态 + 把用户意图转成一个后端动作
  Backend/
    Diagnostics.cs           启动装配（本次进程内只装配一次 + 两个探测串行）
    StartupProbe.cs          进程启动探针（审计 P3 已修）
    ProfileDump.cs           profile 清点：落盘版 DumpAsync + 文本版 StatusTextAsync
    StartupProbes.cs         selftest / dataface 两个小路由探测
    HealthMonitor.cs         健康哨兵（Arm / Cancel）
    DebugCommandLoop.cs      LocalState 文件调试回路与命令表
    VpnSession.cs            ★ 前端唯一可调的会话动作入口
    LocalState.cs            诊断文件读写原语
    Mihomo/MihomoController.cs  mihomo REST 控制器包内客户端
  Vpn/VpnProfileSetup.cs     平台 API（建/连/断/删 profile）—— 原本就是服务，未动
```

依赖方向是单向的：`Frontend → Backend → Vpn/platform`。三条硬规矩：

1. **后端不持有 UI 回调**。`Action<string> setStatus` 全部收回前端；后端只返回结果字符串或抛异常。
2. **异常文案的翻译只在前端**。只有前端知道该显示什么；后端不猜。
3. **会话动作只有一个入口** `VpnSession`。UI 按钮和 debug 回路都调它，
   「连之前必须武装健康哨兵」这件事固定在方法里，不再靠调用方记得 ——
   漏一条路就等于那条路没有黑洞保护。

## 4. 逐字没动的部分（等价性清单）

* 所有文件名与闸门：`probe.txt` / `profile-dump.txt` / `selftest.txt` / `dataface-v4.txt`
  / `dataface-plugin.txt` / `dataface.txt` / `health.txt` / `debug-cmd.txt` / `debug-out.txt`
  / `dataface-sessions.txt`，写入模式（ReplaceExisting vs OpenIfExists+Append）不变。
* debug 命令表与参数口径（含「参数保留原始大小写」这条网卡名坑）、消费即删、
  1 s 轮询、异常只进结果文件不让循环死掉、`watchdog-off` 依然不存在。
* 探测的小路由（`203.0.113.0/24` + `8.8.8.8/32`）、`RequireVpnClientAppUI=false`、
  连接用新鲜回读对象、断开后过 `GracefulTeardown` 闸才删 profile。
* 健康哨兵的全部判据：10 s 一轮、连续两轮国内 IP 不可达才判黑洞、非本次发起的
  dial 阈值 1、硬上限 1800 s、断开后删 profile、前置"隧道真 Connected 才进判定"。
* 控制器全部 REST 口径：`UseProxy=false`、只走 `PATCH /configs`、`/logs` 先抬 debug
  再挂流并在 finally 恢复、手写 JSON（AOT 下反射序列化会抛）。
* 插件工程与 `ClashUWP.Vpn` 包版本：仍是 1.0.22，数据面一行没改。

## 5. 有意改变的三处

1. **审计 P3 修掉了**：`App.Main` 不再在 STA 主线程上
   `GetProfilesAsync().AsTask().GetAwaiter().GetResult()`。探针丢到线程池
   （`StartupProbe.Start`），并改成**分两段落盘** —— 进 Main 先写一次
   `Step=main-entered`，跑完再写全量。代价是 `probe.txt` 可能晚几十毫秒出现，
   换来的是入口路径不再有死锁形状。
2. **哨兵武装收进 `VpnSession`**：UI 与 debug 回路各自 `Arm()` 的重复代码消失，
   `Cancel()` 顺带把 `_healthCts` 置空。调用顺序与原来逐字一致（先武装再连 / 先解除再断）。
3. **写盘收敛到 `LocalState`**，并显式区分 `WriteTextAsync`（会抛，调用方兜）与
   `WriteTextQuietAsync`（不抛，旁路诊断专用）。原先这两类混在 9 处手写
   `CreateFileAsync + FileIO.WriteTextAsync` 里，谁是旁路谁是主流程全靠上下文猜。

顺带清掉一个长期存在的 CS8600（`MihomoController` 里 `GetString()` 可空值赋给
非空 `string dst`），现在前台工程 Rebuild 是 **0 警告 0 错误**。

> 分层在这里的收益很实在 —— 日志点位是按"哪个文件负责哪件事"逐个落进去的

> 换到没分层之前，那一半得写进 UI 组件里。见 [`Docs/11-滚动日志.md`](11-滚动日志.md)。

本轮只做了 `dotnet build -t:Rebuild`（0 警告 0 错误）与逐行搬运比对，
**没有部署、没有发起任何连接** —— 分层本身不改平台调用形态，但"改完还能不能连"
一律要等 Visual Studio 出包后按老判据复验（隧道内 google 204、`encap/ret/flush/rxpend`）。

后端接下来值得动的地方，按性价比排：

* `StartupProbes.RunDatafaceProbeOnceAsync`（244 行）仍是"建 profile→连→打流量→断→删"
  一坨，可以拆成 `SessionHarness`（建/连/断/删 + 闸）与 `EgressChecks`（TCP/TLS/HTTP 三级
  出网判据），后者能直接复用给哨兵 —— 现在哨兵只会 TCP 握手，探不出
  "握手成功但应用层没回来"这种半黑洞。
* `MihomoController` 的六条命令各自 `new HttpClient`，可以收成一个客户端 + 统一的
  「非 2xx 也要把响应体带回来」出口；`delay` 那条是判节点最快的路，值得提到正式判据里。
* `HealthMonitor` 的判据常量（10 s / 两轮 / 阈值 1 / 1800 s）现在还是 `const`，
  挪进 `LocalSettings` 就能像 `encapReturn` 那样做单变量实验 —— 但必须保持默认值不变。
