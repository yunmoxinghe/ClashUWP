## 一、先把"已经是这个行为"的部分说清楚，别记成新做的

app 内点「使用/启用这份订阅」→ `SubscriptionManager.ActivateAsync` → `VpnSession.SwitchSubscriptionAsync` 三段式（Docs/55，1.0.109 起）：
① `TearDownSessionForSwitchAsync` 拆会话 → ② 台上没会话才写正文/记生效/热重载/对账 → ③ **①真拆掉过就重拨目标订阅的 profile**（[VpnSession.cs:222](../ClashUWP/Backend/VpnSession.cs#L222)）。
当前会话读得出且是 `Connected` 的那一支早已做到"先断旧再连新"（[VpnProfileSetup.cs:1508-1514](../ClashUWP/Backend/VpnProfileSetup.cs#L1508)，走 `GracefulTeardown.EnsureTornDownAsync` 并等落地）。

**没做到的只有一支**，也正是用户这一句要修的：`ClassifyNoReadableSessionAsync` 的第三档 —— 有条目 `ConnectionStatus` 读不出（本机 `[星链机场]` 就是这形状，KB2826164：除了重启不会恢复），又没法从网络栈指认它是会话 ⇒ 1.0.110 定的是"不拆、不拨，账照改"。后果就是那句"点了没反应"：**旧隧道继续在跑，账本却被②改到新订阅上了**，而用户要的"连最后选的订阅"根本没发起。

★ 顺带把 18:12 那次的定性订正一句：那一回是**面板**点的（前台 18:12:26 就 `Suspending` 了，`app.log` 那一段没有 `用户发起订阅切换` 行），本批改的是**app 内**这条路。面板那条路我们收不到请求，先断旧连新是平台自己做的（一手：18:03:14 `会话结束，存活 54s` → 2.5 s 后 `平台发起连接 #2`）。

## 二、"热重载也没成功"这句话里成立的部分，和它的边界

热重载（前台 `ReloadActiveConfigAsync` / 插件 `PUT /configs?force=true`）的能力是**换内核配置**，它换不了系统侧会话：profile 的 `ServerUris`、平台装的路由与 DNS、`CustomConfiguration` 里那个 `subId` 都在会话建立时才生效。所以"切到另一条订阅"这件事，光靠 reload 在结构上就不可能完成 —— 必须**断开系统侧连接 + 重拨目标 profile**。今晚的读数反而说明插件那一步是好的：三次配置变化的连接都 `PUT /configs?force=true -> 204` + `PATCH interface-name=WLAN -> 204`（plugin.log:1034/1369/1403）；前台那次 18:02:07 回的是"新订阅已落盘（内核未连接，下次连接自动加载）"，因为那一刻根本没会话可重载。

⇒ 本批两处改动，一处补"断开+重建"，一处把 reload 从"能单独判失败"降下来：

| 位置 | 改动 |
| --- | --- |
| [VpnProfileSetup.cs:1599-1651](../ClashUWP/Backend/VpnProfileSetup.cs#L1599) `ClassifyNoReadableSessionAsync` 第三档 | 不再原地停手：对**每一条读数坏掉的条目**依次 `DisconnectAndWaitReadableAsync`（发一次平台断开 + 等读数恢复，恢复=那条会话记录真被拆掉，Docs/51 §七.4 的判据）。任一条恢复 ⇒ 升格 `TornDown` ⇒ ③ 重拨最后选的订阅；全不恢复 ⇒ 仍回 `SessionStateUnknown`（不重拨，"后修改"照走），但回话里**逐条带上断开结果**，不许再读成"没会话"。 |
| [VpnSession.cs:186](../ClashUWP/Backend/VpnSession.cs#L186) + [SubscriptionManager.cs:281-306](../ClashUWP/Backend/SubscriptionManager.cs#L281) | 三段式的返回值加第三个字段 `Redialed`（①拆过且③拨出去才为真）；`ActivateAsync` 的总成败从 `reloadOk && switched` 改成 `switched && (redialed \|\| reloadOk)`。**没有重拨的三支（NoSession / AlreadyTarget / SessionStateUnknown）照旧从严** —— 那一刻"配置就位"全靠 reload，失败就是没生效。重拨过而 reload 失败时，回话加一句"隧道已按新订阅重建；原地热重载那一步没成，仅附在下文"。 |

## 三、代价与故意没动的地方（明说）

- **多发断开 RPC**：这一支从前一条都不发。方向上是往"没网"走，与 2026-10-16 那次拆错东西导致整机断网不同向（同一论证见 `ClassifyNoReadableSessionAsync` 头注释）；最坏耗时 = 坏条目数 × 15 s（`DisconnectAndWaitReadableAsync` 默认上限），每次断开还占一次 `ProfileStore` 串行写预算 —— 平台不答时会把这段拉长，装机第一轮要盯 `profile-switch` 与 `profile-store` 两类行。
- **僵尸条目仍拆不开**：`[星链机场]` 这类（rasman transport 被占，原始码 4328）断开后读数不恢复 ⇒ 落回 `SessionStateUnknown`，行为与 1.0.112 一致（不重拨）。这不是本批的回归，是本批把"至少试一次"补上了；出口仍是重启，回话里带系统设置→VPN。
- **`Refused`（`Connecting` 拆不掉）未动**：前台没有取消建连的官方动词（`TerminateConnection` 在插件侧且只管建连尝试；官方 sample `DisconnectOnClick:532` 也只在 `Connected` 发断开），用户也没勾这一支。
- **NoSession（真没连着）不拨**：Docs/30 那批立起来的"空壳不拨号/切个订阅不该凭空拉起隧道"口径不变，且它同样不在用户勾选范围内。
- **面板那条路一行未动**：结构上收不到请求（`VpnChannel` 无 `Disconnect()`、`Stop()` 只回应平台断开），插件侧没有可用来"先断旧"的原语。

## 四、装机判据（下次无会话时按这个跑，判据先写死再动手）

前置：`rasdial` = No connections（有会话时点切换会读到 `Connected` 那支，验不到本批新增的第三档）。

1. **正向**：连着 A（`[iKuuu_V2]` 读数正常）→ app 内点 B「使用」⇒ `app.log` 依次出现 `先断开 [iKuuu_V2]：收尾=干净 …` → `切换对账：…` → `再重连=…受理=Ok`，且总回话以 `已切到「B」` 开头（现有形状，不许回归）。
2. **本批新增那支**：需要一条读数不可信的条目在场（本机 `[星链机场]` 若仍中毒就直接有这形状，不必修它）。点切换 ⇒ `profile-switch` 行必须出现 **`状态读不出且归属指认不出（…）⇒ 照发断开` 或 `断开已逐条发过：[星链机场] 对这条断开=…`**；前者 ⇒ 紧随一条 `用户发起订阅连接 subId=<目标>`，后者 ⇒ 回话明写"本次不重拨"。**两行都不出=本批没生效**。
3. **reload 降格**：制造一次 reload 失败（内核 controller 不可达即可，不碰隧道），且这一次是"拆完重拨"的路径 ⇒ 总回话必须是 `已切到「X」（隧道已按新订阅重建；原地热重载那一步没成…）` 而**不是** `切到「X」未完成`。★ 反向不许回归：没重拨的那三支（断开状态点切换）reload 失败时**仍要**报 `未完成`。
4. 回归项：`profile-recreate` 行尾的 `订阅条目刷新=…`（Docs/57 §五 #1，1.0.112 那批）照出；`启动/切换/边沿对账` 三类行文案不变；`nrpt=0`、死接口路由=0；收工 `rasdial` 无残留会话。
