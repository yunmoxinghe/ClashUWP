## 三、★ 1.0.79 的新发现：哨兵武装后整条静默（1.0.80 修复）

**现象**（1.0.79，pid=5680，07:13 拨号）：`health-arm 武装健康哨兵` 之后，`health` 频道一行都没有 ——
没有进循环、没有黑洞判定、没有 `physical-watchdog`。看上去像"哨兵没跑"，实际是**跑了并且当场死了**。

**根因证据**（1.0.80 加了容错之后，同一个位置第一次读就抛，从此可见）：

```
07:40:55.213 app I health-arm  武装健康哨兵
07:40:55.213 app I session     用户发起连接（已先武装健康哨兵）
07:40:55.271 app W health-precheck 第 1 次读状态异常：COMException: 句柄无效。 (0x80070006)   ← 58 ms 后
07:40:57.427 plugin I health             隧道已建立，进入黑洞判定循环（上限 1800s）
07:40:57.427 plugin I physical-watchdog  启动：每 30s 一轮，10 轮全失败才动手；…
07:40:57.892 plugin I profile-connect [ClashUWP] 发起前状态=Disconnected, 连接请求=Ok, 实际状态=Connected
```

读法：**第 2 次读（约 2 s 后）就通了** ⇒ `0x80070006`（ERROR_INVALID_HANDLE）是**时序性的**，
发生在"平台刚把隧道接口建起来、profile 存储正被活动会话占住"那一瞬间；哨兵恰好在这个时刻起第一拍。

**为什么旧代码一点痕迹都没有**：`Arm()` 是 `_ = RunAsync(token)`（fire-and-forget），
.NET 里未观察到的任务异常**不会进任何日志**，也不会崩进程。旧 `RunAsync` 第一句就是那个裸 `await` 读状态，
一抛 ⇒ 整条链路当场终止、无人知晓。代价是这三轮里所有"哨兵该拦的东西"都没人拦：
黑洞判定、`hardCapSeconds=1800` 无条件断开、前台物理兜底，全部不存在，而界面上一切正常。

**1.0.80 的加固**（`Backend/HealthMonitor.cs`）：

| # | 改动 | 为什么 |
| --- | --- | --- |
| ① | `RunAsync` 拆成**外壳 + `RunCoreAsync`**，外壳只 catch 并 `RollingLog.Error("health-crash", ex)`（`OperationCanceledException` 除外 = 手动断开正常退出） | 让"哨兵死于异常"从此**必然留痕**，不再靠"后面那行没出现"反推 |
| ② | 前置确认每次读走 `ReadStatusBoundedAsync(3000)`：读超过 3 s 直接返回 `StatusUnreadable` | WinRT `IAsyncOperation` 没有可靠的取消手段，**故意放弃**那个晚到的孤儿任务；换到的是"哨兵绝不会被一次不返回的读钉死在第一步" |
| ③ | 前置确认**逐轮 try**：单轮异常只记 `health-precheck` warn 并跳过这一轮，30 轮读完仍读不出才弃权 | 一抛就靠外壳兜底 = 这次连接等于没有保护 |
| ④ | **判据不可信不动手**：`StatusUnreadable` 不算"卡住的连接"，直接跳过黑洞判定与断开，写 `health.txt` 后返回 | 与 `PhysicalNetworkProbe` 同一条纪律；旧写法会把"读不出"当成非终态去 `DisconnectAsync` |
| ⑤ | `RunCoreAsync` 内**每一个 await 补 `ConfigureAwait(false)`** | 武装点在 UI 按钮链上，fire-and-forget 会捕获调用方 `SynchronizationContext`；一条保命的熔断不该依赖窗口还在 pumping |
| ⑥ | UI 3 秒轮询的 `catch { }` 改成 `ui-poll` **边沿出声**（同类错误不重复记，恢复补一行） | `MainComponent` 那条静默 catch 是同一种"吞异常"的写法 |

★ **源码态、未装机**（下一版生效）：`health-precheck` 那条正面证据行原本按 `i == 0` 打，
实测第 1 轮就抛 ⇒ 首轮只有 warn、没有"读到了什么"的 Info 行。已改成按**首次成功读数**打
（并带上此前异常次数）。本轮结论靠后面那行 `health 隧道已建立…` 反推哨兵活着，够但勉强。
★【1.0.81 已装机验】这一条随 1.0.81 上机成立：
`health-precheck 第 1 次读状态=Disconnected（成功 1 次，异常 0 次）` —— 首轮就是正面证据，不必再反推。

★ **没做的那一步（下一批首选，且需要单独判断）**：`VpnProfileSetup` 里
`private static readonly VpnManagementAgent Agent` 是 `0x80070006` 最可疑的来源 ——
官方 sample 是**每次操作 `new VpnManagementAgent()`**，我们的 `StartupProbe` 也照官方那样局部新建。
但这个类约 20 处调用、全是最要命的建/连/断/删路径，**本轮不在装机验收中间盲改**；
1.0.80 的做法是"承认它会同时刻失败，重试 + 限时 + 不动手"。真要动它，得单独一批、单独验。

★★【1.0.81 订正：上面那句"静态缓存最可疑"是错的，本轮现读官方文档 + 用装机数据自己驳掉了】
三条证据：① 官方参考页（winrt-26100 moniker）的类声明原文是
`[MarshalingBehavior(MarshalingType.Agile)]` + `[Threading(ThreadingModel.MTA)]` ——
自由线程对象，"缓存在静态字段上会被公寓/线程绑死"这个前提不成立；
② 1.0.80 那次会话里 UI 的 3 秒轮询走的是**同一个缓存实例**（`VpnSession.StatusAsync` →
`OurStatusAsync` → `Agent.GetProfilesAsync`），整整 1350 s `ui-poll` **零异常**（那条边沿出声是
1.0.80 新加的，"零"是真零）；③ 失败的时刻是 `07:40:55.213` 发起 `ConnectProfileAsync`、
`07:40:55.271`（58 ms 后）哨兵第一次 `GetProfilesAsync` 抛错 —— 只有撞上连接 RPC 的那一读炸，错峰读全好。
⇒ 存活下来的形态是**并发**（连接在飞时枚举 profile 存储），不是"实例过期"。
1.0.81 按这条改：新增 `ProfileStore` 串行层（全进程一个 agent + `SemaphoreSlim(1,1)`），
装机 3 次拨号 + 隧道连跑 300 s + 6 次连点「建/重建 profile」并发压测，`0x80070006` **0 次**、
`profile-store` 排队超时 **0 行**。全文见 **Docs/34**（含"这是唯一存活解释、非已证实机制"的诚实边界）。

## 四、§8-E 定稿：静默通知的 `TimedOut` 只记账

**官方口径 + 实机一致**：`SuppressPopup=true` 的静默 toast 在 `Show` 之后**几乎立刻**回
`dismissed:TimedOut`（横幅显示时机的寿命到期），而条目**仍在通知中心**；
"它在不在"的权威判据是 `Update()` 的返回值（`NotificationNotFound`/Failed），不是回调。
`ExpirationTime` 帮不上忙 —— 官方 Remarks 明写"系统在 `Show` 之后会立即尝试呈现，所以该属性很少用到"，
那条"到期自动移除"的说明是 Windows Phone 8.x 时代的。

**1.0.79（未定稿）实机**：`TimedOut` 被当"真离场"走 30 s 节流补发，但循环每秒重看一次状态，
结果是一条自我循环：

```
07:13:44 toast 启动：每 1000ms 原位刷新 …
07:13:46 toast 状态通知已消失（第 1 次，dismissed:TimedOut，非用户划掉：只按节流补发，不计额度）
07:13:47 …（第 2 次）  07:13:48 …（第 3 次）  07:13:49 …（第 4 次）  07:13:50 …（第 5 次）
```

整段会话统计：**51 次"消失/回调"行 / 52 秒**，即每秒一次 `Hide→Show` 重发。

**1.0.80 定稿**（`Vpn/StatusToast.cs`）：循环里**不再抢先清 `_shown`**，"在不在"全部交给 `HandleDismissed` 判定；
`HandleDismissed` 三分支 —— `UserCanceled` 计补发额度（`MaxReRaise=3`，耗尽后每会话一次引导 / 每天一次引导）、
`TimedOut` **只记一行账、什么都不动**、其余原因才走 30 s 节流补发。整段 1350 s 会话的 toast 全部日志只有三行：

```
07:40:58 toast 启动：每 1000ms 原位刷新 tag=clash-status setting=Enabled 补发上限=3 引导通知=每天一次
07:41:00 toast 状态通知回调（第 1 次，dismissed:TimedOut，横幅显示时机到期（静默通知必然立刻到期）：只记账，通知仍在通知中心）
08:03:26 toast 已撤下状态通知（平台回调 Disconnect）
```

即 **51 → 1**，且 0 次补发、0 次引导通知（用户没划掉，就不该人人收到那条会出横幅的引导）。
