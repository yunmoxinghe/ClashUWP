## 0. 为什么要动：现状的两处代价

1. 清单里第二个 `<Application Id="Plugin">` 没有 UI，只能靠 `AppListEntry="none"` 隐藏，而这个属性会触发
   「无权创建无头应用」（1.0.72 就是这么被迫放弃隐藏的，见 Docs/25）。
   微软自己对无头应用的官方合规做法也是**绕**：造一个空白应用、借它的 exe/dll 填 `Executable`/`EntryPoint`、
   再把 `AppListEntry` 属性删掉（见 [Servicing MSIX store apps for Windows Server IoT](https://learn.microsoft.com/zh-cn/windows-hardware/service/iot/servicing-msstore)）。
   ⇒ 合并之后 `AppListEntry` 这个属性根本不需要出现在清单里，豁免问题由构造消失。
2. 双版本号 + 本地 feed：应用 1.0.74 / 组件 1.0.43，`artifacts/packages` 已堆了 41 个 nupkg，
   并且踩过「同版本不重新拉取 → 主工程吃旧 nupkg」的坑（现在 feed 里没有 1.0.41/1.0.42，
   只有 1.0.40 和 1.0.43，主工程靠 NuGet 的最低版本解析吃到 1.0.43 才恰好对得上）。

## 1. 机制依据（全部现读，CsWinRT 2.3.1）

| 结论 | 证据 |
| --- | --- |
| 非组件工程不注册自己的激活工厂 —— 这才是"必须拆工程"的真根因，不是平台限制 | `CodeGenerator/Generator.cs`：`if (!context.IsCsWinRTComponent() && !context.ShouldGenerateWinMDOnly()) { … return; }` |
| `CsWinRTComponent` 对 `OutputType` **没有门禁**，WinExe 可以开 | `nuget/Microsoft.Windows.CsWinRT.targets:576`：按属性无条件 `Import ... Authoring.targets` |
| 投影规则只约束 **public** 类型 | Learn：`restrictions apply only to public types`；CsWinRT1001/1003/1004/1005/1006 全打在 public 面上 |
| 模块形态（`ClashUWP.dll` + 极小 `ClashUWP.exe` 桩）的开关是 **合并属性**，不是组件属性 | `build/Microsoft.Windows.CsWinRT.BeforeMicrosoftNetSdk.targets`：`Condition="'$(CsWinRTMergeReferencedActivationFactories)'=='true' AND (OutputType Exe\|WinExe)"` 里才设 `NativeLib=Shared` / `CustomNativeMain` / `_CsWinRTEnableStubExeGeneration` |
| ★订正（原判"进不了 payload"是错的）：授权生成的 `ClashUWP.winmd` **会**进 msix payload | 静态推演（`CsWinRTIncludeHostDlls` 的 `Content` 只带 `Pack`、没有 `CopyToOutputDirectory`）当时看着成立，但 `Authoring.targets` 还把**组件工程的 `GetTargetPath` 覆盖成只返回那份 winmd**，而本项目 `IncludePublishItemsOutputGroup=true` 的 publish 路线正是从 `GetTargetPath` 收发布项 ⇒ 第一次 Build 实测报 `APPX0702: Payload file '…\ClashUWP.winmd' does not exist`。解法见 Docs/31 §二的 `ClashUwpDropAuthoringPackagingArtifacts` 目标（只删 `@(Content)` 无效，要删 `ContentWithTargetPath` + `PackagingOutputs`） |
| `CsWinRTAotExportsEnabled` 在 `PublishAot` 下自动为 true ⇒ 组件自包含导出，`WinRT.Host.*` 那一整段分支被跳过 | `CsWinRT.targets:31`；`Authoring.targets:69/94/294` 的 `Condition="'$(CsWinRTAotExportsEnabled)' != 'true'"` |
| 平台只按**包家族名**定位插件，不认 Application Id、不认类名 | 本仓 `VpnProfileSetup.cs:46/127/130` 用 `Package.Current.Id.FamilyName` 写 `VpnPluginPackageFamilyName` ⇒ 合并后建连/取 profile 逻辑**一行都不用改** |

## 2. 执行顺序

### 步骤 1：构建探针（先证伪，不改架构）

★ 订正：实际执行时**没有单独跑这一步**，探针直接并进步骤 2/3 的正式改造一次跑通，
没有出现预期外的 CsWinRT100x。下面的探针写法留作下次改 public 面时的低成本预检手段。

只给 `ClashUWP/ClashUWP.csproj` 临时加两行，用 VS / UwpBridge 的 msbuild 通道跑一次 **Build（不 Publish、不部署）**：

```xml
<CsWinRTComponent>true</CsWinRTComponent>
<CsWinRTEnableLogging>true</CsWinRTEnableLogging>
```

要看的结果：

- 通过 ⇒ 说明当前 3 个 public 类型（`App`、`MainComponent`、`VpnProfileSetup`）里违规项就是预期那几个，继续步骤 2；
- 报 CsWinRT100x ⇒ 把报错清单原样收进本文档，逐条判"改 internal"还是"改签名"；
- 顺手确认 `obj/**/ClashUWP.winmd` 生成出来、且 `$(TargetDir)` 里没有多余文件进包。

探针完**必须 revert**，别把 `CsWinRTComponent=true` 留在还没搬迁的树上（那会让授权器扫全部 public 类型，`GracefulTeardown` 那类值元组暂时无所谓，但 `App`/`MainComponent` 必炸）。

### 步骤 2：文件搬迁（一次性，建议单独一笔提交）

- `ClashUWP.Vpn/*.cs` 共 19 个源文件 → `ClashUWP/Vpn/`，**命名空间一律保持 `ClashUWP.Vpn`**
  （保持它，清单的 `ActivatableClassId` 才是一个字都不用改）。
- 只有 `VpnBackgroundTask` 必须留 public：`public sealed partial class VpnBackgroundTask : IBackgroundTask`，
  成员只有 `public void Run(IBackgroundTaskInstance)` ⇒ 可投影，CsWinRT1003「至少一个 public 类型」也由它满足。
- 其余 6 个现 public 类型全部转 internal（它们在组件里已跑通授权，转 internal 只会更宽松）：
  `VpnPluginConfig`、`DnsEntry`、`DnsConfig`、`AppSplitRule`、`AppSplit`、`SubscriptionReload`。
  （`VpnPluginConfig` 转 internal 后，`CsWinRTIncludes=ClashUWP.Vpn` 这条投影需求同时作废。）
- 主工程原有 3 个 public 转 internal：
  `App`（基类是泛型闭合 `ReactorApplication<MainComponent>`，CsWinRT1004/1006 违规）、
  `MainComponent`（基类 `Microsoft.UI.Reactor.Component` 不可投影，且有 `public override Element Render()`）、
  `VpnProfileSetup`（`Task<string>` 返回值不是 WinRT 类型）。
  `App.Main` 转 internal 不影响 AOT 入口 —— 入口是 `CustomNativeMain` 的 `__managed__Main`，不走平台按 EntryPoint 反射。
- 删除 `ClashUWP.Vpn/AssemblyInfo.cs` 里的 `[assembly: InternalsVisibleTo("ClashUWP")]`（同assembly了）。

### 步骤 3：主工程 csproj

| 项 | 动作 |
| --- | --- |
| `<CsWinRTComponent>true</CsWinRTComponent>` | **加** |
| `<CsWinRTDetectDependentAuthoringWinMDs>false</CsWinRTDetectDependentAuthoringWinMDs>` | **加**（默认 true 会把 NuGet 依赖里的 winmd —— Reactor.Uwp —— 卷进授权元数据链，没必要） |
| `<CsWinRTIncludes>ClashUWP.Vpn</CsWinRTIncludes>` | **删** |
| `<PackageReference Include="ClashUWP.Vpn" …>` + 上面那段"必须 PackageReference 不能 ProjectReference"注释 | **删**（该结论只在跨工程时成立） |
| `<CsWinRTMergeReferencedActivationFactories>true</CsWinRTMergeReferencedActivationFactories>` | **保留**，但注释要改口径：现在它唯一的作用是让 `BeforeMicrosoftNetSdk.targets` 那一支继续设 `NativeLib=Shared`/`CustomNativeMain`/开桩 exe。删掉它 ⇒ 产物变回单一 `ClashUWP.exe`，平台无法 `LoadLibrary`，`inProcessServer` 直接失效 |
| `ClashUWP/nuget.config` | **可删**（本地 feed 只服务 ClashUWP.Vpn；Reactor.Uwp 来自 nuget.org，`artifacts/packages` 里没有它）。`artifacts/packages` 整个目录连同 41 个 nupkg 一起清 |
| `ClashUWP.slnx` | 删 `ClashUWP.Vpn` 工程节点；`<Deploy />` 仍只挂在主工程 |
| 工程目录 | 删 `ClashUWP.Vpn/`（csproj 里那两条"静默规则"注释搬进 Docs，别丢） |

### 步骤 4：Package.appxmanifest

- 整段删掉 `<Application Id="Plugin"> … </Application>`（连带它的 `VisualElements` / `AppListEntry` 纠结）。
- 把 `windows.backgroundTasks` 扩展从 Plugin 挪到 App 的 `<Extensions>` 里，属性照抄不动：

```xml
<Extension Category="windows.backgroundTasks"
  Executable="$targetnametoken$.exe"
  EntryPoint="ClashUWP.Vpn.VpnBackgroundTask">
  <BackgroundTasks>
    <uap:Task Type="vpnClient" />
  </BackgroundTasks>
</Extension>
```

- `<Extensions>`（Package 级）**完全不动**：`<Path>ClashUWP.dll</Path>` + `ActivatableClassId="ClashUWP.Vpn.VpnBackgroundTask"`。
- 清掉【事实 2】那段注释里"必须拆组件"的表述，换成第 1 节那行 `Generator.cs` 依据 —— 那是工具链强制，可用 `CsWinRTComponent` 解除。
- `Identity Version` 抬一位（比如 1.0.75.0），单一版本轨。

### 步骤 5：三个 Tools 离线测试工程改源链接

`..\..\ClashUWP.Vpn\X.cs` → `..\..\ClashUWP\Vpn\X.cs`，共 7 处：
`DnsConfigTest`（3）、`YamlShapeTest`（5，其中 3 个在 ClashUWP.Vpn）、`IpPacketChecksumTest`（1）。
这些工程是把源文件编进自己 assembly，类型转 internal 不影响它们。
`Tools/run-offline-tests.cmd` 里若有工程名引用同步改。

### 步骤 6：验证（全部走 VS / UwpBridge，不自制 ps1 —— AGENTS.md 第 2 条）

1. `Build`（x64 Release）无 CsWinRT100x；
2. `Publish` + 生成 msix，包内应有 `ClashUWP.dll`（原生）+ `ClashUWP.exe` 桩 + `clash_bridge.dll` + `Country.mmdb`，
   **不应有** `ClashUWP.winmd` / 多余 `ClashUWP.pri` / `ClashUWP.Vpn.dll` / `WinRT.Host.*`；
3. 部署后三条硬判据：VPN 平台仍自动注册插件（`VpnManagementAgent` 能列出我们的 profile 并连上）、
   `plugin.log` 出现新的 `插件进程启动 version=…` 行、开始菜单/应用列表只剩一个 ClashUWP；
4. 收工判据照旧：`nrpt=0`、死接口路由=0，没有自动重拨。

★ 1.0.76 的执行情况：第 1、2 条全过；第 3 条只做到"注册层面"（清单摄取、payload、平台仍认家族名、
后台任务宿主身份），`plugin.log` 那行要拨号才有 —— 夜里无人值守不拨（原因与判据见 Docs/31 §四）。
取证别再走注册表 `ActivatableClasses` 那条路，本机查不到，改用 `Extensions\ContractId\…` 与
`Get-AppxPackageManifest`，口径见 Docs/31 §三 的「取证口径纠正」。

## 4. 商店可发型核对表（与上面的改造独立，可并行准备）

**A. 受限能力审批 —— 这是唯一的真门**

- 口径已更新：不再需要"提前联系支持"。上传包时平台检测到受限能力，就会要求在
  Partner Center 的 **Submission options → Restricted capabilities** 页填写"这个能力怎么用、为什么必须"，
  认证人员据此判定；批了才继续走剩下的认证。后续更新一般不用重复申请（除非新增能力）。
  见 [App capability declarations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations)。
- 好消息：`networkingVpnProvider` 在受限能力表里的条目**没有**"不建议声明 / 多数情况不批"那句附加语
  （`userPrincipalName`、`screenDuplication`、`walletSystem`、`enterpriseDeviceLockdown` 才有）。
- 侧载不受此限（Learn 原文：Store approval isn't required to sideload）⇒ 我们现在的自签流程不用改。
- 官方 sample 那句"VPN apps in Windows are curated"（[UwpVpnPluginSample README](https://github.com/microsoft/UwpVpnPluginSample/blob/main/README.md)，
  仓库已于 2026-06-11 归档）具体落点就是这条能力的审批，没有额外的白名单程序。
- 要写的理由素材（现成）：插件用 `VpnChannel.StartWithTrafficFilter` 建隧道、`IVpnPlugIn` 做
  Encapsulate/Decapsulate、`VpnManagementAgent` 建/删自家 profile；mihomo 用户态转发需要 `internetClientServer`
  绑本地端口、`privateNetworkClientServer` 访问局域网。**别写**"需要接管全局路由"这种表述。

**B. 清单/打包形态**

1. 单一 Application（第 2 节）⇒ 不再需要无头豁免；开始菜单入口就是真 UI。**已落地（1.0.76）**。
2. ★ 订正：`Identity` **早就换过**了，这条待办作废。清单现在就是 `8B8CC4F4.ClashUWP` +
   `Publisher=CN=A19C62A9-…`，`ClashUWP/Package.StoreAssociation.xml` 已在工作区（未跟踪），
   里面是商店预留身份 + MSA 账号绑定 ——  Docs/30 §5 那批未提交改动就是这件事。
3. 要动的是签名配置：删 `PackageCertificateKeyFile`（那个指向 `Docked AI_StoreKey.pfx` 的**绝对路径**本身就不能进发布配置）、
   `AppxPackageSigningEnabled`、`GenerateTemporaryStoreCertificate`，改由 `Package.StoreAssociation.xml` 走商店签名；
   注意 MSIX 打包 targets 已经会去 `@(Content)` 里找 `Package.StoreAssociation.xml`，别把它当冗余文件清掉。
   ★ 1.0.76 实测：构建期真正签上去的证书不是 pfx 里那张 `CBDB46DF…`，而是 `A4A67B07…`
   （Subject 的 CN 一致、本机没有私钥、`Get-AuthenticodeSignature`=UnknownError）——
   侧发要按 Docs/30 §5 用本机受信的 `FB3309A6…` 重签才能免 UAC 装上，
   而**换签名证书 = 换包家族哈希** ⇒ 已有 VPN profile 全认不出来，这条必须写进发布流程。
4. 架构：`clash_bridge.dll` 目前只有 x64（Go 侧只出 x64），`AppxBundlePlatforms=x64`。
   只投 x64 合规，但要在 listing 里把设备兼容性写清；arm64 要么补 Go 产物、要么显式不支持。
5. 清单里所有 `<rescap:Capability>` 必须排在 Custom/Device capability 之前（我们现在只有 rescap，位置安全）。

**C. 商店策略里会碰到我们这个形态的几条**

- **10.2.8**：改用户 Windows 设置/体验必须取得用户同意、且只能用受支持的方法。
  ⇒ 建 profile、`ConnectAsync` 拨号、NRPT/路由下发都得是用户点出来的动作；协议激活（`clash://install-config?url=`）
  只填 URL、不静默导入、不自动连接 —— MainComponent 现有的"用户点『拉取并启用』才发请求"正好合规，改造时别为了省事把它自动化掉。
- **10.3.x 可测试**：需要订阅才能跑通的产品，认证会要可用凭据。机场链接/测试账号得准备一份给 Notes to Tester，
  否则第一次提交必挂在"无法测试"。
- **10.2.4 / 10.2.3**：`clash_bridge.dll`、`Country.mmdb` 全在自己包内，合规；不要引入外部安装或下载执行。
- 隐私：产品元数据要挂隐私政策；订阅 URL、节点日志属个人信息口径，`RollingLog` 的热路径禁记原则顺带就是合规资产。
- WACK/`Windows App Certification Kit`：见 [App package requirements for MSIX app](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements)，
  提交前本地跑一遍，`msix` 里缺原生 dll、有托管运行时残留都会在那儿暴露。

**D. 顺序建议**

先做 A（能力理由文案，5 个工作日级别的缓冲在这里，不在代码），并行做第 2 节改造；改造稳定后再动 B 的身份/签名，
最后按 C 逐条自检。真机 VPN 建连判据（隧道内 google 204）与收工判据（nrpt=0、死接口路由=0）在这轮里不能省 ——
清单形态一变，插件宿主是不是还被平台拉起来，只有跑通一次才算数。
