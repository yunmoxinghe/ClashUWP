## 〇、先把模型钉死：面板条目不是平台镜像

`VpnManagementAgent` 给的是四个动词（`GetProfilesAsync` / `AddProfileFromObjectAsync` /
`UpdateProfileFromObjectAsync` / `DeleteProfileAsync`），**全在 `Vpn\ProfileStore.cs:204-225` 后面排队**。
平台不会把本地订阅清单镜像进面板 —— 条目只可能是**我们主动推**出来的。
所以"面板漂了"永远要先问一句：**那一刻有没有进程活着、有没有走到推的代码上。**

改之前，推只有四个时机，全在**前台进程**（插件的 vpnClient 后台任务里这四个动词**一次都没调过**，
本批现读 grep 复验）：

| # | 时机 | 出处 | 推的范围 |
|---|---|---|---|
| 1 | 拉取订阅 | `Backend\SubscriptionManager.cs:185` | **只推当前这一条** |
| 2 | 切/启用订阅 | `Backend\SubscriptionManager.cs:262`（旧） | **只推当前这一条** ← 本批的靶子 |
| 3 | 应用挂载对账 | `Frontend\MainComponent.cs:382` → `SyncSystemProfilesAsync` | 整份清单 + prune |
| 4 | 删订阅 | `Backend\SubscriptionManager.cs:501` 附近 | 那一条 |

## 一、成因：为什么"换了订阅条目却不跟着动"

### 1.1 主因 —— 单推一条追不上一个"清单的函数"

面板条目名不是订阅名本身，而是 `SystemProfileName(p, all)`（`SubscriptionManager.cs:681`）的输出，
它的**输入是整份清单**：不重名 → 用订阅名；重名 → 退化成 host；host 也撞 → 退回 id。

⇒ 后果是反直觉的：**新拉一条同名订阅，改变的是另一条已经在面板里那条的期望名**。
而时机 2 只 Ensure 当前 `id`，永远碰不到那条 —— 于是"切了订阅、面板没动"，
而且要漂到下次应用挂载（时机 3）才被顺手修掉。本机就有这个形状（两份 `iKuuu_V2`）。

### 1.2 次因 —— "跳过（断开后再对账）"这句话没有执行者

`EnsureSubscriptionProfileResultAsync` 对已存在的条目只在 `ConnectionStatus == Disconnected` 才 Update
（`Backend\VpnProfileSetup.cs:664`），`PruneOrphanProfilesAsync` 同一把尺子（`:825`）；
不满足时记一行"跳过（断开后再对账）"。**但"断开后"没有任何一处会重跑对账** ——
调用点只有 1.1 那张表里的四处，断开本身一个都不触发。
⇒ 跳过一次 = 漂到下次重启应用。这句承诺是空头支票，本批 §二.2 补的就是它。

### 1.3 仍然没修的四条（本批刻意不碰，别当成"已解决"）

- **app 不跑仍不同步**：插件侧没有对账。搬到插件进程要付两样代价 ——
  `Connect` 是同步 WinRT 回调（在里面同步等异步是 Docs/09 P3 点名的死锁形状），
  且 prune 变成无人看着就删系统条目（叠加 §1.4）。
- **Docs/45 的读数毒**：切过订阅后本包所有进程读 `ConnectionStatus` 永久抛 `0x80070006`。
  这一条决定了 §二.2 为什么"边沿那一轮不 prune"。
  ★【2026-10-23 订正，Docs/45 §八】形状是**按条目**中毒（坏一条、其余照读），"永久"只对那条坏条目成立；
  且 1.0.96 已把"读不出当没连着放行删除"修掉（Docs/45 修法第 6 条），所以"边沿不 prune"从此是**分工**（删除只留给挂载那一轮），不再是安全兜底。
- **换签名证书＝换包家族哈希**：旧家族自己建的条目能不能删掉**至今没有一手**
  （1.0.79 只是把 prune 的判据从"家族必须相等"放宽成"`IsOurs` 命中就迁移式清理"，并在汇总行标 `[旧家族]`）。
- **Add/Update 回非 `Ok` 只落日志**（缺口③）：UI 不会因为面板少一条而报错，这是刻意的。

## 二、改了什么

### 2.1 切订阅 ⇒ 推整份清单

`ActivateAsync` 里那次"只推当前 id"换成全量对账：

```csharp
// Backend\SubscriptionManager.cs  ActivateAsync（原 :262）
string reg = await SyncSystemProfilesAsync("切换");
```

顺序保持**拨号之前**（原来那句注释"profile 先就位才谈得上连它"仍然成立）。
`SyncSystemProfilesAsync` 本来就包含当前 id 的 Ensure，所以对目标条目行为等价，
多出来的是**其它条目**的 Ensure + 基础 profile + prune。

顺带删掉了因此没有调用方的公开包装 `VpnProfileSetup.EnsureSubscriptionProfileAsync`
（`internal ... ResultAsync` 是同一实现的返回结果版，留着就是死代码）。

### 2.2 会话边沿 ⇒ 补一轮"欠着的"对账（`断开后再对账` 的执行者）

`Frontend\MainComponent.cs` 的 3 秒轮询，在算完 `changed` 的当场合上旗子，在推的位置让路：

```csharp
if (changed && !firstPoll)
    pendingRealign = true;
...
if (pendingRealign && !VpnSession.SwitchInProgress)
{
    pendingRealign = false;
    await SubscriptionManager.SyncSystemProfilesAsync("边沿");
}
```

三个决定各有理由，装机若要改回来先读懂它们：

1. **挂边沿，不挂每轮**：每轮推等于持续往 `ProfileStore` 那把串行闸上排队（Docs/38 §十一）；
   边沿是用户/平台动作的结果，次数有界。而刚被换下/刚断开的那条恰好在这一刻回到 `Disconnected`
   —— 它唯一能被改的状态，§1.2 那句承诺只有落在这里才兑现得了。
2. **`pendingRealign` 而不是当场推**：A 案切换有几秒窗口，窗口里推会跟切换抢同一条 profile；
   但让路时**边沿不能丢** —— 丢了以后 `connectedSub` 稳定在新值上，再也"没变化"可言，
   那条被跳过的 profile 就永远补不上。所以记一次"欠对账"，切换一结束立刻补，**用户这一次动作内闭合**。
3. **边沿那一轮 `allowPrune=false`**：删除判据要先读 `ConnectionStatus`，而 Docs/45 那条毒最容易
   在会话边沿这一刻成立；更糟的是 `GracefulTeardown.EnsureTornDownAsync:185` 现在把
   "读不出来"当成"没在连"直接放行删除（Docs/48 §七 明写这条还没修）。
   ⇒ **补条目安全，删条目不搬**，prune 仍只留给挂载那一轮。
   ★【1.0.111 订正 · [Docs/56](56-边沿对账漏关prune-Docs50判据3从未成立-1.0.111.md)】本条**在代码里从未生效**：
   参数与汇总行文案都写好了，调用点（`MainComponent` 轮询里的边沿那轮）漏传 `allowPrune: false`，
   而默认值是 `true` ⇒ 1.0.95~1.0.110 每条「边沿对账」都在跑 prune，§五 第 3 条判据从未成立。
   这里给的两条理由也一起过期：`EnsureTornDownAsync` 的放行 1.0.96 已修掉（Docs/51），
   prune 自己的条目级闸同样是"读不出 ⇒ 保留"（`VpnProfileSetup` 的 `status != "Disconnected"`）
   ⇒ 不 prune 剩下的理由是**分工**（删条目只归挂载那一轮，边沿只补条目，不跟刚结束的会话抢同一个 RPC），
   不是安全兜底。参数已补，理由按 §五 第 3 条的文案逐字保住。

`SyncSystemProfilesAsync` 的签名因此变成 `(string trigger = "启动", bool allowPrune = true)`，
汇总行前缀跟着变成三种可归因的形态：`启动对账：` / `切换对账：` / `边沿对账：`。
默认值是 `"启动"` ⇒ **挂载那一轮的判据行逐字不变**（Docs/48 §5.2 那份机器契约没动）。

## 五、装机判据（这一批要一次采到的五条）

1. **两类新前缀各至少一条**：`app.log` 里 `profile-sub-sync` 出现 `切换对账：` 与 `边沿对账：`。
   只出现 `启动对账：` ⇒ 本批等于没上机。
2. **边沿补推闭合**：制造漂移 —— 两条**同名**订阅（本机 iKuuu_V2 的形状），app 内从 A 切到 B，
   要看到 A 那一轮 `切换对账` 里 `跳过 ≥ 1`，紧接着**同一次动作内**出现一条 `边沿对账` 且
   对它给出 `更新 ≥ 1`；面板里 A 那条的名字随之等于新清单算出的期望名。
3. **边沿不删东西**：每条 `边沿对账：…` 汇总行末尾必须是 `本轮不 prune（边沿只补条目，删除留给挂载那一轮）`；
   出现 `prune 幽灵 profile：删 N` 且 N>0 而前缀是"边沿" ⇒ 判据不成立，回 §二.2 第 3 条查。
   ★【1.0.111 订正 · Docs/56】本条 **1.0.95~1.0.110 装机期间从未被验过，而且验了也不会通过**：
   参数与汇总行文案都写好了，调用点（`MainComponent` 轮询里的边沿那轮）漏传 `allowPrune: false`，
   而默认值是 `true` ⇒ 每条实际出现的 `边沿对账` 行尾都是 `prune 幽灵 profile：删 N / 留 M`，不是本条要求的
   `本轮不 prune（…）`。一手两行抄在 Docs/56 §二（2026-10-23 23:13:46 pid=1900、23:16:22 pid=8080）。
   之所以十四版没暴露：本批根本没装机，后来装机期又因为它的前置形状（§五 #2 的两条同名订阅）没造出来，
   被整条当成"还没轮到验"顺延 —— 判读法上真正的缺口是"**按 `删 0` 判无害**"读不出"**这轮根本不该跑 prune**"，
   订正与两条口径见 Docs/56 §三。1.0.111 已补参数。
4. **毒没被喂大**：一轮切换里 `0x80070006`、`profile-store … 拒绝`、`本轮放弃` 三类行的次数
   不得比 1.0.91 基线上升（本批明知故犯地多打了 N+2 次 RPC，这条是它的代价账）。
5. **切换没变慢**：`切换对账` 行与紧随其后的拨号发起行之间的间隔，对着 §四 那四个基线数看；
   若明显被推高，改法不是砍对账范围，而是把 `切换` 那一轮挪到 `SwitchSubscriptionAsync` 之后
   （代价：目标 profile 可能还没就位就被拨，会把 Docs/36 那条"CannotFindProfile"重新请回来）——
