## 二、构建期实测：Docs/29 里那条"winmd 进不了 payload"是错的

Docs/29 §1 原本写着「`CsWinRTIncludeHostDlls` 只给 `Pack` 元数据、没有 `CopyToOutputDirectory`，
所以授权生成的 winmd / ProjectPri 进不了 msix payload」。**静态推演，被第一次 Build 直接打脸**：

```
error APPX0702: Payload file '…\bin\…\win-x64\ClashUWP.winmd' does not exist
```

真实链条是：`Authoring.targets` 把**组件工程的 `GetTargetPath` 覆盖成"只返回那份 winmd"**，
而本项目走 `IncludePublishItemsOutputGroup=true` 的 publish 打包路线 —— 那个 `GetTargetPath`
正是发布项的来源，于是 winmd 照样进了 `@(PackagingOutputs)`；而文件此刻还躺在 obj 生成目录里
（复制到 `$(TargetDir)` 那步挂在 `AfterBuild`，排在打包之后）。

修法（已进 csproj，注释就写在属性旁边）：

```xml
<Target Name="ClashUwpDropAuthoringPackagingArtifacts"
        AfterTargets="CsWinRTIncludeHostDlls;GetPackagingOutputs"
        BeforeTargets="_ComputeAppxPackagePayload">
  <ItemGroup>
    <Content Remove="$(TargetDir)$(AssemblyName).winmd" />
    <Content Remove="$(ProjectPriFullPath)" />
    <Content Remove="$(AuthoringTransitiveTargets)" />
    <ContentWithTargetPath Remove="…" />
    <PackagingOutputs Remove="$(TargetDir)$(AssemblyName).winmd" />
  </ItemGroup>
</Target>
```

★ 只删 `@(Content)` 没用 —— 打包读的是 `ContentWithTargetPath` 与发布项，
定位靠 `-verbose` 日志里 `WinAppSdkExpandPayloadDirectories` 那行 "Adding '…ClashUWP.winmd'"。

顺带：Docs/29 §2 的"步骤 1 构建探针"**没有单独执行**，直接并进正式改造一次跑通，
没有触发了 CsWinRT100x 之外的报错。

## 四、功能判据：1.0.76 拨号撞开一个回归，1.0.77 全绿（2026-10-20 04:32–04:38）

### 4.1 合并本身成立，但把 P/Invoke 打进了一坑

1.0.76 那次点连接：平台**确实**按新形态激活到了插件类 ——
`bgtask 插件进程启动 version=8B8CC4F4.ClashUWP/1.0.76.0`、`session L3 隧道接口已建立` 都出来了，
M1 的"平台能不能激活合并后的插件类"到此已经回答：**能**。

紧接着数据面起不来：

```
bridge-start StartMihomoBridge 异常: Method '[ClashUWP]ClashUWP.Vpn.MihomoBridge.clash_bridge_start(
uint8[],int32,int32,uint8[])' requires marshalling that is not yet supported by this compiler.
```

根因不在代码逻辑，在**程序集属性**：`DisableRuntimeMarshalling` 是 `[module: …]` 级别的，
按程序集生效。旧组件工程 `ClashUWP.Vpn.csproj` **没有**这个属性（`git show HEAD:ClashUWP.Vpn/ClashUWP.Vpn.csproj`
现读确认），主工程 `ClashUWP.csproj` 有。源码一搬进来，`[DllImport] byte[]` 这种需要运行时封送的
数组参数就在 NativeAOT 下变成了"不支持的封送"。修法只有官方那一条：**换 `[LibraryImport]` 源生成封送**。
`ClashUWP/Vpn/MihomoBridge.cs` 六个入口全部改成

```csharp
[LibraryImport(DllName)]
internal static partial int clash_bridge_start(byte[] configJson, int length, int mtu, byte[]? mmdbDir);
```

★ 踩到的第二个坑：改完带 `CallingConvention = CallingConvention.Cdecl` 直接 6× `error CS1069`
（`System.Runtime.InteropServices.CallingConvention` 这个转发类型在主工程的引用集里解析不到）。
x64/arm64 只有一种调用约定，写与不写等价，所以删掉；**将来若补 x86 产物必须把这一项加回来**。
`Start / LastError / BoundInterface` 三个包装函数没动，调用点零改动。

### 4.3 进程隔离：合并后到底还在不在（这条把 Docs/29 的前提改成了"条件成立"）

Docs/29 原来写"进程隔离由平台强制、合不掉"。实测口径是**分两段**：

```
04:35:39.954 pid=15504  bgtask 后台任务被平台取消（Canceled）——宿主进程可能被回收
04:35:41.570 pid=5160   app 启动 version=8B8CC4F4.ClashUWP/1.0.77.0
04:35:42.594 pid=5160   connect 平台发起连接 #1 resident=全新内核 pid=5160
```

- **前台在跑时**：vpnClient 激活被送进**已运行的前台进程**（日志里插件行与 app 行同为 pid=15504）。
  机制就是 UWP 的单实例语义：同一 `Application Id` 的激活（含后台激活）路由进现成实例。
  ⇒ 第三节第 6 条那个"三个 mca 身份"只证明可分开激活，不证明运行时分开。
- **关掉前台窗口时**：平台先 `Canceled` 旧会话，随后**另起一个后台宿主**（pid 5160）重拨，
  隧道自己回来了 —— 7 条 `ClashUWP` 路由、NRPT 1 条（隧道自己的），且这个后台进程被平台
  `Suspending`/`Resuming` 来回调度过也没掉线。再启动界面时，激活又路由回 5160（窗口挂到它上面）。
- ⇒ 结论：**"关掉前台 UI 隧道仍在"成立**，代价是一次约 2 s 的平台重拨间隙；
  数据面不会随界面一起死，也不需要为它上 `uap10:SupportsMultipleInstances`（那会把
  in-app AppService 的 CLI 通道从"连到界面进程"变成"另开一个实例"，Docs/13 的设计要重写，
  而收益只是省掉这一次重拨间隙）。这条判据到此关闭，Docs/29 §3 的 M1 / R1 口径同步订正。

### 4.4 仍然没算验过的两件事（夜里做等于白做）

- **可达性判据（隧道内 google 204）本轮不算数**：Verge 在跑，`Meta` wintun 占着
  `0.0.0.0/0 → 198.18.0.2`，我们的 include 又是 `198.18.0.0/16`（和 Verge 的 fake-ip 段重叠），
  插件侧 `net-follow` 观测到的物理网卡就是 `bound_iface=Meta` —— 出口是"隧道套隧道"，
  204 成与不成都不能归因给我们这条线。要定这条生死，得先退掉 Verge 再拨（memory「Local network baseline」）。
- **物理兜底哨兵依旧是已知误判源**：两次会话各起了 `physical-watchdog`（30 s × 10 次 114.114 不可达就拆隧道并
  `DropProfileAsync`），本轮都在 5 分钟内主动断开所以没触发；判据本身没变（探针不绑接口、吃默认路由），

- ★ 全程没写任何碰隧道的 `debug-cmd`，`autoProbe` 仍为 0。夜里那两次拨号是用户明确授权
