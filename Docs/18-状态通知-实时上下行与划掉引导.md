# 18 · 状态通知：通知中心常驻的实时上下行（应用 1.0.66 / 组件 1.0.34）

## 0. 这一批做的是什么

用户诉求（原话）："**行，对齐这里，如果用户划掉的话，再发一个普通通知引导前往设置关闭横幅**"。
"这里"指安卓版 `DynamicNotificationModule`：连上之后常驻一条通知，实时显示 ↑↓ 速率与累计流量。

落地的东西只有一个新的插件侧文件 `ClashUWP.Vpn/StatusToast.cs`，加上三处接线：
计数点、开关、Start/Stop。不碰数据面逻辑，不碰内核，不碰 profile。

## 1. 先说清楚：Windows 上没有安卓那个"位置"

| 候选载体 | 结论 |
| --- | --- |
| 托盘图标 | `Microsoft.UI.Windowing.TrayIcon` 明确不支持 UWP 包；`Shell_NotifyIcon` 要 HWND（Win32 only）。**做不到**。 |
| Live Tile | Win11 已废。**不做**。 |
| 任务栏进度 `ITaskbarList4::SetProgressValue` | Win32 only，包内不可用。**做不到**。 |
| **通知中心一条常驻 toast** | ✅ 唯一能落地的形态，也是用户认可的那条："点开通知中心就行了，和安卓 UX 一致"。 |

## 2. 与安卓逐条对齐（源码存档 `.local/ref/cmfa_notif/DynamicNotificationModule.kt`）

| 安卓 | Windows 这一版的对应做法 | 是不是等价 |
| --- | --- | --- |
| `setOngoing(true)`（没有划掉按钮） | `ToastNotification.SuppressPopup = true` + `<audio silent='true'/>`，划掉后**补发**（限流） | ❌ 不等价，Windows 没有"不可划掉"的语义，只能补发 |
| `setOnlyAlertOnce(true)` + `IMPORTANCE_LOW` 通道 | 同上（静默：只进通知中心，不弹横幅、不响） | ✅ |
| `notify(R.id.nf_clash_status, …)` 同 id 覆盖 | 固定 `Tag="clash-status"` + `Group="clash"`，之后只 `ToastNotifier.Update(NotificationData, tag, group)` | ✅ 官方口径："*Won't reappear as a popup; the notification's data is silently updated within Notification Center*"，且"*Leaves the notification in place within Notification Center*" |
| `ticker(SECONDS.toMillis(1))` 每秒刷 | 一拍 1 s，但**文案变了才调 Update** | ✅（少敲平台，行为不变） |
| `isInteractive` / `SCREEN_ON\|OFF` 门 | **无等价物**：UWP 侧没有"通知中心此刻是否可见"的只读入口，`ToastNotificationManager.GetNotificationHistory` 在 26100 投影里不存在（winmd grep = 0）。用"变了才刷"替代 | ⚠️ 目的达成，手段不同 |
| `contentTitle` = 当前 profile | 第一行 `<text>`：`ClashUWP · 隧道运行中（{订阅 id}）` | ✅ |
| `contentText` = `$uploading/s` / `$downloading/s` | 第二行：`↑ 12.3 KB/s　↓ 4.5 MB/s` | ✅ |
| `subText` = 累计 uploaded/downloaded | 第三行：`累计 ↑ 12.3 MB　↓ 45.6 MB` | ✅ |
| 数据源 `Clash.queryTrafficNow()` / `queryTrafficTotal()` | 插件自己的**隧道 L3 字节**计数（见 §4） | ❌ 口径不同，明说 |

★ 标题里刻意**不放**"已连接 mm:ss"：那一行每秒都在变，会把"变了才刷"变成"每秒必刷"；
安卓的 `subText` 也只放累计。秒数在 `sessions` 日志里有（`alive=`）。

★ 也刻意**不放** `<progress>`：官方标注进度栏只支持桌面端 toast，而且上下行速率不是"完成度"，
硬造一个参考速率只会误导。三行文字才是与安卓一一对应的形态。

## 3. 划掉之后（安卓不用写、我们必须写的那一段）

安卓不需要处理"用户删通知"：`setOngoing(true)` 压根没有划掉按钮，前台服务通知归系统管。
Windows 的 toast 随手能划掉，所以两个信号都接：

① `ToastNotification.Dismissed` 事件 —— 官方定义"*Occurs when a toast notification leaves the
screen, either by expiring or being explicitly dismissed by the user. **Apps that are running**
subscribe to this event.*"，原因取 `ToastDismissedEventArgs.Reason`
（`UserCanceled` / `ApplicationHidden` / `TimedOut`）。
最后那句是关键限制：**进程还在才有事件** ⇒ 只能当快通道，不能当唯一依据。
事件回调在平台线程上，所以它只立一个牌子（`Volatile.Write`），动手的仍然是通知循环，
保证只有一个线程改"当前挂着的那条"。

② `Update()` 的返回值 —— 官方对照表写明"*If the user dismissed the notification, the update will
fail*"，`NotificationUpdateResult` 专门有 `NotificationNotFound` 这一档。
这条**不依赖进程活着**，是可靠判据。

任一命中 ⇒ 用同一 tag 静默补发一条，**并**发一条普通通知（会出横幅）：

```
ClashUWP：状态通知被划掉了
隧道仍在正常工作，划掉通知不影响它。这条状态通知显示实时上下行，被划掉后还会自动补发几次。
想彻底清静：设置 → 系统 → 通知 → 找到 ClashUWP → 关闭横幅，或直接关掉这个应用的通知。
[打开通知设置]   ← activationType='protocol' arguments='ms-settings:notifications'
```

两条限流（都是必要的，不是可选的）：

* 补发一个会话最多 **3** 次（`MaxReRaise`）。第 4 次划掉就彻底放手、这条循环退出 ——
  划 4 次还在回来是骚扰，不是常驻。
* 引导通知**每个会话一次 + 每天一次**（`LocalState\toast-guide.txt` 记最近一次日期）。
  读写失败时按"没抢到名额"处理：宁可少发一条，也不要每次划掉都弹一次横幅。

★ 做不到"一键关闭"：系统不给应用自助改自己通知设置的权限，只能把人送到设置页。

会话结束（平台回调 `Disconnect`）时 `StatusToast.Stop()` 会 `Hide` 掉常驻那条 ——
它讲的就是"隧道正在跑"，会话都结束了还留着就是一条永久谎报。
`Hide` 优先按活对象撤；极端时序（刚 Show 就 Stop）用一个同 tag/group 的空壳去撤，
因为 `Hide` 只认 tag+group，内容无所谓。

## 4. 数字是从哪儿来的（口径，别读错）

`ClashVpnPlugin` 新增 `long _outBytes` / `_inBytes`，只在**已有**的热点位置各加一次
`Interlocked.Add`，不新增任何 IO：

| 计数 | 加在哪 | 量的是什么 |
| --- | --- | --- |
| `_outBytes`（↑） | `Encapsulate` 取包之后，`Buffer.Length`（档 3 与档 1/2/4/5 两条路各一处） | 平台交进来的每个**出站原始 IP 包**长度 |
| `_inBytes`（↓） | 回程泵注包成功之后（`n`）+ 假内核 echo 应答成功之后（`reply.Length`） | 注回本机的每个**回程原始 IP 包**长度 |

因此这两个数：

* **不含**外层 UDP 封装开销（我们的 outer transport 是发给静默黑洞的占位通道，不承载数据）；
* **不等于**内核 REST `GET /traffic` 的代理好速度（那条才是"节点上跑出去多少"）；
* 每会话随其它计数器一起 `Interlocked.Exchange(…, 0)` 归零，所以"累计"就是本次会话的累计。

同一批数也进了取证出口，事后能核对通知有没有读错：

* `sessions` 行的 `evt=disconnect` 尾部追加 `upBytes=… downBytes=… toast=0|1`
  （只在**尾部**加，不动既有列名与顺序 —— 那一行是机器契约）；
* `dataface-plugin.txt` 快照新增一行 `UpBytes=… DownBytes=…`。

★ 为什么不用 `GET /traffic`：那是 WebSocket，插件侧要另起一条 HTTP 客户端并在
AppContainer 内回环 127.0.0.1:9090（可达性本身也**未实测**）。为一个显示用的数字引入
一条新的网络依赖不划算，而隧道 L3 计数已经能回答"这条隧道现在有多少流量在走"。

## 5. 开关

`settings.txt` 新增一行（插件每次 Connect 读一次）：

```
statusToast=1        # 默认开；0 = 完全不发通知
```

对齐的是安卓 `ServiceStore.kt:64` 的 `dynamicNotification`（`defaultValue = true`）。
差别要说清：安卓关掉是退回 `StaticNotificationModule` 那条"只说在跑、不带速率"的常驻通知；
我们没做那条降级形态，**0 就是彻底不发**。理由是 Windows 侧这件事的全部代价与风险都来自
通知本身（划掉会不会补发、插件进程发通知算不算越界），关掉就关干净，留半条只会更难判读。

留开关的原因有两条：① 插件进程到底有没有包身份、通知会不会被用户设置/策略压掉，
**本轮尚未实测**，真出问题一行文件就能退回，不用重装；② 它是每秒一次的平台调用，
与数据面无关，属于"可以随时摘掉、不影响隧道"的那一类。

开关状态进了那条"本次真正生效"的设置日志（`channel=settings`，`statusToast=…`），
所以"实验臂看着切了其实没切"那种坑在这一项上也会被抓到。

## 7. on-machine 验收清单（这批全部是**未实测**项，按下述顺序判读）

前 4 条是"通知到底能不能从 vpnClient 后台任务进程发出来"，第 5 条起才是行为。
读日志一律 `clashuwp-cli logtail plugin 120`（插件进程 → `logs/plugin.log`；
`sessions` 用 `logtail sessions`）。

1. **身份**。`channel=toast` 第一行：
   * `启动：… setting=Enabled` ⇒ 插件进程有包身份、通知可用，继续往下看；
   * `CreateToastNotifier 失败 …` ⇒ 后台任务进程没有身份（或被策略压掉），通知这条路作废。
     退法有两个：`statusToast=0` 认了，或把状态通知搬到前台进程（代价：app 一挂起就不刷新）。
   * `setting=DisabledForApplication` / `DisabledByGroupPolicy` / `DisabledForUser` ⇒ 系统里
     本应用通知被关了，代码没错，去设置里打开。
2. **发得出**。连上之后 1~2 s 内，通知中心（`Win+N`）出现一条
   `ClashUWP · 隧道运行中（{订阅 id}）`，**没有横幅、没有声音**。
   有横幅 ⇒ `SuppressPopup` 没生效（或被系统通知设置覆盖），记录现象再调。
3. **平台没报错**。若出现 `平台引发失败 err=0x…`，说明 Show 被 Windows 拒了，
   这个 hresult 是唯一线索，先抄下来。
4. **绑定成立**（这条最容易静默失败）。制造流量（下载一个大文件），盯 3~5 s：
   第二行 `↑ …/s ↓ …/s` 的**数字要变**。
   如果通知里出现的是字面量 `{statusRate}` 或者一直是初值不更新 ⇒ 绑定名/XML 占位读错了，
   这不是"效果差一点"而是这一项**没做成**，得改回 replace 形态（重新 Show 同 tag；
   代价是条目每次被顶到通知中心最上面，官方对照表写明了这一点）。
5. **原位刷新不挪位**。连续刷新期间，条目在通知中心里**位置不动**（Update 的官方语义），
   且不会每秒重新弹一次。
6. **空闲不敲平台**。停止流量后 30 s，`sessions`/`plugin.log` 里不该再有 toast 活动
   （实现是"文案变了才 Update"，速率与累计都不变 ⇒ 一次调用都不发）。
7. **划掉 → 补发 + 引导**。把那条通知右滑划掉：
   * `channel=toast` 出现 `状态通知已消失（第 1 次，dismissed:UserCanceled）`
     —— 如果 reason 里是 `update:NotificationNotFound`，说明事件没送到（进程/时序），
     靠 `Update` 返回值这条兜住了，这正是它存在的意义；
   * 通知中心里同一条又回来了（还是静默）；
   * 右下角弹出**普通横幅**"ClashUWP：状态通知被划掉了…"，带「打开通知设置」按钮。
8. **按钮跳设置**。点「打开通知设置」⇒ 系统 设置 → 通知 页。
   若被拒（协议激活失败），记 `err=`，退法是只留正文那句路径说明、把按钮摘掉。
9. **限流**。再划 2 次（累计 3 次补发），第 4 次划掉之后应当出现
   `本会话放弃刷新状态通知（用户持续划掉）`，此后这个会话不再回来；
   同一天内引导横幅**不应再出现第二次**（`toast-guide.txt` 里是今天的日期）。
10. **收尾干净**。断开 VPN（或让看门狗拆掉）后，通知中心里那条常驻通知应当**消失**；
    `plugin.log` 应有 `已撤下状态通知（平台回调 Disconnect）`。
    留着不撤就是 bug（谎报"隧道运行中"）。
11. **对账**。会话结束后 `logtail sessions` 里那条 `evt=disconnect … upBytes=… downBytes=…
    toast=1`，与 `dataface-plugin.txt` 的 `UpBytes=/DownBytes=` 应当一致，
    且与通知里最后显示的累计值同量级。
12. **回归**。头条判据照旧：隧道内 `google 204` 心跳、国内直连不受影响、
    收尾 `nrpt=0 幽灵路由=0 profile=0`。状态通知不该改变这些数的任何一条 ——
    它只读计数，不碰包。

判绿标准：1~6 全过 ⇒ 这一批算成立；7~9 全过 ⇒ 用户的诉求（划掉→引导关横幅）算落地；
10~12 全过 ⇒ 没把已有的会话行为弄坏。第 4 条不过 ⇒ 明说没做成，不写"基本可用"。
